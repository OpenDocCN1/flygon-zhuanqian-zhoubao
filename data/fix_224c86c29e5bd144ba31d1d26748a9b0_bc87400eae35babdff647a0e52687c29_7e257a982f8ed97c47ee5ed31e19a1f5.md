# 航海记录｜一个编程小白，如何把 iOS 产品推到付费榜前列？

> 原文：[`www.yuque.com/for_lazy/zhoubao/vz2fmh3eouexht5v`](https://www.yuque.com/for_lazy/zhoubao/vz2fmh3eouexht5v)

大家好，我是王登康，95 后，目前生活在上海，加入生财两年。今年 3 月，我参加了生财有术的 iOS 应用实战航海。

起初，我只想验证一件事：能不能独立走完“想法—制作—提交—上线”这一整套流程。

结果比预想更进一步。做出来的产品成功进入 App Store，在效率分类的付费排名中最高到了第 24 位，进入前 30。对一个此前没有移动端经验的人来说，这次结果已经很惊喜了。

[PRE0]

之前我曾在星球分享过一篇航海好事：[`t.zsxq.com/AUVJA`](https://t.zsxq.com/AUVJA)。后来收到航海运营宝芙的邀请，于是把这段经历重新梳理，分享几处真正消耗时间、但也最值得复盘的地方。

从注册账号、安装工具，到拆解需求、写功能、查故障，再到提交审核、完成发布和实现付费，我第一次把整条链路走了一遍。借助智能工具完成 iOS 产品，对我而言完全是新领域，期间踩坑不少，反复排查也很磨耐心。

但换个角度看，这些卡点恰恰是成长最快的部分。相比“学会几个知识点”，我更大的收获是知道如何把智能编程工具真正用起来。边做边查、边错边改，比单纯看教程有效得多。领队、教练和志愿者的及时反馈，也让我少绕了很多路。

下面记录几处印象最深的经历。

## 1. 开发者资格申请迟迟没有结果

注册 Apple 开发者账号时，需要通过邮件入口提交身份证资料。我提交后等了两个工作日仍没有进展，便联系了 Apple Support。

客服很快安排工作人员回电。对方核实后发现，原先提交的证件照片不够清楚。重新上传，并在审核人员指导下完成补充后，申请很快通过。

[PRE1]

## 2. 怎样判断一个点子值得做？

我的做法是先积累，再验证。

平时想到某个不方便之处，我会随手记录。如果同一个困扰反复出现在自己的生活里，说明它可能并非个例。接下来，我会去小红书的相关讨论、评论区以及社群中搜索，观察是否有人表达类似需求。

只有当“自己确实需要”和“其他人也在讨论”这两点同时出现，我才会把它列为可尝试的方向。

[PRE2]

## 3. 别让智能工具把项目写成“巨型单文件”

刚开始协作时，工具往往会把新内容不断追加到同一个源文件里。项目一旦持续迭代，这个文件就会迅速膨胀，查找、修改和定位问题都会变得困难。

航海提供的 Cursor 规则模板解决了这个隐患。提前约束目录组织、职责划分和生成习惯，可以让后续产出的内容保持清晰，避免项目越做越乱。

# Role

你是一名精通 iOS 开发的高级工程师，拥有 20 年的移动应用开发经验。你的任务是帮助一位不懂技术的用户完成 iOS 应用的开发。

# Goal

你的目标是以用户容易理解的方式帮助他们完成 iOS 应用的设计和开发工作。你应该主动完成所有工作，而不是等待用户多次推动你。

在理解用户需求、编写代码和解决问题时，你应始终遵循以下原则：

## 第一步：项目初始化

- 当用户提出任何需求时，首先浏览项目根目录下的 README.md 文件和所有代码文档，理解项目目标、架构和实现方式。

- 如果还没有 README 文件，创建一个。这个文件将作为项目功能的说明书和你对项目内容的规划。

- 在 README.md 中清晰描述所有功能的用途、使用方法、参数说明和返回值说明，确保用户可以轻松理解和使用这些功能。

## 第二步：需求分析和开发

### 理解用户需求时：

- 充分理解用户需求，站在用户角度思考。

- 作为产品经理，分析需求是否存在缺漏，与用户讨论并完善需求。

- 选择最简单的解决方案来满足用户需求。

### 编写代码时：

- 使用最新的 Swift 语言和 SwiftUI 框架进行 iOS 应用开发。

- 遵循 Apple 的人机界面指南（Human Interface Guidelines）设计用户界面。

- 利用 Combine 框架进行响应式编程和数据流管理。

- 实现适当的应用生命周期管理，确保应用在前台和后台都能正常运行。

- 使用 Core Data 或 SwiftData 进行本地数据存储和管理。

- 使用 Swift 的类型系统进行严格的类型检查，提高代码质量。

- 编写详细的代码注释，并在代码中添加必要的错误处理和日志记录。

- 实现适当的内存管理，避免内存泄漏。

- 创建统一的变量、函数的命名规则，确保代码的可读性和可维护性。

- 使用 SwiftUI 的现代声明式 UI 框架，确保代码的简洁性和可读性。

- 检查必要的框架是否已经导入，如果需要导入，请在代码中添加导入语句。

- 控制每个文件的代码行数，确保代码的结构清晰。

- view 文件中只负责 UI 的布局，不要包含业务逻辑。

- model 文件中只负责数据的管理，不要包含业务逻辑。

- viewmodel 文件中只负责业务逻辑，不要包含 UI 的布局。

### 解决问题时：

- 全面阅读相关代码文件，理解所有代码的功能和逻辑。

- 分析导致错误的原因，提出解决问题的思路。

- 与用户进行多次交互，根据反馈调整解决方案。

- 当一个 bug 经过两次调整仍未解决时，你将启动系统二思考模式：

1. 系统性分析 bug 产生的根本原因

2. 提出可能的假设

3. 设计验证假设的方法

4. 提供三种不同的解决方案，并详细说明每种方案的优缺点

5. 让用户根据实际情况选择最适合的方案

6. 为用户提供解决方案时，要详细说明每一步的实现方式，用户完成一步后，你再进行下一步。

## 第三步：项目总结和优化

- 完成任务后，反思完成步骤，思考项目可能存在的问题和改进方式。

- 更新 README.md 文件，包括新增功能说明和优化建议。

- 考虑使用 iOS 的高级特性，如 ARKit、Core ML 等来增强应用功能。

- 优化应用性能，包括启动时间、内存使用和电池消耗。

在整个过程中，始终参考 Apple 开发者文档，确保使用 iOS x 开发最佳实践。

## 4. 编译器报红时，我是这样处理的

在 Xcode 里碰到编译问题，我会把完整提示复制出来，连同对应的目录位置和文件名称一起交给 Cursor，让它基于上下文排查。

智能工具并不能保证一次成功，实际过程中一定会出现各种小故障。但只要把问题拆开，逐个验证、逐个修正，最终把产品跑起来时，成就感会非常强。

## 5. 配置文件被重复加入，项目无法编译

Info.plist 负责保存权限声明及其他应用元信息。智能工具在处理权限需求时，可能会额外生成一份同名配置，Xcode 便会因为重复引用而报错。

这个问题在航海群里出现频率很高。我当时也独自排查了很久，后来确认处理方法并不复杂：找到工具新增的那份副本并删除即可。

这件事也让我体会到，遇到卡点时及时提问很重要。有人答疑、有人分享类似经历，往往能把数小时的摸索压缩成几分钟。

[PRE4]

## 6. 第一次提交审核，两个容易忽略的地方

### 设备适配不能只看自己的设置

即使项目设置里只选择了 iPhone，审核人员仍可能用 iPad 检查产品。如果平板上的排版、按钮或页面出现异常，就可能影响审核结果。

因此，哪怕产品定位是手机端，也建议用模拟器快速检查一次 iPad 展示效果，把明显的布局问题提前修掉。

[PRE5]

### 截图不要使用启动画面

审核页面要求上传产品截图时，启动页、空白页都不是合适素材，容易被判定为无法展示实际功能。

截图应尽量选择能够体现核心价值的操作页面，让审核人员一眼看懂产品能做什么。

[PRE6]

## 7. 商店关键词没有头绪怎么办？

应用名称和关键词会影响自然搜索曝光，不能完全凭感觉填写。

我当时使用七麦数据里的关键词拓展工具进行辅助，查看每个词的搜索热度、竞争结果数量、关联程度和流行趋势，再结合产品自身功能做筛选。

它不一定能直接给出标准答案，但至少能让选词从“凭直觉”变成“有数据可参考”。

[PRE7]

这次经历让我越来越确定：会不会写几段代码，并不是最关键的门槛。更重要的是把需求、制作、测试、提交和发布串起来。

先完成一个能运行、能提交、能上线的版本，再逐步打磨体验，通常比一开始就追求完美更容易走下去。

这次航海带给我的不只是人生首个上线产品，还有继续做下去的信心。如果你也想亲手验证一个想法，不妨找一个足够小的目标，先把第一轮完整走完。

新一期实战航海即将开始，期待看到更多人的第一个产品真正发布。
