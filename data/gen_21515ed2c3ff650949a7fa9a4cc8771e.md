# 一、AI Agent 筑基

**Agent：能够独立完成工作的 AI 员工**

## 1. Agent 到底是什么？

可以把 Agent 理解成一名被明确安排了目标、职责边界、工作工具和验收要求的 AI 员工。

你只需要告诉它最终想得到什么结果，Agent 就会自己分析任务、拆解步骤、调用工具、处理异常，最后交付产物。

我现在处理很多事情时，都会直接交给 Codex。

以前安装一个软件，我需要自己搜索官网、找到正确安装包、下载、配置，再确认软件是否正常运行。

现在，我通常只需要对 Codex 说：

“帮我安装这个软件。”

它就可以自行寻找合适的下载渠道，完成安装，并检查最终能否正常使用。

Codex 本身就是一种 Agent，更具体地说，它是编程 Agent，也可以被扩展成通用型 Agent。

它擅长阅读和修改文件、编写代码、执行命令、操作项目。配合浏览器、CLI、MCP 以及各种插件后，它还可以完成资料检索、文档处理、数据整理、软件安装等工作。

因此，Codex 的能力边界远不止写代码。

不过，不同项目之间的工作环境通常是相互隔离的，新对话也不会自动继承上一段对话的完整记忆。

这反而提供了一种非常实用的设计方式：

一个项目文件夹，对应一名负责特定工作的 AI 员工。

你可以在这个项目里放入相关代码、规则和文件，明确告诉它：

- 你是谁；
- 你的职责是什么；
- 你的工作流程是什么；
- 你的输出标准是什么；
- 哪些事情不能做。

Codex 进入这个项目后，就会按照这套设定工作。

不同项目拥有不同规则，Codex 也就可以承担不同岗位，成为一个个专门化的 AI 员工。

所以，Agent 并不是凭空创造出来的。我们真正要做的，是为 Agent 设计一套清晰、稳定、可复用的工作设定。

## 2. 一名 AI 员工的设定应该长什么样？

每类工作的流程不同，对应的项目结构自然也不会完全一样。

目前并不存在一套适用于所有业务的“标准答案”。刚开始时，也没有必要一上来就设计一个非常复杂、看起来很专业的目录。

大多数成熟项目，都是在真实使用过程中逐步形成的。

你可以先让 AI 参与工作。随着任务不断推进，项目文件夹里会慢慢出现：

- 原始材料；
- 处理后的结果；
- 脚本；
- 验证工具；
- 业务规则；
- 知识库；
- 临时文件；
- 历史记录。

当一项业务流程真正跑通后，再让 Codex 回头梳理整个项目，把已经验证过的步骤、规则、禁区和验收标准固化下来。

刚看到这里，很多新手可能会担心：

这么多文件该怎么整理？

如果让 Codex 自动沉淀，会不会整理错误？

流程能不能稳定复用？

其实没必要过度焦虑。后面第三部分会提供可以直接使用的提示词。只要按框架逐步推进，通常不会出现太大问题。

最终，你会得到一个结构清晰、能够反复执行的项目。沉淀出来的 Skill 等文件，也可以迁移到其他项目中继续使用。

经过整理之后，原本散落在聊天记录和各种文件中的经验，会逐渐变成：

- 项目目录；
- AGENTS.md；
- Skill；
- 脚本；
- 验证器；
- 业务资料；
- 输出模板。

这时，一次性的经验就被转化成了可以长期复用的工作系统。

## 3. 关于 Agent 的几个关键理解

理解 Agent 的工作机制后，很多以前觉得奇怪的操作就变得容易解释了。

### 为什么新对话开始时，要先让 Agent 阅读项目？

因为新对话不会自动拥有之前的聊天记忆。

让 Agent 重新阅读项目文件，本质上就像让新员工入职培训，重新了解：

- 自己的身份；
- 负责的工作；
- 具体流程；
- 使用的工具；
- 交付标准；
- 禁止事项。

### 为什么一个项目最好只对应一名 Agent？

更准确地说，一个项目最好只服务于一类明确工作。

项目在长期执行中，会不断积累新的规则、脚本、素材和结果。如果同一个项目一会儿做内容，一会儿做数据，一会儿又处理客户问题，无关信息就会逐渐混在一起。

最后可能出现：

- 工作职责模糊；
- 规则彼此冲突；
- 文件难以查找；
- Agent 不知道当前任务优先级；
- 项目逐渐失去稳定性。

一个干净的项目，应该围绕一类明确业务持续积累。积累越多，Agent 对该项工作的理解就越深，执行结果也会越稳定。

### 为什么不能只把规则放在聊天记录里？

因为聊天上下文是有限的。

对话变长以后，早期内容可能被压缩，甚至被遗忘。今天刚刚解决的问题，换一个新对话后，可能又会重新出现。

更可靠的做法，是把经过验证的经验及时写入项目文件：

- 长期原则放入 AGENTS.md；
- 完整工作流程写入 Skill；
- 确定性、重复性的动作交给脚本；
- 明确的验收要求交给验证器。

这样，即便换了新对话，Agent 重新读取项目后，也能按照同一套规则继续工作。

因此，搭建稳定 Agent 的核心，不是写出一条“完美提示词”，而是完成这样一个循环：

**真实执行 → 人工纠偏 → 经验沉淀 → 再次验证**

真正重要的是把一次成功转化为长期能力，让项目保持边界清晰、流程可复用，也让 Agent 在换一个对话后仍然能够重新上岗。

# 二、Skill：AI 员工的标准作业手册

理解了 Agent，下一步就要理解 Skill。

## 1. Skill 是什么？

如果 Agent 是一名员工，那么 Skill 就是它完成某类工作的操作手册。

一份完整的 Skill，通常需要告诉 Agent：

- 什么情况下应该启用这项能力；
- 开始前要检查哪些内容；
- 任务应该按什么顺序推进；
- 哪些动作可以交给脚本；
- 哪些地方必须由 Agent 自己判断；
- 遇到异常时是继续、重试还是停止；
- 最终需要生成哪些文件；
- 怎样才算达到交付标准。

换句话说，Skill 是业务流程、操作步骤、判断边界、工具使用方式和验收要求的集合。

在第一次执行任务时，我们往往会不断补充新的要求：

“这个内容不能删除。”

“Cookie 失效后要先停下来，不要继续领取任务。”

“推荐产品前，必须先通读全文。”

“需要生成三个文件，验证通过后才能修改飞书状态。”

最初，这些要求都只存在于当前聊天里。当前对话中，Agent 可以按照你的提醒执行；但换到新对话，很多规则就会消失。

如果某项要求已经在真实任务中被验证有效，并且未来还会反复使用，就应该把它从聊天记录中提取出来，写入 Skill。

这样，新对话中的 Agent 只要读取这份 Skill，就能重新掌握相同的工作能力。

## 2. 一份 Skill 通常包含哪些文件？

一个 Skill 通常是一个独立文件夹，以 SKILL.md 作为入口文件，再根据实际需要添加脚本、参考资料、模板和验证工具。

常见结构可以包括：

### SKILL.md

这是整个能力的总入口，主要写清楚：

- 这项 Skill 解决什么问题；
- 什么任务会触发它；
- 整体执行流程是什么；
- 哪些情况下必须停止；
- 最终应该交付什么结果。

### references/

用于保存详细规则和背景资料，例如：

- 字段说明；
- 内容规范；
- 异常类型；
- 输出格式；
- 业务定义。

这样可以避免把所有内容都堆在一个过长的 SKILL.md 里。

### scripts/

用于保存可重复执行的代码，例如：

- 请求接口；
- 下载字幕；
- 解析 JSON；
- 自动创建目录；
- 检查文件；
- 批量处理数据。

这类输入和输出比较明确的动作，交给脚本完成往往更加稳定。

### templates/

用于保存输出模板，帮助 Agent 明确最终产物应该包含哪些字段、标题和基本结构。

### examples/

用于保存成功案例与失败案例。

当抽象规则不容易理解时，案例能够帮助 Agent判断什么结果是合格的，哪些结果不能接受。

当然，这只是常见组织方式，并不是唯一答案。不同业务可以使用不同的目录结构，关键在于：每个文件都应该有清晰职责。

## 3. SKILL.md 应该写什么？

我们案例中的 SKILL.md 大致就是按照这样的思路设计的。

不过你不需要一开始手动编写。后面可以直接让 Codex 根据实际流程帮你生成，再结合任务执行结果持续修改。

## 4. Skill 从触发到执行的完整链路

当用户提出一项任务后，Agent 首先要判断：当前任务是否符合某个 Skill 的适用条件。

如果符合，它就读取对应的 SKILL.md，并根据里面的要求，按需加载参考资料、调用脚本、使用模板。

整个过程可以概括为：

用户提出任务  

↓  

Agent 判断需要使用哪项 Skill  

↓  

读取 SKILL.md  

↓  

根据需要读取规则、模板和案例  

↓  

调用脚本、CLI 或 MCP 执行动作  

↓  

Agent 进行语义判断  

↓  

运行验证器  

↓  

交付最终结果

这种设计不需要 Agent 一开始就把整个项目的所有内容都读进上下文。

只有任务真正需要某项能力时，才加载相应的 Skill 和资料。这样不仅能减少无关信息干扰，也能让项目结构更加清楚。

如果你担心 Agent 自动调用错误，也可以直接指定：

“请使用 XX Skill 完成 XX 任务。”

## 5. Skill 如何安装和查找？

如果你想使用别人已经制作好的 Skill，可以直接告诉 Codex：

“帮我安装这个 Skill。”

默认情况下，Skill 往往会被安装到全局目录。安装后，你也可以在相应位置查看当前已经安装的 Skill。

不过，大多数 Skill 都是服务于特定业务流程的。

如果不同业务中存在名称相近、功能相似的 Skill，或者全局 Skill 越来越多，担心 Codex 调用错误，那么可以不进行全局安装，而是把 Skill 放进对应项目文件夹，作为该项目专属能力。

因为 Skill 本质上就是一个包含说明文件和相关代码的文件夹。

全局 Skill 和项目 Skill 的核心内容并没有本质区别，主要差异在于：

- 存放位置不同；
- 生效范围不同；
- 是否可被多个项目调用不同。

## 6. Skill 和 Agent 有什么区别？

很多人会疑惑：Skill 里面也有具体步骤，那它和 Agent 到底有什么不同？

可以这样理解：

如果任务比较短，步骤较少，直接调用一个 Skill 就足够了。

你只需要告诉 Codex：

“使用这个 Skill 完成某项任务。”

但如果任务链路很长，需要经历多个环节，就更适合搭建 Agent。

Agent 可以按照完整工作流，依次调用多个 Skill，让不同能力协同完成一个复杂任务。

比如，我的一些复杂 Agent 会串联调用 7 个 Skill。每个 Skill 负责一道相对独立的工序，而每道工序内部又包含多个具体动作。

这种方式的优点是：

- 整体流程更清晰；
- 每个环节更容易单独维护；
- 某个能力可以被其他项目复用；
- 后续迁移和修改成本更低。

简单总结：

**Skill 是单项能力，Agent 是能够调度多项能力完成完整任务的工作主体。**

# 三、知识库：AI 员工的资料室与历史档案

如果 Agent 是员工，Skill 是操作手册，那么知识库就是它长期使用的资料库和工作档案。

知识库可以保存：

- 业务背景；
- 原始资料；
- 历史产物；
- 审核记录；
- 已确认的经验；
- 可复用的规则；
- 重要案例。

它的作用，是让 Agent 在新的对话中，仍然能够重新找到完成任务所需的背景信息。

不过要注意：知识库并不是 AI 自动拥有的永久记忆。

它本质上仍然是一批被保存下来的文件。Agent 每次开始任务时重新读取这些文件，才会表现得像“记得以前发生过什么”。

很多人刚开始使用 AI 时，会把资料和要求都堆在聊天记录中。

短期来看，这样没有问题。当前对话里的 Agent 可以根据上下文理解业务，也能记住你刚刚提出的规则。

但聊天越来越长后，就会出现一系列问题：

- 早期内容可能被压缩或丢失；
- 临时讨论和正式规则混在一起；
- 很难分辨哪一版结论才是最终版本；
- 换新对话后需要重新介绍业务；
- 资料难以稳定检索和复用；
- 其他 Agent 不知道应该读取哪段记录。

聊天记录适合讨论、试错和达成共识，但不应该成为长期保存业务知识的唯一位置。

一条信息只要已经确认，并且未来还会继续使用，就应该从聊天里提取出来，写入知识库或项目设定。

## 1. Obsidian：适合 AI 读取的知识管理工具

Obsidian 本质上是一款用于管理本地 Markdown 文件的工具。

一个 Obsidian 知识库，实际上就是一个包含许多文件和文件夹的普通本地目录。

即使未来不再使用 Obsidian，这些 Markdown 文件也依然可以被 VS Code、Codex、Claude Code 或其他工具读取和处理。

因此，它不仅适合人阅读，也非常适合作为 AI 的资料来源。

## 2. 从简单文件夹开始建立知识库

很多人一开始搭建知识库，就会纠结：

- 目录要分几层？
- 标签应该怎么设计？
- 要不要建立双向链接？
- 每个主题应该如何分类？

其实没必要一开始就把这些问题全部解决。

不同业务需要保存的内容不同，因此并不存在一套人人通用的“黄金目录”。

更实用的做法是：先让知识库服务真实任务，再让结构随着工作慢慢形成。

当你处理了几项任务后，会逐渐发现：

- 哪些文件几乎每次都会产生；
- 哪些信息经常需要查询；
- 哪些资料应该集中维护；
- 哪些目录开始变得混乱；
- 哪些字段适合做成固定模板；
- 哪些主题需要建立索引。

这时再让 Codex 统一整理现有资料，调整目录、补充索引、制作模板，往往比一开始凭空设计更可靠。

知识库不是靠想象设计出来的，而是先从真实业务中自然生长，再通过整理和固化变得清晰。

## 3. 项目文件夹与知识库如何分工？

项目文件夹和知识库既可以放在一起，也可以分开管理。

项目文件夹更像 Agent 的办公室，通常放置：

- AGENTS.md；
- Skill；
- 脚本；
- 验证器；
- 配置文件；
- 临时工作目录；
- 任务执行记录。

知识库更像长期档案室，主要保存：

- 原始资料；
- 整理后的内容；
- 历史产物；
- 主题索引；
- 审核结论；
- 可被多个任务反复使用的业务知识。

如果项目规模不大，两者完全可以放在同一个文件夹里。

当资料数量不断增加后，也可以把知识库独立拆分出来，再将它作为项目的资料目录接入。

## 4. 怎样让 Agent 准确找到需要的资料？

当知识库规模较小时，可以让 Agent 先整体浏览目录，建立基本认识。

但当文件越来越多，就不适合每次都把全部资料塞进上下文。

更合理的方式是分层读取：

先查看项目规则  
→ 再读取知识库总索引  
→ 根据当前任务定位相关主题  
→ 打开对应文件和原始资料  
→ 完成任务并生成新产物  
→ 更新索引和审核状态

这样既能降低无关信息的干扰，也能避免上下文被大量不相关内容占满。

# 四、CLI / MCP：让 Agent 真正连接外部世界

前面我们已经明确了几个角色：

- Agent 负责理解目标、拆分任务和做出判断；
- Skill 负责规定某项工作应该如何完成；
- 知识库负责保存长期需要使用的资料。

但如果 Agent 只能在聊天框里思考，不能打开软件、读取系统、修改文件或操作业务平台，那么它依然只是一个会给建议的大脑。

CLI 和 MCP 的作用，就是把 Agent 的判断连接到外部工具，让它从“会回答”变成“能执行”。

## 1. 外部工具为什么重要？

真实业务通常不会只发生在聊天窗口里。

它可能涉及：

- 读取飞书文档；
- 领取或更新任务；
- 修改表格；
- 查询 GitHub；
- 下载视频；
- 处理字幕；
- 执行本地脚本；
- 读取数据库；
- 操作浏览器；
- 将最终结果写回业务系统。

这些动作都需要依赖具体工具完成。

Agent 负责判断“现在应该做什么”，CLI 和 MCP 则负责把这个决定传递给外部系统，真正完成操作。

## 2. CLI：通过命令行调用软件和系统

CLI，也就是命令行工具，可以让 Agent 通过终端执行各种确定性操作。

例如：

- 创建和整理文件夹；
- 批量重命名文件；
- 运行数据处理脚本；
- 调用接口；
- 下载和转换文件；
- 检查输出结果；
- 执行项目构建；
- 读取系统信息。

对于输入明确、步骤固定、结果容易验证的工作，CLI 通常比手动操作更加稳定。

而 Agent 的优势在于，它可以先理解任务，再根据需要选择合适的命令和脚本执行。

这样，Agent 负责思考与调度，CLI 负责具体落地，二者结合后，才真正具备把业务流程自动化的能力。
