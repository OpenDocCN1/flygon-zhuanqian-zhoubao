# 一、AI Agent 筑基

Agent：可独立完成工作的 AI 员工

### 1. 什么叫 Agent？

Agent 是被赋予目标、权限边界、工具与验收标准后，能够持续执行一类工作的执行主体。用户只说想要什么结果，它会自行理解需求、拆解路径、调用工具、处理异常并交付成果。

我现阶段大部分事务都交给 Codex 处理。

过去装软件，要自己查官网、找安装包、下载、配置并验证；现在只需说“帮我装这个软件”，它就能找到靠谱渠道、完成安装并自检可用性。

Codex 本身就是一个编程 Agent，也是通用 Agent。它擅长读写文件、写代码、执行命令、操盘项目。借助浏览器、CLI、MCP 与插件，还能完成检索、文档、数据整理、软件部署等海量工作，能力边界远超代码。

不同项目间环境相对隔离，新对话不会自动继承全部记忆。这反而方便我们做岗位化设计：一个项目文件夹对应一名专岗 AI 员工。在该文件夹里留下代码、设定和资料，明确身份、职责、流程与标准，Codex 进入后即按此设定执行。不同项目规则不同，Codex 就能扮演不同角色。

做 Agent 员工的本质，是为 Agent 设计清晰、可复用、可沉淀的工作设定。

### 2. AI 员工的设定长什么样？

不同业务类型，项目结构自然不同。目前并无一套放之四海而皆准的黄金目录。起步时不必追求复杂完整的架构。

多数成熟项目都是在真实运转中长出来的。先让 AI 参与干活，随着任务推进，文件夹里会自然出现原始素材、产出结果、脚本、校验器、规则库、知识库与临时文件。

待某条业务链路跑通后，再让 Codex 回溯整理，把已验证的操作步骤、业务规则、禁区与验收标准固化下来。

看到这里新手可能会焦虑：文件太多怎么归档？自动沉淀会不会乱？能否稳定复用？其实不必过度担心。第三部分会给出可直接使用的提示词，按框架逐步推进基本不会出错。最终会得到结构清晰、可反复复用的项目，沉淀的 Skill 等资产还能跨项目迁移。

整理后，零散在聊天记录与文件里的经验会变成项目目录、AGENTS.md、Skill、脚本、验证器、业务资料与输出模板，形成可长期复用的工作系统。

### 3. Agent 使用的关键点拨

理解原理后，一些反直觉的操作就合理了。

新对话为何要先让 Agent 读项目？因新对话无历史记忆。让它先读项目文件，相当于新员工入职培训，了解身份、职责、流程与标准。

为何一个项目最好只对应一个 Agent，并长期专岗？项目在运行中会持续沉淀代码、规则、素材与产出。若让同一项目处理互不相关的工作，会导致信息混杂、职责漂移与规则冲突。时间久了 Agent 会迷失定位。

保持项目干净，服务于一类明确工作，积累越深理解越稳。

为何不能仅依赖聊天记录保存规则？上下文有限，对话越长早期指令越易被压缩丢失。今天刚纠正的问题，下次对话可能重现。

正确做法是把已验证的经验及时固化：长期原则写入 AGENTS.md，完整流程写入 Skill，确定性动作交脚本，验收标准交验证器。这样换对话后，Agent 重新读取项目即可按同一套标准工作。

稳定产出 AI 员工的核心，不是一条完美提示词，而是“真实执行→人工纠偏→规则沉淀→重新验证”的闭环。把一次成功转化为长期能力，保持边界清晰、流程可复用，让 Agent 换对话也能重新上岗——这正是本次分享想讲清的事。

# Skill：AI 员工的作业手册

理解 Agent 后，下一步是理解 Skill。

### 1. Skill 是什么？

如果 Agent 是员工，Skill 就是它执行某类工作的标准作业手册。它会说明何时启用、前置检查、执行顺序、可脚本化环节、需人工判断处、异常处理策略、交付物清单与合格标准。

Skill 是流程、规则、判断边界、工具与验收的集合。跑通首条任务时，我们通常会不断补充要求：某处不可删除、Cookie 失效要停止、推荐前需通读全文、必须生成三文件验证通过后才能改飞书状态……这些要求初始都落在聊天里，换对话就不在。

一旦某条要求经真实任务验证且会反复使用，就应从聊天中提取进 Skill。新对话的 Agent 读取后即可恢复该能力。

### 2. Skill 的基本组成

一个 Skill 通常是一个独立文件夹，以 SKILL.md 为入口，按需放入脚本、参考资料、模板与验证工具。

SKILL.md 为总入口，说明能力边界、触发条件、整体流程、停止时机与交付物。

references/ 保存详细规则，如字段说明、内容规范、异常类型、输出结构，避免塞满 SKILL.md。

scripts/ 保存可重复代码，如接口请求、字幕下载、JSON 解析、目录创建、文件检查等输入输出稳定、适合代码化的工作。

templates/ 保存产物模板，明确输出应包含的字段、标题与结构。

examples/ 保存正反案例，帮助 Agent 理解合格与不合格的边界。

结构并非唯一，关键是职责清晰。

### 3. SKILL.md 写什么

案例中的 SKILL.md 即按此思路生成，无需手动从零写，后续可让 Codex 基于真实流程生成并迭代。

### 4. Skill 的触发到执行链路

用户提出任务 → Agent 判断是否匹配某 Skill → 读取 SKILL.md → 按需加载规则、模板、案例 → 调用脚本/CLI/MCP → Agent 做语义判断 → 运行验证器 → 交付结果。

这种设计避免一次性把所有规则塞入上下文，按需加载，保持项目清晰，减少干扰。也可直接指令“使用 XX Skill 完成 XX”，降低误调风险。

### 5. Skill 的安装与查找

可让 Codex “帮我安装这个 Skill”。默认装到全局，也可在对应位置查看已安装列表。若业务特定、担心全局冲突，可不全局安装，只放进项目文件夹作为专属能力。本质都是包含说明与代码的文件夹，区别在于位置与生效范围。

### 6. Skill 与 Agent 的区别

流程短、操作单一时，直接用 Skill 足够。如“使用这个 Skill 完成任务”。

流程长、涉及多环节，则更适合搭建 Agent。Agent 能按工作流依次调用多个 Skill 协同完成复杂任务。如我部分复杂 Agent 会串联7个 Skill，每个 Skill 负责一道工序，内部再拆多步，便于维护、复用与迁移。

简言之，Skill 是单项能力，Agent 是调度多项能力完成完整任务的主体。

# 知识库：AI 员工的资料库与工作档案

Agent 是员工，Skill 是手册，知识库则是长期使用的资料库与档案。它保存业务背景、参考资料、历史产物、审核记录与已确认经验，让新对话也能恢复上下文。

注意：知识库不是 AI 大脑里的永久记忆，而是一组文件。Agent 每次重新读取文件才表现得像“记得以前的事”。

把大量资料堆在聊天记录里，短期可行。随对话变长会出现压缩丢失、规则与临时讨论混杂、版本难以分辨、换对话需重新交底、检索复用困难等问题。聊天适合讨论与试错，长久保存应写入知识库或项目设定。

### 1. Obsidian：适合 AI 读取的知识管理工具

Obsidian 本质是本地 Markdown 文件查看器。知识库就是一个普通本地目录，停止使用 Obsidian 后，文件仍可被 VS Code、Codex、Claude Code 等读取，兼顾人读与机读。

### 2. 从简单文件夹开始搭建

不必一开始纠结目录层级、标签体系、双向链接。不同业务保存内容不同，不存在通用黄金结构。更实际的做法是先服务真实任务，让结构随工作自然生长。

处理几条任务后会发现哪些文件常生成、哪些信息常被查、哪些资料需集中、哪些目录混乱、哪些字段适合模板化、哪些主题需索引。此时再让 Codex 统一梳理，效果更可靠。

知识库是先从业务中生长，再经整理固化。

### 3. 项目文件夹与知识库的分工

可放一起也可分开。项目文件夹像办公室，含 AGENTS.md、Skill、脚本、验证器、配置文件、临时目录、任务记录。

知识库像档案室，保存原始资料、整理后内容、历史产物、主题索引、审核结论、可多任务复用的业务知识。

小规模可合放，随着资料增多可独立拆分，再作为资料目录接入项目。

### 4. 让 Agent 准确找到资料

知识库小时可整体浏览，建立全貌。规模大了应分层读取：项目规则 → 知识库总索引 → 定位相关主题 → 读取对应文件与原始资料 → 完成任务写回产物 → 更新索引与审核状态。降低干扰，避免上下文被无关资料填满。

## CLI / MCP：Agent 连接外部工具的操作通道

Agent 能思考规划，Skill 规定怎么做，知识库提供资料。若只能在对话框里思考，仍只是建议大脑。CLI 和 MCP 是把判断变成实际动作的操作通道。

### 1. 从会回答到能操作：外部工具的价值

真实工作涉及飞书文档、任务领取、表格修改、GitHub 查询、视频下载、字幕处理、本地脚本、数据库、浏览器操作、结果回写系统等。Agent 负责判断下一步做什么，CLI/MCP 负责把判断传给外部系统落地。
