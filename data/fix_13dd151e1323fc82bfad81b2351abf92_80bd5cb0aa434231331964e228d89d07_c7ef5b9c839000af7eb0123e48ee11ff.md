# 把 AI 训练成能独立办事的数字同事：从 CLI、MCP 到完整 Agent 工作流

想让 AI 真正参与业务，关键不只是换一个更强的模型，还要给它准备稳定的工具、清晰的规则，以及可以反复运行的工作环境。

下面就以“批量处理 B 站视频字幕，并整理到 Obsidian”为例，完整走一遍搭建过程。

## 一、先认识两类基础工具

### 1. CLI：让 AI 通过终端调用软件

CLI 是 Command Line Interface，即命令行接口。简单来说，它就是软件提供的一套文字指令。用户可以在终端输入命令完成操作，自动化程序或 Agent 也能调用这些命令。

CLI 之所以适合接入 Agent，是因为它通常具备几个特点：

- 输入格式明确；
- 输出结果相对稳定；
- 可以被脚本串联；
- 容易记录和重复运行；
- 能够嵌入更长的自动化流程。

只要某条命令在电脑上能够稳定执行，Agent 就能把它当成一个可靠的工作节点。

如果希望 Codex 处理飞书里的资料，可以安装飞书 CLI，让它直接连接飞书并完成下载、创建、修改等操作。再结合相应的 Skills，能够覆盖更多业务场景。

### 2. MCP：把外部服务变成标准化工具

MCP 的全称是 Model Context Protocol，即模型上下文协议。

它的作用，是把外部系统的功能整理成一套结构化工具。Agent 不需要自行研究底层接口，也不用手动拼接复杂请求，只要按照工具说明提供参数，再读取返回结果即可。

例如：

- 飞书 MCP 可以提供文档搜索、表格读取、任务创建、状态更新等功能；
- GitHub MCP 可以提供仓库读取、Pull Request 查看、评论获取等功能。

[PRE4]

从使用体验上看，MCP 就像一套提前布置好的操作面板。每个工具有什么用途、需要哪些参数、最后会返回什么内容，都会事先约定好。

需要哪一种 MCP，直接交给 Codex 安装即可。

当然，如果没有可用的 CLI 或 MCP，Agent 也能借助浏览器，或者 computer use 插件来操作网页。但网页方案高度依赖页面布局、登录状态和弹窗情况，页面一改版，流程就可能失效。

所以在条件允许时，优先选择稳定的 CLI 或 MCP。

# 二、正式搭建前，先把常用装备准备好

网络环境先自行处理，再安装 Codex。

首次打开 Codex 后，可以先配置两个常用插件。浏览器建议使用 Chrome，并将它设为默认浏览器，同时开放完整访问权限。我平时使用 GPT5.6 Sol 极高模式，速度设置为 1.5 倍。

接着新开一个不绑定项目的会话，缺什么软件，就让 Codex 现场完成安装。

| 工具 | 主要用途 |
|---|---|
| Codex | 主要执行工作 |
| GitHub Desktop | 查看变更、追踪问题、回到旧版本 |
| Obsidian | 保存可检索、可关联、可长期复用的内容 |
| Hermes | 另一套 Agent 执行环境 |
| 飞书 | 展示业务任务和处理进度 |
| 控制台 | 统一管理待办事项 |
| VS Code + Claude Code 插件 | 辅助 Obsidian 内容创作，目前 GPT 写文案的质量还有提升空间 |

可以直接给 Codex 下面这些指令，表达清楚需求即可，不必逐字照抄：

> 请下载并安装 GitHub 移动端。

> 请安装 Obsidian，它是一款知识库软件。Hermes 暂时不用安装，第四部分再处理。

> 请下载 VS Code，将界面切换为中文，并安装 Claude Code 插件。

准备好之后，就可以制作第一个 AI 数字员工了。

本文采用的示例是：

> 批量输入 B 站参考视频链接，获取字幕，拆解内容，再保存到 Obsidian 知识库。

# 三、把重复业务改造成 Agent

## 一套八阶段搭建流程

这套方法是在包子老师六步法的基础上重新整理出来的。

| 阶段 | 具体动作 | 目的 | 最终效果 |
|---|---|---|---|
| 1 | 准备项目目录与版本管理 | 让资料集中保存并可追踪 | 出错时能够审查和撤销 |
| 2 | 让 AI 熟悉背景资料 | 避免在不了解业务的情况下贸然行动 | 减少错误推断 |
| 3 | 明确目标并调研方案 | 先确认技术路线是否可行 | 得到落地计划 |
| 4 | 完成一个最简样例 | 用真实结果暴露隐藏问题 | 形成 MVP |
| 5 | 接入飞书任务面板 | 支持排队、协作和批量处理 | 业务流程可视化 |
| 6 | 整理规则、Skills、脚本和检查机制 | 把临时共识变成项目资产 | 形成可复用流程 |
| 7 | 在当前会话再次运行 | 检验完整链条 | 找出流程漏洞 |
| 8 | 换一个全新会话重跑 | 排除聊天记忆带来的影响 | 证明能力属于项目本身 |

## 阶段一：准备项目目录和 Git

### 1. 建立独立工作目录

先创建一个专用文件夹，再让 Codex 打开它作为项目目录。

目录名称最好短一些、容易理解，尽量使用英文，避免使用“新建文件夹”“测试版”这类含义模糊的名字。

与项目相关的原始资料，可以复制一份放进去，原始文件继续保留在原处。

### 2. 加入版本管理

随后在该目录中初始化 Git，并用 GitHub Desktop 进行管理。

Git 会保存文件新增、修改和删除的历史记录，GitHub Desktop 则提供可视化界面。

这一步很重要，因为 Agent 往往会连续创建和修改许多文件。没有历史记录时，很难判断哪些内容来自原始资料，哪些是 AI 新生成的，也不容易撤销错误改动。

先在电脑上准备一个空目录。

如果有参考资料，再在项目目录里建立一个专门的资料子目录，将相关文件复制进去。尝试本文示例时，也可以把压缩包解压到这个位置。

## 阶段二：先让 AI 观察项目

在提出修改要求之前，先让 Codex 阅读项目现有内容，包括文档、示例结果、PDF、PPT 和必要图片。

重点是明确告诉它：当前只阅读，不执行修改。

可以这样说：

> 暂时不要做任何改动，请完整阅读项目目录中的所有内容。如果有文档、PDF 或 PPT，请同时查看其中的文字和图片。

如果需要参考外部页面，可以说：

> 先不要执行操作，请阅读下面的链接，完整查看其中的文字与图片。【链接 1】【链接 2】

针对本文案例，也可以简化为：

> 请先阅读项目目录中的全部文件，判断这个项目的用途和现有结构。

## 阶段三：描述目标，让 AI 先调研

不要一上来就要求它写程序。先把业务目标、输入、输出和期望流程说清楚，让它先给出技术方案。

例如：

> 暂时不要编写代码。我想实现这样一个流程：输入一个 B 站视频链接，获取视频信息和字幕，再对字幕进行整理，最后保存到 Obsidian 知识库。请到 GitHub 查找质量较高的项目和 Skills 作为参考。完成调研后，先说明可行方案、技术路径和所需信息，等我确认后再动手。

如果手里已经有源码，可以直接让它基于现有代码继续；如果没有，也可以先让它从头研究。

接着询问：

- 当前还缺少哪些信息？
- 是否具备运行最简版本的条件？
- 最先应该验证哪一个环节？

[PRE6]

样的话就可以问问他还需要什么信息，能不能跑最小 MVP，然后执行。你认为现在是否达到了最小闭环的开工条件？如果可以，先出抓取这个链接的字幕【链接】。

知识库不存在唯一正确答案。只要它能够稳定保存内容、方便查找，并且确实解决问题，就是合适的方案。

## 阶段六：把经验沉淀成项目资产

当最简流程已经验证通过，就进入稳定生产阶段。此时重点不再是继续拉长聊天记录，而是把已经确认的业务规则写入项目。

通常需要整理四类内容：

- **AGENTS.md**：记录整个项目必须遵守的总规则；
- **Skill.md**：记录某一类任务的标准操作顺序；
- **脚本**：处理稳定、重复、机械的数据操作；
- **验证器**：检查输出是否满足最低要求。

[PRE18]

这里必须注意：脚本只能做确定性的事情，不能替 AI 进行开放式语义判断。

早期为了尽快跑出结果，很容易在程序里加入临时规则：

[PRE19]

这条规则或许适用于当前样本，但换一条视频，作者可能会说：

- “接下来我们按照价格展开。”
- “现在进入产品推荐部分。”
- “先从基础款开始介绍。”
- 也可能完全没有明显的过渡表达。

如果程序把某句话、某个行号、某个价格，甚至“第几款”直接写死，那么它只能处理少数相似样本。

更可靠的分工应该是：

- AI 阅读完整内容，结合上下文判断语义边界；
- 脚本保存 AI 已经做出的判断，并负责文件和格式检查；
- 验证器负责阻止不符合底线要求的结果进入下一阶段。

[PRE20]

[PRE21]

本次演示需要特别强调一个危险点：不要依靠固定句子、固定价格、固定行号或产品序号切割文章。

程序负责稳定执行，AI 负责理解语义，验证器负责最后把关。三者各自承担不同职责，才能避免流程既不可靠又难以扩展。

另外，每轮生产都应把 Cookie 检查放在最前面，而且要静默完成：

1. Cookie 缺失或失效，立即中止；
2. 在确认凭证有效前，不读取业务任务；
3. 不把 Cookie 写入日志或归档；
4. 本地文件全部生成后，先运行检查程序；
5. 再由 AI 完成最终复核；
6. 所有条件满足后，才允许将飞书任务标记为完成。

这样设计，是因为聊天里的约定可能随着会话结束而消失，而写死的程序规则又只能适应单一案例。

把规范、工具和验收机制拆开保存，既能保留流程的稳定性，也能让 AI 保持处理复杂语义的弹性。

最终得到的，其实是一份可重复使用的岗位说明。下一次只要告诉 AI“处理任务 2”，它就应该知道：

- 先检查哪些前置条件；
- 到哪里读取任务；
- 结果如何保存；
- 哪些情况需要停止；
- 何时才允许回写成功。

## 阶段七：在原会话里做一次回归检查

每次修改项目规则、脚本或文件结构后，都要重新运行一条真实任务。

目的，是确认新改动没有破坏原本正常的功能。如果出现执行失败或结果质量下降，就修正问题，必要时恢复到之前的版本。

## 阶段八：换新会话验证独立运行能力

完成上一轮检查后，关闭原来的长对话，重新开启一个全新会话。

让 Codex 重新阅读项目文件，再执行一条任务。

这一步是为了确认：它能否仅依靠项目中保存的规则和 Skills 完成工作，而不是依赖此前聊天中没有写入项目的临时记忆。

如果新会话能够完成任务，并通过所有检查，就说明这套流程已经从“某一次聊天里表现不错”，升级为“项目本身具备可调用能力”。

这也是判断一个 Agent 是否接近生产可用的重要标准。
