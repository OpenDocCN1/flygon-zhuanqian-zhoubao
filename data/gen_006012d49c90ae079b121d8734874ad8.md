这是我之前发的精华，里面有些做法现在看已经有点局限，这次一并更新。

先说硬件。做 iOS 必须有 Mac。我之前用的是一台 2018 年买的 Mac Pro，i5、8G 内存、128G 硬盘，Xcode 最高只能到 15，开发体验极差，尤其是改 Bug 时代码一大风扇狂转烫手。春节国补期间我换了台 Mac mini M4、24G、1T。

**一、设备是效率分水岭**

换机之后开发速度直接翻倍，最关键的是 Xocde 16。新版解决了之前 Cursor 新建文件不会自动同步到 Xcode 的问题，老版本必须右键手动 Add Files to 项目。硬件允许的话，iOS 开发一定要升到最新 Xcode，能避掉一堆坑。

**二、复杂应用的核心开发思路**

App 功能一多，Bug 数量会爆炸。我说复杂不是指核心算法复杂，而是像加个分享、加个收藏这种小功能，都可能让难度翻倍。

我的做法是“模块化推进”。先把一个功能做通，再开下一个。每完成一个小功能、修好一个 Bug，就新建一个 Composer，尽量不要在一个 Chat 里堆多个问题。这样 AI 不会被之前的上下文污染，解决效率高很多。

另外不建议盲目用 Agent 模式做傻瓜式开发。小工具用它还行，一旦要分模块开发，让 AI 代替你思考，就会陷入无尽的 Bug 循环。所以我基本不用 Agent。

**三、readme.md 和 cursorrules 是生命线**

这两个文件太重要了，每次新建 Composer 都要 @ 一下，让 Cursor 快速理解项目全貌。

我的流程是先写一份简易的产品需求文档，用 Chat 模式和 AI 讨论实现路径，完善 readme.md 后再用 Composer 写代码。

readme.md 必须把下面三点讲清：

（1）App 核心功能有哪些，提前规划好。最忌做到一半临时加功能，复杂度一高可能三四天都修不完 Bug。想加功能先让 AI 评估改动范围和难度，能评估再动，不能就别动，实在要加宁可重开项目。

（2）项目目录结构提前设计好。不设计的话前期没事，功能多了代码量上来了，Xcode 会频繁报错，最后 AI 会建议你重构全部文件，那种痛苦很难受。

（3）页面跳转关系用树状结构写清楚，点哪个按钮进哪个页面。否则后期会经常出现页面连不上的小毛病。

cursorrules 我是在花生大佬的版本上加了几条。代码变多后 AI 容易重复声明变量函数、漏导入依赖、甚至激进地改动整个页面的 UI 布局。加了这些限制后小问题少了很多，省时间。

**四、实现前后端打通，用网页后台管控 App 前端内容**

**五、版本回退的土办法**

Cursor 常出现改一个功能把整个 App 搞崩的情况。懂 Git 的可以用 Git，我没用，直接土办法：

（1）核心功能完成后整份文件复制一份存本地，标注版本号。崩了就删现网重建项目。缺点是文件夹多，一个 App 可能有十几个备份。

[PRE19]

（2）修 Bug 时，先 Save All 再 Reject All 撤销。也可以双击 Chat 记录里的第一条提示词，重新编辑就能回退到该对话前的代码状态。因为一个功能往往不是一次提示就能成，多次迭代也能用这个技巧回溯。

**六、高效修 Bug**

（1）Xcode 编译报错会标文件位置，Cursor 修 Bug 时要 @ 对应文件，尤其是代码行数超 200 行后，只复制错误信息不够用。

（2）编译成功后能装手机测试了，这时重点看右下角控制台。很多功能表面能跑，实际出错信息都在控制台。把报错和现象描述一起丢给 Cursor。

[PRE20]

（3）不要一次堆很多功能再测。每完成一个小功能就编译测试一次。后期上新小功能也容易引发大量报错，边做边测虽然繁琐，但能及时止损。

**七、别完全依赖 Cursor，要保持思考**

比如我做电子书 App 时，Cursor 的方案会导致每次打开 App 都重复向服务器拉图片 PDF，造成巨大压力。如果你不测试、不思考，Cursor 不会主动帮你优化。

开发时要站在技术角度想用户体验，测试不同状态下 App 的表现。比如会员订阅：未付费状态、已付费状态、过期状态，界面逻辑是否自洽。很多坑都是因为逻辑没想清。
