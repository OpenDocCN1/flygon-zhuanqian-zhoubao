把 AI 真正用起来，关键一步是让它能跟各种工具对话。

把 AI 和工具连通，是落地里最要紧的一环。

常用的联通方式无非这几种：MCP、API、CLI。MCP 可以简单理解为让 AI 挂载外部工具的通用桥梁。API 就是平台对外提供的程序调用口。CLI 则是能在命令行里直接跑的指令。

选哪种方式差别不大，重要的是连通之后，AI 能自主读数据、写结果，你就不用再当信息搬运工了。

### 用 Git 做多 Agent 编程底座

编程场景里，多 Agent 协作最稳的做法是建立在 Git 上。

Commit 等于一次代码存档。AI 改完一段代码并跑通测试，就打一个 Commit。之后有问题也能看到它到底动了哪几行，随时回滚到之前版本。

Branch 就是一条独立的开发分支。通常一个 Issue 对应一条 Branch。AI 在自己的分支上工作，不会污染主分支。

Worktree 则为不同分支创建不同本地目录。一个 Agent 在一个目录里搞视频导出，另一个 Agent 在另一个目录里修登录 bug。两边都能同时读文件、装依赖、跑测试，不会互相踩踏。

当然 Git 不能解决所有冲突。两个 Agent 同时改同一个模块，合并时照样会打架。所以多 Agent 协作的前提，还是先把任务拆干净。

### 把重复活全丢给 AI

工具打通后，并不是每一步都得人点一下。

一个完整闭环可以是这样：

先和 AI 聊需求，让它整理成 Issue。确认后，AI 自行读取 Issue 和 Figma 效果稿，建 Branch、建 Worktree，然后改代码、跑测试、打 Commit，再提 PR/MR。

开发中，它能把进展写回 Issue。上线后，若 Sentry 报警，AI 可读日志、定位代码并提交修复。PostHog 的用户行为数据，也能成为下一次迭代的依据。

人在流程里主要做三件事：定目标、定方案、做验收。建任务、更新状态、管分支、跑测试、整理日志这些重复活，尽量交给 AI。

国内也有同类替代。Linear 可以换成 PingCode、TAPD、禅道；Figma 可以换成即时设计、MasterGo；代码托管可以用 Gitee、CODING；错误监控可用 Fundebug；用户分析可用神策、GrowingIO。

工具名字会换，功能本质一样：保存项目事实，让人和 AI 都能读到。

### 流程可以简化

自己做项目时，我不会照搬团队的完整规范。

需求往往直接写进 GitHub Issue，或放在项目任务文档里。一个任务一条 Branch，只有真需要多个 Agent 并行才开多个 Worktree。

页面简单时，我不专门维护 Figma，直接用参考图加文字说明。产品未上线也不急着接 Sentry、PostHog，先把功能跑通再说。

流程简化了，保留三件事的记录：要做什么、代码改了什么、是否验收通过。

其他能自动化的环节，整理任务、建分支、改代码、跑测试、提交 Commit，我都让 AI 完成。

工具连通后，AI 会持续读取 Issue、设计稿、代码和日志，Token 自然会涨。

但这些 Token 花在了真实推进上，而不是你切回窗口后把背景从头讲一遍。

## 六、案例一：销售报告脚本

前面讲了本地项目、方案调研、上下文沉淀、分阶段开发。这里用一个销售成本报告脚本把方法串起来。

需求其实不复杂。

供货商或采购平台能导出采购数据，通常是 Excel/CSV，包含商品名、编号、规格、采购成本。

独立站保存的是销售订单，用的是另一套 SKU。供货侧编号和销售 SKU 无法直接对应，需要先按商品名、颜色、尺寸等属性建立映射，再把成本和销售数据拼起来。

手工处理就要在多张表里反复查找复制，数据一多很容易错。

### 1. 从对话进入本地项目

这类任务不适合只在聊天窗口里做。

采购数据、销售数据、生成的报告都在本地。把脚本放进本地项目，AI 才能直接读样本文件、改代码、跑脚本、检查输出的 Excel。

以后换新销售数据，不用重写逻辑，把文件扔进指定目录运行即可。

注：不是每个工具都需要 Web 页面或 GUI。轻量脚本在本地处理数据，反而更高效。

[PRE1]

### 2. 先调研，再定方案

写脚本前，先让 AI 理解两边的数据。

独立站 SKU 很清晰，供货商编号只在各自平台有效，和销售 SKU 不是一回事。

所以第一步不是算成本，而是建商品映射关系。

AI 先读两边商品数据，梳理名称和属性，生成可能的匹配。能确定的直接关联，名称相近、属性缺失或有多选的单独列出来人工确认。

确认后保存成映射表。脚本据此找到销售 SKU，再把采购成本合并到销售数据。

按报告所需关系把处理逻辑固化成代码。之后字段不变就不需要 AI 再介入执行，手动跑也一样。

### 3. 分阶段开发和验证

可以分成四步走。

第一步，读取各平台数据，统一商品名、颜色、尺寸等属性。
第二步，生成供货商品与销售 SKU 的映射表，不确定的单独输出人工确认。
第三步，按映射表把采购成本关联到销售订单。
最后汇总销量、销售额、采购成本，生成 Excel 报告。

每完成一步都用真实商品核对。先确认关系，再检查成本和销售。匹配错了，后面全错。

### 4. 真实业务驱动迭代

第一版跑通只说明流程通了。

接入新供货商，格式字段可能变化；新商品要补充映射；同一 SKU 多次采购，取最近成本还是平均成本，也要按业务确认。

报告还可能加入退款、广告费、物流费。

每遇一种新情况，AI 都要重新读样本数据和项目规则，改脚本，再用真实数据验证。

Token 就花在分析表格、整理映射、改代码、排查异常、重新生成报告上。

这个本地脚本虽小，但业务数据和统计口径一直在变。AI 要跟着变，Token 消耗自然增加。

## 七、Token 消耗的第二个门槛：业务需求变多

前面讲的是让 AI 把项目做下去。

流程跑通后，还得有真实业务。否则做个 Demo 改几轮页面就结束了。

以自动化剪辑为例。

直播团队一场两小时直播后，要剪出十几条竖屏短视频。

需要自动拼接、加字幕、配 BGM，按固定尺寸导出。

[PRE3]

听起来是几个功能，实操会遇到各种坑：

视频没声音、编码不兼容、字幕时间对不上、素材路径带中文。

每来一种新素材，AI 就要重新读代码、看 FFmpeg 日志、改逻辑、跑测试。

Token 就耗在这类具体问题上。

再看跨境电商。

卖家同时用 Shopify、Amazon、TikTok Shop，仓库供应商又是两套系统。

要做后台同步订单、商品、库存、售后。

麻烦在各平台接口字段不统一。同一商品 SKU 各不相同。取消订单、部分退款、库存锁定规则也不同。

AI 要读多套接口文档，写适配代码，看返回数据，处理限流、授权失效、字段缺失。接入新平台往往要加一套适配。

财务报表也一样。

老板要日看销售额、广告费、物流费、退款、实际利润。数据来自 Shopify、Stripe、PayPal、Meta 广告、物流商。

AI 先理清口径，再写脚本拉取清洗汇总。只要金额对不上，就要沿着订单、支付、退款往回查。

这些项目耗 Token，不是因为代码难，而是业务细节和例外太多。

AI 不断读取文档、代码、测试数据、错误日志，再下一轮修改。

真实业务上线后不会结束，新需求、新数据、新问题会持续出现，AI 也要持续读改验。

Token 的第二次跃迁，在于老项目的迭代维护和新项目的开发。

## 八、Token 消耗的第三个门槛：业务自动交付

到这一步，用法又变了。

前面是我用 AI。现在是业务系统通过 API 调用 AI。

API 就是程序调用模型的入口。

用户发起请求，系统自动整理相关数据发给 AI，再把结果写回业务流程。整个过程后台完成，不需要人打开对话框。

现在很多所谓的 AI 应用，只是网页里放了个聊天框。用户还得自己组织问题、补充资料，再把答案复制到别处。

在我看来这只是换了个入口，还谈不上真正的业务自动化。

判断一个 AI 功能是否真正接入业务，看结果能否直接推动下一步：更新任务状态、生成待确认方案、调用已有系统继续处理。

调一次模型 API 不难，难的是上下文。

AI 不知道客户是谁、订单在哪、公司业务规则是什么。这些信息必须由系统在调用时主动提供。

如果 AI 需要查订单，后端就给它查询工具。AI 发请求，程序查库，回结果，AI 再判断，直到任务完成。

我不会把一切都丢给模型。

金额计算、库存扣减、权限校验这类有明确规则的，还是程序来做。AI 更适合理解表达、判断类型、整理信息、生成内容。

涉及退款、付款、删除数据、对外发布，我会保留程序校验和人工确认。业务自动化的目标不是让 AI 乱操作，而是减少人来回复制信息、反复判断的步骤。

一次业务处理往往要调用多次模型，每次都带上系统规则、业务数据、历史记录和工具返回。

一个人用 AI，一天能发多少任务有限。接入业务后，每个用户请求、每次数据变化都可能自动触发模型。Token 消耗开始由业务量决定。

我甚至觉得，未来所有 AI 产品，表面卖功能，实质卖的是业务封装后的 Token。

这就是第三次跃迁：以前是我调 AI，现在是业务系统在调 AI。

## 九、案例二：小程序 GMV 12K+ 微信小店+知识库自动交付

看一个最近上线的案例，AI 服务成为业务核心。数据是上线后真实的 Token 消耗，用来生成分析报告。

这是一个通过微信小店卖的知识服务。用户付款后填问卷，系统结合问卷和知识库生成个性化报告，以 PDF 交付。

流程：微信小店下单 → 自动发货 → 小程序填问卷 → 飞书创建任务 → Hermes 调用国产大模型 → 生成报告 → 自动推送用户

用户付款后系统自动发货。

[PRE5][PRE6]

交付的不是固定资料，而是小程序入口。用户从订单进入小程序，系统校验订单有效后才开放问卷。

问卷提交后自动创建报告任务。用户不用加客服，也不用发订单截图。

技术栈：微信小程序、微信云开发、飞书、Hermes、国产大模型。

小程序负责交互。云开发处理订单校验、问卷数据、报告文件、消息通知。

飞书多维表格管理任务。运营可看到等待生成、已完成的报告，也能人工补信息、处理异常。

本地电脑用 CLI 跑 Hermes Agent，定时从飞书读任务。拿到问卷后先从知识库检索，再调用大模型生成结构化报告。

报告完成后检查内容和格式，生成 PDF 上传云端，再通过微信消息推送入口。用户点开就能在小程序查看或下载。

从下单到通知，全程无需运营手动传文件。

[PRE7]

这套系统里，AI 负责理解用户、匹配知识库、撰写报告。订单、身份、任务状态、PDF 排版、消息通知由程序处理。

模型层可替换。后续调效果或成本，可接入其他国产模型，小程序和交付流程不用重做。

上线前还有合规工作。小程序要备案，隐私指引要按实际收集信息配置。姓名、联系方式、业务数据哪些保存、哪些进模型，要提前定。

AI 参与生成报告，页面和 PDF 也要保留说明。技术跑通只是第一步，备案、隐私、完整交付流程要一起做。

该虚拟报告商品已卖出 600 多份，系统已稳定生成 500 多份报告，链路在真实业务中跑通。

每新增一笔有效订单，系统就会自动读问卷、检索知识库、生成报告。

Token 消耗不再看我一天发起多少任务，而是跟着业务量走。

前面讲的本地项目、方案调研、上下文沉淀、业务自动交付，在这个小程序里都有体现。

从对话进入本地项目

小程序代码、云函数、配置、日志都保存在项目目录。

AI 进入本地项目后可直接读代码、改云函数、跑测试、按日志排查。换对话或模型，只要重新读目录就能继续。

## 先调研，再确认方案

开发前要先梳理完整用户路径：小店下单、自动发货、进小程序、校验订单、填问卷、生成报告、微信消息通知。

下单自动推小程序入口；生成报告推微信服务消息；小程序推送部分信息到飞书；电脑 Hermes 拉取飞书数据处理后再写回飞书；小程序拉取飞书报表记录。这些卡点都要提前做技术验证。任一环节不通就得调整方案。

技术验证时，若平台较大，如微信开放平台、小程序平台，让 AI 严格按官方文档设计开发，能少走很多弯路。

[PRE8]

小程序支持云开发、云托管、自建服务器。

自建服务器需备案和域名，时间长，不考虑。

云开发和云托管可走小程序 ICP 备案，审核快。还能把小程序和小店通过云开发绑定，用同一套用户身份验证，开发量更少、稳定性更好。

所以部署方案采用 小程序 + 云开发 + Agent 主机。

## 把项目上下文保存下来

项目涉及多系统，靠聊天记录无法长期维护。

订单如何校验、问卷字段、任务状态、报告结构，都要写进项目文档。换窗口或换模型时，AI 不用重新问一遍业务流程。

## 分阶段开发和验证

没必要一次跑通整条链路。

先完成小店订单和小程序身份校验，再处理问卷提交与任务创建。流程稳定后接入知识库和大模型，最后完成 PDF 生成和微信消息推送。

每一段都用真实数据验证，出问题也能快速定位是订单、问卷、报告生成还是消息通知的问题。

所有流程验证完成后可小范围上线，走真实一单测试。再逐步放量，遇到问题也易处理，不伤用户信任。

系统稳定后全量发布，开始大规模推广。

当用户量级上来，做直播带货等营销场景时，还要考虑爆单问题。

## 打通各个工具

系统不只有小程序。

微信云开发存订单、问卷、报告文件；飞书管任务；Hermes Agent 读任务、检索知识库、调用模型。

打通后任务信息可在系统间流转，人不用反复复制问卷、下载报告再手动发送。

## 从真实业务走向自动交付

系统开始收真实订单后，还要应对问卷未填完、报告生成失败、任务需重试、运营处理异常等需求。

这些不是开发前能全部想全的。用户越多情况越多，项目会持续调整。

链路稳定后，每一笔有效订单都会自动触发问卷、知识库检索、模型生成、PDF 制作、消息通知。

## 十、未来

Token 榜单可关注，无需焦虑。

每个人工作和业务不同，消耗本来就没有标准。

刚开始用 AI，多问多试，先摸清能做什么不能做什么，再定目标。

接着把 AI 嵌入日常工作和真实项目，帮自己处理更多事。

有了合适业务，再做成可自动交付的产品，或帮别人做 AI 化改造。

Token 排名只是结果。更值得看的是，这些 Token 有没有帮你省时间、做出产品、带来真实收入。
