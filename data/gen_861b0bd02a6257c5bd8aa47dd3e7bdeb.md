最近试着用 Cursor 做了一个 YouTube 视频下载小工具，全程几乎没写代码，主要就是和 AI 对话、点 Apply/Accept。这篇把过程完整记录下来，给想用 AI 做点东西的朋友一个参考。

第4步结束后，首页已经能正常打开，页面效果先看图：[PRE0] [PRE1]。测试结论：功能实现完整，常规测试正常。整体算下来，从动手实现到收尾，大约 30 分钟。

第5步做视频解析功能。首页样式没问题后，我告诉 AI：“index.html 和页面样式都正常，咱们继续下一步吧。”[PRE2]。按照提示，先创建一个 JavaScript 文件处理前端交互。这里有个小细节：操作时 Apply 有时会出现两个选项，如果项目里已经有同名空文件，直接选 Apply to current file；如果没有，就选 create a new file。AI 给出的测试流程是：粘贴 YouTube 链接、点击解析按钮、等待页面展示视频信息[PRE3]。可实际输入 URL 后，点解析毫无反应，过了好一会儿才弹出报错[PRE4]。把情况发给 AI，它让我直接运行 `from app import app; print(app.url_map)` 来检查路由[PRE5]，结果没有任何输出[PRE6]。继续追问才发现，系统里根本没装 `flask-cors`，`pip list | grep flask-cors` 是空的，于是重新 `pip install flask-cors`。再按终端逐行执行：

python3
from flask import Flask
from flask_cors import CORS
print("导入成功")
from app import app
print(app.url_map)

这次能看到路由表了，里面有 index 和 parse_video，说明缺少的 /parse 路由已经正常注册[PRE7] [PRE8] [PRE9]。重新回到前端页面，把 URL 粘进去再点解析，结果又冒出新的错误[PRE10] [PRE11] [PRE12]。继续让 AI 修，终于成功拿到解析结果。功能是通了，但页面样式比较粗陋，就让 AI 根据描述优化了一版[PRE13] [PRE14] [PRE15]。这个功能从头到尾，加上测试和排错，大概用了 1 到 1.5 小时。

第6步实现下载功能。这次操作的流程变得很机械：把 AI 建议的代码 Apply、Accept，重启服务，再测试[PRE16]。在页面输入 URL 解析视频后，点最下方的“下载视频”按钮，看看能不能把文件存到本地。第一次测试就翻车了[PRE17]，AI 给代码加上了 User-Agent 头、禁用了证书检查、开启了详细输出，还补了一些下载选项。再次执行，仍然下载失败，报错是 `[youtube] ... Failed to extract any player response`，并提示到 GitHub 上报 issue[PRE18] [PRE19]。继续把问题交给 AI[PRE20]，它这次让我安装 ffmpeg 再试[PRE21]。装上之后，下载终于成功[PRE22]，服务端日志也显示进度 100%、合并到本地文件[PRE23]。我又拿了一条 39 分钟的 YouTube 视频做测试，文件大小 346MB，下载了差不多十几分钟[PRE24] [PRE25]。结论是：基础下载功能已经 OK，测试通过。如果觉得速度慢，可以让 AI 继续给优化建议，照例应用代码再反复测试；不用死磕某个环节，等熟悉了再回头调优也不迟[PRE26]。后面的几个小问题，我都是先用同样的流程处理：让 AI 改代码，应用后再测试，有问题继续丢回去。优化后同样 346MB 的文件只要 4 分钟就下完了，速度提升非常明显[PRE27] [PRE28]。这个功能总耗时约 1 小时。

第7步做下载进度条。核心下载功能完成后，这一步就属于体验优化，非必需。为了让用户点击下载后能看到实时进度，我给 AI 的指令是“先做下载进度实时显示”，它很快给出修改方案[PRE29]。测试时特意用了一个 2.4M 的小视频，方便观察效果。实际运行时，进度条能正常展示，下载完成后整个进度区域自动隐藏[PRE30] [PRE31]。不过 AI 合并代码后也带来一个副作用：之前修好的“文件大小显示”又变回了“未知大小”。解决办法仍然是丢回给 AI，让它把修复后的完整代码合并好，直接整体替换，而不是零散修改。我的复述是：“下载进度条正常了，但解析视频信息里的文件大小字段又变成未知大小，之前修过，请帮我修复。”[PRE32] [PRE33]。另外还发现两个小问题：一是文件没有存到项目的 downloads 目录，反而到了桌面；二是下载的视频文件名一直没改，不方便查找。这两个我也统一丢给了 AI[PRE34] [PRE35]。应用修改后，文件回到 downloads 目录，文件名也按视频标题生成了，确实方便很多[PRE36] [PRE37]。测试结论：功能正常，总耗时不到 0.5 小时。

第8步实现视频质量选择。我继续对 AI 说，把需求文档里还没做的功能继续完成。它会先列出待实现列表，并建议先做优先级较高且简单的项。于是选择了视频质量选择功能[PRE38] [PRE39]。测试过程中也有一些小波折，都靠询问 AI 解决了。最终效果显示，清晰度可以选择，下载、进度条等功能也都没有受影响[PRE40] [PRE41]。结论：新功能实现正常，旧功能回归测试也正常。耗时不到 1 小时。

第9步是下载历史记录。说实话，这个功能不是核心，这个工具真正离不开的只有解析视频和下载视频，其余都是锦上添花。但这段记录也算给大家一个启发：不会写代码，光凭 Cursor 能不能把拍脑袋的想法落地？我没有去调研市面上同类工具是否都有历史记录，纯粹想验证一下。如果真能做出来，还挺提气的。所以尽管可做可不做，我还是决定试一把。

先做历史记录前端页面。AI 给出实现方案[PRE42]，在右侧窗口 Apply 再 Accept 即可。整个方案有三个步骤：先安装依赖[PRE43]，再修改 app.py 添加数据库支持[PRE44]，最后修改 templates/index.html 加入历史记录标签页[PRE45]。按这个流程操作后，前端页面正常显示[PRE46] [PRE47]。

接着实现“下载完成后写入一条记录”。我按 AI 的提示，请它提供 JS 和后端 API 代码[PRE48]。我先加了获取历史记录的 API，一通操作下来，下载视频反而失败了[PRE49]。还是老规矩，把问题丢给 AI，拿到方案后在右侧 Apply、Accept。这里啰嗦一句：Accept 之后一定要 Ctrl+S 保存文件，别漏掉[PRE50]。重启服务后又有新问题，继续问 AI[PRE51]，应用方案[PRE52]，这次下载成功，历史记录里也出现了数据[PRE53]。再换一个视频 URL 下载，历史列表依然能正确记录[PRE54] [PRE55]。

最后补上了“重新下载”功能：历史记录列表右侧有一个【下载】按钮，点击即可重新下载对应文件[PRE56]。

以上，就是我用 Cursor 实现 YouTube 视频下载工具的完整记录。核心思路其实很简单：说清楚需求，把报错原样给 AI，Apply/Accept 后不断验证。即使不会写代码，也可以一步步把想要的东西做出来。
