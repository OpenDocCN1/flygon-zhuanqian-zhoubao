## 38.3 路由配置进阶 —— 声明式路由地图的分层与类型化治理

### 为什么需要这个概念？

单页应用(SPA)随业务增长，路由数量爆炸，扁平配置难以维护、权限混乱、类型不安全。你需要一种结构化方式表达“页面嵌套”、“多视图复用”、“路由元信息携带业务属性(权限/标题/缓存)”。传统字符串路由跳转易出错，重构时无编译期保护，迫切需要 TypeScript 级别的类型安全。

> "详解 `children` 嵌套渲染机制、`components` 多视图复用、`meta` 携带权限/标题/缓存策略等配置模式。"
>
> ——《20230418_038.md》

### 核心定义

**嵌套路由** 通过 `children` 数组实现 UI 组合的层级映射，父路由渲染 `RouterView` 作为出口，子路由在其中渲染。这直接对应了“布局组件包裹内容区”的经典模式。

**命名视图** 允许单一路由配置 `components: { default: Foo, sidebar: Bar }` 对应模板中多个 `<router-view name="sidebar"/>`，实现同级多视图并行渲染。这解决了“侧边栏、主内容、底部广告”需独立更新的需求。

**路由元信息** 通过 `meta` 字段携带任意业务数据(如 `requiresAuth: true`, `roles: ['admin']`, `keepAlive: true`)，供导航守卫与布局组件消费。这是声明式配置的核心：将“业务属性”附着在“路由节点”上。

**类型化 RouteRecordRaw** 利用 TypeScript 模块扩展 `declare module 'vue-router' { interface RouteMeta { ... } }` 实现 `route.meta.xxx` 的智能提示与编译期检查。

### 关键性质

**路由匹配优先级**：静态路径 > 动态路径参数(`:id`) > 通配符(`*`)，子路由匹配前提是父路由已匹配。这决定了配置顺序的重要性。

**惰性加载边界**：`component: () => import('./View.vue')` 自动形成代码分割点，构建产物生成独立 JS Chunk。这是性能优化的起点。

**类型系统约束**：`RouteRecordRaw` 强制 `path`、`name`、`component` 三要素，`meta` 需配合模块扩展生效。

### 典型例子

**后台管理经典布局**：

```typescript
const routes: RouteRecordRaw[] = [
  {
    path: '/app',
    component: () => import('@/layouts/DefaultLayout.vue'),
    children: [
      { path: 'dashboard', meta: { title: '仪表盘' } },
      { 
        path: 'user/:id', 
        component: () => import('@/views/UserDetail.vue'), 
        meta: { requiresAuth: true } 
      }
    ]
  }
]
```

**多标签页复用**：

```typescript
{
  path: '/home',
  components: {
    default: HomeContent,
    header: HeaderNav,
    footer: AdsBanner
  }
}
```

配合模板：

```vue
<router-view />
<router-view name="header" />
<router-view name="footer" />
```

### 边界条件

- 嵌套路由过深(>4层)会导致 `RouterView` 嵌套过深、Props 透传困难、调试栈溢出风险。
- 命名视图与 `keep-alive` 结合时，`include` 需精确匹配组件 `name` 选项，否则缓存失效。
- 动态路由参数变化(如 `/user/1` -> `/user/2`) 组件实例默认复用，需通过 `beforeRouteUpdate` 或 `watch(() => route.params)` 响应。

    C --> D[路由元信息 meta]

## 38.4 导航守卫体系 —— 状态机视角下的路由切换控制流

### 为什么需要这个概念？

路由切换本质是有限状态机迁移，必须在“离开前”、“进入前”、“更新中”注入横切逻辑(鉴权、数据预取、埋点、确认离开)。缺乏统一控制流会导致：权限校验散落业务代码、重复请求、页面闪烁、脏数据残留。你需要标准化的、可组合的、支持异步阻塞的拦截机制。

> "梳理 `beforeEach` → `beforeRouteEnter` → `beforeRouteUpdate` → `beforeLeave` 完整生命周期，掌握 `next(false)`/`next('/login')` 控制流。"
>
> ——《20230418_038.md》

### 核心定义

**全局前置守卫** `router.beforeEach((to, from, next) => { ... })`：应用级横切关注点(登录态、全局 Loading)。

**全局解析守卫** `router.beforeResolve`：在 `beforeRouteEnter` 之后、导航确认前，适合数据预取、权限细粒度校验。

**全局后置钩子** `router.afterEach((to, from) => { ... })`：无 `next`，不可阻塞，用于埋点、标题更新、关闭 Loading。

**路由独享守卫** 路由配置 `beforeEnter: (to, from, next) => {}`：针对单一路由的准入控制。

**组件内守卫**：
- `beforeRouteEnter`：组件实例未创建，通过 `next(vm=>...)` 访问
- `beforeRouteUpdate`：复用组件时参数变化
- `beforeRouteLeave`：离开前确认/保存草稿

### 关键性质

**执行顺序确定性**：

```mermaid
sequenceDiagram
    participant G1 as 全局 beforeEach
    participant R1 as 路由独享 beforeEnter
    participant C1 as 组件 beforeRouteEnter
    participant G2 as 全局 beforeResolve
    participant C2 as 组件 beforeRouteUpdate/Leave
    participant G3 as 全局 afterEach
    
    G1->>R1: next()
    R1->>C1: next()
    C1->>G2: next()
    G2->>C2: next()
    C2->>G3: 导航确认
```

这个时序图展示了导航管线的严格串行执行顺序，任何一环调用 `next(false)` 或抛出错误都会中断后续流程。

**`next()` 控制流语义**：

| 调用形式 | 语义 | 典型场景 |
|---------|------|---------|
| `next()` | 放行，继续管线 | 默认通过 |
| `next(false)` | 中断导航，URL 重置为 `from` | 权限不足、表单脏数据取消离开 |
| `next('/path')` | 重定向到新路径 | 未登录跳转登录页、403 降级 |
| `next(error)` | 终止导航，传递错误给 `router.onError()` | 服务端校验失败、异常兜底 |

**异步阻塞机制**：导航守卫内部异步操作(如 `await api.checkPerm()`)会暂停导航管线，直到 `next()` 被调用。这保证了“数据准备就绪再渲染”的语义。

### 典型例子

**登录拦截**：

```typescript
router.beforeEach((to, from, next) => {
  if (to.meta.requiresAuth && !store.token) {
    next('/login?redirect=' + encodeURIComponent(to.fullPath))
  } else {
    next()
  }
})
```

**表单离开确认**：

```typescript
beforeRouteLeave((to, from, next) => {
  if (form.dirty) {
    next(confirm('未保存确定离开?'))
  } else {
    next()
  }
})
```

**面包屑/文档标题更新**：

```typescript
router.afterEach((to, from) => {
  document.title = to.meta.title || 'Default'
})
```

### 边界条件

- `beforeRouteEnter` 中无法访问 `this`，必须使用 `next(vm => { vm.xxx })` 回调获取实例。
- 守卫内抛出未捕获 Promise Rejection 会导致导航静默卡死，必须 `try/catch` 并 `next(false)` 或 `next(error)`。
- 重定向循环：A `next('/b')` -> B `next('/a')` 触发 `NavigationDuplicated` 或无限循环，需设置访问标记防重。
- `next()` 在同一守卫中多次调用仅首次生效，后续调用被忽略且控制台警告。

### 数据流图

```mermaid
flowchart TD
    A[导航触发] --> B{全局 beforeEach}
    B -- next() --> C{路由独享 beforeEnter}
    B -- next(false) --> D[中断/重置 URL]
    B -- next('/path') --> E[重定向]
    C -- next() --> F{组件 beforeRouteEnter}
    F -- next() --> G{全局 beforeResolve}
    G -- next() --> H{组件 beforeRouteUpdate/Leave}
    H -- next() --> I[导航确认]
    I --> J[全局 afterEach]
    J --> K[组件挂载/更新]
```

## 38.5 动态路由与权限模型 —— 运行时路由表的数据驱动构建

### 为什么需要这个概念？

静态路由表无法满足“按权限渲染菜单”、“不同角色看到不同页面”、“运行时从后端下发路由策略”的需求。前端硬编码路由导致：权限变更需重新发版、菜单与路由不同步、403/401 处理分散。你需要一种“后端返回路由树 -> 前端动态注册 -> 菜单联动 -> 刷新保持”的完整工程方案。

> "展示后端返回路由树 → `router.addRoute` 动态注册 → 递归生成侧边菜单 → 刷新保持状态的完整方案。"
>
> ——《20230418_038.md》

### 核心定义

**动态路由注册**：`router.addRoute(parentName, routeConfig)` 在运行时向路由器注入新路由记录，支持嵌套、懒加载、命名视图。

**权限模型映射**：后端返回 `[{ path: '/admin', meta: { roles: ['admin'] }, children: [...] }]`，前端递归筛选 `user.roles.some(r => route.meta.roles?.includes(r))`。

**菜单联动生成**：同一路由树数据源，经 `filterRoutes` 筛选后，同时驱动 `router.addRoute` 与 `SidebarMenu` 组件递归渲染。

**403/401 降级策略**：匹配不到路由 -> `router.addRoute({ path: '/:pathMatch(.*)*', redirect: '/404' })` 或导航守卫拦截跳转 `/403`。

**刷新保持状态**：利用 `localStorage`/`sessionStorage` 缓存后端路由树，应用初始化时 `store.commit('SET_ROUTES', cachedRoutes)` 同步注册，避免白屏等待接口。

### 关键性质

- `router.addRoute` 是幂等追加，同名路由会被覆盖(后注册生效)，适合热更新场景。
- `router.removeRoute(name)` 支持注销，配合登出清理动态权限路由。
- `router.hasRoute(name)` 可用于守卫中预判目标路由是否已注册，决定是否放行或等待注册完成。
- 动态路由注册是异步非阻塞的，导航触发时若路由未就绪，需在守卫中 `await waitUntilRoutesReady()`。

### 典型例子

**RBAC 后台管理流程**：

```typescript
// 1. 登录成功后获取路由树
const routes = await fetchUserRoutes()

// 2. 递归筛选权限
const accessibleRoutes = filterRoutes(routes, user.roles)

// 3. 动态注册到布局路由下
accessibleRoutes.forEach(route => {
  router.addRoute('layout', route)
})

// 4. 跳转重定向目标
router.push(redirectPath || '/dashboard')
```

**权限筛选算法**：

```typescript
function filterRoutes(routes: RouteRecordRaw[], userRoles: string[]): RouteRecordRaw[] {
  return routes
    .filter(route => {
      if (route.meta?.roles) {
        return userRoles.some(r => route.meta!.roles!.includes(r))
      }
      return true // 无 roles 限制则公开
    })
    .map(route => ({
      ...route,
      children: route.children ? filterRoutes(route.children, userRoles) : undefined
    }))
}
```

这个递归函数展示了如何实现“父节点无权限则子节点全不可见”的语义，同时保持树结构完整性用于菜单渲染。

### 边界条件

- 动态路由注册必须在 `router.isReady()` 之前或导航守卫内完成，否则首屏导航可能匹配失败落入 404。
- 菜单数据与路由数据耦合度高，后端接口变更易导致前端双端报错，建议定义共享 TS Interface 并通过 OpenAPI 生成。
- 懒加载动态路由：`component: () => import(/* webpackChunkName: "admin" */ `@/views/${route.component}`)` 需确保构建工具支持动态导入变量路径(或使用 Vite `import.meta.glob`)。
- 循环引用路由树(父引用子、子引用父)会导致 JSON 序列化爆栈，传输层需扁平化或使用 `flatted` 库。

### 时序图

```mermaid
sequenceDiagram
    participant U as 用户登录
    participant A as 认证服务
    participant F as 前端路由器
    participant S as 本地存储
    
    U->>A: 登录请求
    A-->>U: 返回 token + 路由树
    U->>F: filterRoutes(routes, roles)
    U->>S: 缓存路由树
    loop 遍历路由
        F->>F: router.addRoute('layout', route)
    end
    F->>F: router.isReady()
    F-->>U: 跳转目标页
    
    Note over U,F: 刷新场景
    U->>S: 读取缓存路由树
    S-->>U: 路由树数据
    U->>F: 同步注册路由
    F-->>U: 直接渲染目标页(无白屏等待)
```

## 38.6 性能与体验优化 —— 懒加载、预加载与视觉连续性的工程权衡

### 为什么需要这个概念？

首屏加载所有路由 JS 导致白屏时间过长(FCP/LCP 恶化)，用户流失率上升。路由切换时现场下载 Chunk 造成“白屏等待 -> 渲染”体验断裂，尤其弱网环境。页面切换缺乏过渡动画，用户失去空间定向感，交互显得生硬。

> "对比 `import()` 与 `webpackChunkName`、利用 `router.prefetchRoutes()` 提前获取、配合 `<Transition>` 实现页面切换动效。"
>
> ——《20230418_038.md》

### 核心定义

**路由懒加载**：`component: () => import('./HeavyView.vue')` 利用动态导入语法，Vite/Rollup 自动代码分割生成独立 Chunk，按需加载。

**Chunk 命名策略**：`/* webpackChunkName: "chunk-name" */` 或 Vite `manualChunks` 配置，控制合并粒度，避免过度碎片化(HTTP/2 多路复用下 10-50KB/Chunk 为宜)。

**预加载策略**：`router.prefetchRoutes([routes])` 在浏览器空闲期(`requestIdleCallback`)预取高概率访问路由的 Chunk，存入浏览器缓存。

**滚动恢复**：`scrollBehavior(to, from, savedPosition) { if (savedPosition) return savedPosition; else return { top: 0 } }` 实现列表页返回保持滚动位置、详情页回顶部。

**过渡动画**：`<router-view v-slot="{ Component }"> <Transition name="fade" mode="out-in"><component :is="Component"/></Transition> </router-view>` 结合 CSS `fade-enter-active/leave-active` 实现淡入淡出/滑动。

### 关键性质

**懒加载与预加载互补**：懒加载减首屏包体，预加载隐延迟，二者结合实现“首屏快、二屏即时”。

**资源优先级差异**：`prefetch` 为低优先级 `rel=prefetch`，不阻塞关键资源；`preload` 为高优先级 `rel=modulepreload`，用于当前导航必需资源。

**滚动恢复机制**：依赖浏览器 History Scroll Restoration API，`history.scrollRestoration = 'manual'` 交由 Vue Router 接管。

**过渡动画模式**：`mode="out-in"` 保证旧组件离场完成再进入新组件，避免布局抖动，但增加切换感知延迟(约 150-300ms)。

### 典型例子

**电商大促页**：首屏只加载 `Home`，`ProductDetail`、`Checkout` 标记预加载，用户点击商品瞬间打开。

**后台管理**：左侧菜单悬停 200ms 触发目标路由预加载，点击时 Chunk 已就绪。

**长列表保持**：用户在 `/list?page=3` 点进详情 `/detail/101`，返回时自动恢复 `scrollY` 位置。

### 边界条件

- 过度预加载消耗带宽/内存，移动端弱网需根据 `navigator.connection.effectiveType` 动态开关。
- `Transition` 包裹 `router-view` 时，若子路由也有 `Transition`，嵌套过渡需用 `key` 强制重置或使用 `<TransitionGroup>`。
- 滚动恢复在虚拟列表/无限滚动场景失效，需手动记录 `scrollTop` 并配合 `data-index` 定位恢复。
- 懒加载 Chunk 加载失败(网络/版本不匹配)需全局 `router.onError` 捕获并提示“版本已更新，请刷新”。

### 设计中的取舍

**为什么不用全量加载所有路由？** 全量加载虽无切换延迟，但首屏 JS 体积随路由数线性增长，FCP/LCP 指标恶化，首屏白屏时间不可控。懒加载将“加载成本”分摊到按需访问时刻，符合“用户只为所用买单”原则。

**预加载与懒加载的 trade-off 是什么？** 预加载消耗带宽换取“零延迟切换”，懒加载节省带宽接受“首次访问延迟”。工程决策依据：高频核心路由(如详情页、结算页)预加载；低频长尾路由(如设置、帮助)懒加载；移动端弱网关闭预加载。

**过渡动画的 `out-in` vs `in-out` 怎么选？** `out-in` 保证布局稳定(旧组件离开后新组件进入)，适合结构变化大的页面切换；`in-out` 并行过渡更快但可能导致布局抖动，适合结构相似的标签页切换。默认推荐 `out-in` 以稳为主。

## 38.7 微前端子应用路由隔离 —— 基座与子应用的路由共治契约

### 为什么需要这个概念？

微前端架构下，主应用与多子应用共享同一浏览器 History 栈，路由冲突、基础路径不匹配、守卫协作缺失会导致白屏、404、状态污染。子应用独立开发、独立部署，必须在不知晓主应用具体路由结构的前提下正确运行。你需要一套标准化的路由隔离、分发、同步协议。

> "结合 qiankun/微前端场景，解决子应用 history 模式基础路径、基座与子应用路由同步、跨应用导航守卫协作问题。"
>
> ——《20230418_038.md》

### 核心定义

**基础路径隔离**：子应用入口设置 `base: '/sub-app1/'`，内部路由均以此为前缀，主应用通过 `qiankun` `registerMicroApps({ activeRule: '/sub-app1' })` 完成前缀匹配与剥离。

**路由模式统一**：主子应用均采用 `history` 模式，子应用 `router.push('/detail')` 实际触发 `window.history.pushState(null, '', '/sub-app1/detail')`，由基座代理。

**基座路由分发**：主应用监听 `popstate`/`hashchange`，根据 `activeRule` 判断激活哪个子应用，调用 `loadMicroApp`/`unmount` 生命周期。

**子应用通信与守卫协作**：主应用全局守卫 `beforeEach` 先行鉴权 -> 放行至子应用 -> 子应用内部守卫二次校验 -> 组件渲染；跨应用跳转 `router.push('/sub-app2/detail')` 触发主应用分发。

**共享依赖与路由实例**：`VueRouter` 实例不共享，但 `Vue`/`VueRouter`/`Pinia` 等库实例通过 `qiankun` `shared` 配置或 `importmap` 去重，避免多实例冲突。

### 关键性质

**路由前缀剥离透明**：子应用代码感知不到 `base` 前缀，编写路由如同独立 SPA。

**沙箱隔离副作用**：`snapshot`/`proxy` 沙箱确保子应用卸载时 `window.history` 监听器、定时器、全局变量被清理，不污染主应用。

**预加载策略**：主应用可在用户点击菜单前 `prefetch` 子应用 HTML/JS/CSS，进入时仅执行 `mount`，实现毫秒级切换。

**嵌套微前端**：子应用内再嵌套微前端(三级)，需层层透传 `base` 与 `publicPath`，复杂度指数级上升，非必要勿用。

### 典型例子

**企业级 ERP**：主应用 `Portal`(登录/首页/权限) + 子应用 `Finance`(`/finance`)、`HR`(`/hr`)、`CRM`(`/crm`)，各自独立 Git 仓库、CI/CD、技术栈(Vue2/3/React)。

**旧系统渐进式迁移**：遗留 jQuery 页面作为子应用挂载 `/legacy/*`，新业务用 Vue 3 微应用，共存过渡期 1-2 年。

### 边界条件

- 子应用内部使用 `router.push('/login')` 会相对 `base` 解析，若需跳转主应用登录页，需 `window.top.location.href = '/login'` 或约定全局事件总线。
- 刷新子应用页面：浏览器直接请求 `/sub-app1/detail`，Nginx 需配置 `try_files $uri $uri/ /sub-app1/index.html` 回退到子应用入口，而非主应用。
- 共享路由状态(如面包屑、Tab 标签)需主应用维护全局 Store，子应用通过 `props`/`eventBus` 同步，避免各自为政。
- `vue-router` 版本不一致(主应用 v4、子应用 v3)会导致 API 不兼容，强制统一主版本或使用兼容层适配。

## 38.8 多源对照

本章所有技术内容均基于单一素材源 `20230418_038.md` 构建。由于未提供其他来源文档，此处不设立“共识与分歧”对照。若引入 Vue Router 官方文档、qiankun 官方文档或社区最佳实践文章，可补充以下对照维度：

### 潜在共识点（需补充文献验证）

- 嵌套路由是表达布局嵌套的标准模式
- 导航守卫执行顺序为框架内置确定性行为
- 动态路由注册是权限驱动菜单的标准实现路径
- 懒加载 + 预加载是首屏性能优化的黄金组合

### 潜在分歧点（需补充文献验证）

- **TypeScript 类型扩展位置**：官方文档推荐在 `vue-router.d.ts` 全局扩展，部分团队偏好在路由定义文件局部 `declare module`
- **预加载触发时机**：Vue Router 官方 `prefetchRoutes` vs 社区自定义 `IntersectionObserver` + 菜单悬停预加载
- **微前端路由模式选择**：`history` 模式需 Nginx 配合 vs `hash` 模式零配置但 URL 不美观
- **动态路由注册时机**：登录后同步注册 vs 路由守卫中异步等待注册完成
