# 连续两场 **Codex** 线下局复盘：从真需求到 **AI** 产品 **demo**，我们现场验证了什么？

连续两场Codex线下实操局走下来，我最深的感触不是“AI真猛”，而是——**它把“做出来”这件事变得太快了，快到你甚至来不及掩盖“你到底要做什么”这道题的空白。**

几分钟就能捣鼓出一个能跑的demo，但真正难住的，往往是站在代码之外的那一刻：这个产品，到底为谁做？

两场活动，一场是6月19日的同城聚会，原定4小时硬是拖到了5小时；第二场原本没打算办，可第一场报名截止后还有十几位朋友在排队，临时又加开一场。

这么紧凑的节奏里，我想认真复盘的不只是活动本身，而是我验证过的几个判断，以及如果你想照着办一场AI实操局，能直接拿走的方法。

## 别急着打开Codex，先回答“给谁用”

很多人一听到AI编程，第一反应就是装环境、写提示词、让Codex吭哧吭哧写代码。这些当然得会，但这次的实践主题，官方定为：“真需求不能被发明，只能被发现。”

这个主题我特别认。它源于刘小排老师的一次直播分享，我正好听过，也在深海圈跟着学过，一直很有感觉。

现在AI工具越来越强，不会写代码的人也能通过Codex捏出一个能跑起来的demo，门槛确实被拉低了。但另一个问题也跟着冒了出来：我们太容易把自己的“灵光一现”当成别人的“真实痛点”。

一个点子，脑内兴奋，做出来也快，可它到底有没有真实用户？有没有具体使用场景？用户是否正忍受着某个麻烦？为了摆脱这个麻烦，他们已经付出了什么？这些问题但凡有一个答不上来，那大概率就是伪需求。

在活动现场，我给大家发了一个“四问填空法”，所有人都照着填：

1. **第一批用户是谁？**
   别写“所有人”。学生、视频号创作者、病人家属、减肥人群、自媒体博主，这群人的需求完全是两回事。用户写得越具体，产品才越能落地。

2. **需求发生在什么具体场景？**
   别说“提升效率”这种空话。要问：他在什么时刻最烦躁？当时正拿着手机干什么？哪一步把他卡住了？
   不是“学生要提分”，而是“学生期末考试前三天，需要快速背完一整页高频考点”。
   不是“家属要关心爸妈身体”，而是“子女在外地，不知道独居老人今天有没有按时吃药”。

3. **用户已经付出了什么成本？**
   不一定是钱。时间、注意力、转发的动作、反复用笨办法硬扛，都算。一个人如果已经在为这个问题花钱花时间，说明这问题不是你凭空想象出来的。

4. **先解决哪个最小但最痛的问题？**
   别一上来就画大系统，挑最小的一步下手。我的公式是：我的产品服务哪类人？他们在什么场景下、遇到什么具体麻烦？为此付了多少成本？我的最小版本先解决其中哪个环节？

这四个空，填不出来，就先别急着重启电脑。

## 第一场：4个小组，4个demo，全是从想法到落地

6月19日那场，现场分了4组，流程是：需求分享 → 分组讨论 → 制作MVP → 产品答辩 → 现场投票。最后不出意外，每组都完成了自己的产品。

**第一组：考前速记工具**
解决学生考前突击记忆的问题。我自己不是目标用户，一开始感受不强，但现场有伙伴非常笃定这是刚需。这件事也提醒我：判断需求，不能只看“我是否用得上”，更得看目标人群的真实频次。

**第二组：视频号爆款拆解工具**
输入一条视频号链接，系统自动抓取数据、口播稿、互动情况，然后拆解它凭什么爆，最后归整到飞书多维表格。对正处在起号期、天天拆同行找选题的内容创作者来说，方向很提效。

**第三组：八杯水提醒工具**
喝水提醒的App已经不少了，这个项目最关键的考验是：用户凭什么放着现成的不香，要换成你的？不是有产品就不能做，而是必须找到自己的差异化场景。

**第四组：吃药提醒工具（当天第一名）**
它解决的痛点非常具体：子女、家属、护工，如何确认并提醒病人按时吃药。重点不在“提醒”，而在“家属能否确认对方真的吃了”。场景、关系、痛感都极其清晰。

现场最微妙的一幕发生在讨论环节。各组聊得太投入，我瞄了一眼时间，差不多半小时过去了，忍不住打断：“不能再讨论了，现在就动手。”

因为讨论会给人“已经想明白”的错觉。但真实的问题，只有动手做出来之后才会爆炸式冒出来：这个页面按钮放哪？用户第一步点哪里？输入什么字段？输出结果有价值吗？陌生人看得懂吗？

这些问题光靠脑补，补不出来。

**AI产品实操局真正的价值，不是让大家讨论出一份完美方案，而是逼你在限定时间里做出来一个最小呈现。先做出来，再被真实反馈打脸。**

## 现场突发需求：先给Codex扫个盲

在活动准备阶段，我默认大家是有点基础的。真到了现场，有位伙伴举手说：“我是昨天刚装好Codex，还不太会用。”还有人说，希望之后能有一场科普局，讲讲怎么做Skill、怎么调用Skill、怎么用Codex。

这个声音特别有价值。它说明“拿Codex做产品”的前面，还站着一个更基础的需求：**很多人需要先搞清楚Codex到底能替他干什么。**

于是我当下打开电脑投屏，现场演示了几个我自己的真实用法：

1. 把Codex当技术同事、运维同事，让它装环境、排故障。
2. 开新项目时，先让它读一遍项目说明文档，再按真实场景给方案。
3. 把某播主大量视频内容蒸馏成一个可调用的skill。
4. 说一条语音，自动流转生成👸号文字、朋友圈、口播脚本和📕笔记。

这本身就是当天主题最好的活教材：需求不是坐在屋里拍脑袋想出来的，而是现场碰出来的。

## 顺手用Codex做了个投票系统

答辩环节快开始，我突然意识到：现场要投票，但投票工具还没着落。我直接打开Codex，现场搓了一个投票系统。

投完之后有人问我：“这是你刚现场写的？”我说：“是。”

这东西不复杂，但它反而成了当天我最喜欢的一个演示。因为这不是提前彩排好的炫技道具，而是问题真实发生的当下，我们立刻动手，用Codex做出了一个能服务现场的最小工具。

这就是我理解的AI编程的底层价值：**它不打算把每个人变成程序员。它想让每个人在问题出现的那一刻，有本事把它快速变成可跑、可验证、可用的小工具。**

## 第二场：从“陌生局”到“需求复验”

6月21日加开的那场，于我而言意义很不一样。第一场结束后还有十几个人追着要报名，这件事本身就说明：这个主题不是一次性热闹，有人愿意花时间、有人愿意动手、还有人愿意把真实需求拿出来做demo。

需求能不能反复发生，才是验证它真伪的试金石。第二场，本质上就是一次需求复验。

第二场参与者里，我认识的人屈指可数。过去我组局，总有一两个熟人或微信聊得来的朋友垫底。但这次，一群陌生人破冰的速度让我刷新认知。复盘之后我发现：真让大家熟起来的，不是外向性格，而是**我们手里有一个共同任务——从真实需求出发，用Codex做出一个demo。**

不是围坐一团自我介绍，也不是礼貌寒暄。而是一起做产品时，人自然会进入具体问题：你想解决谁的问题？先做哪一小步？页面怎么设计？3小时能不能搞定？

人在共同解决一个具体问题时，关系会变得特别真实。**好的线下局，不一定靠熟人关系起动，一个清晰的共同任务，就是最高效的破冰方式。**

---

## 第二场的3个产品：全是从自己身上长出来的

第二场人少，分了3组：

**第一组：爱豆模拟器**
市面上有类似玩法，大家觉得有趣，想用Codex模拟一个出来玩玩。我体验了一把，说真的挺好玩的。它不一定能成为最强商业项目，但作为AI产品实操练习相当合适：交互明确、反馈即时。

**第二组：减肥情绪疗愈产品**
这位伙伴本身做减肥业务，自己也在减肥。他抓住的不是“减肥”这个大词，而是减重过程中更细节的那一环：当一个人控制饮食没忍住、体重卡住了、想放弃的时候，真正的需求不止是“再忍一忍”的知识，而是一种情绪上的安慰与陪伴。所以他做的是一个给减肥人群提供情绪疏解的轻应用。

**第三组：自媒体选题生成工具**
这位伙伴自己日常搞内容创作。做号的人都懂那种抓狂：最大的困难往往不是写不出来，而是今天压根不知道该写什么。于是他做了一个快速生成选题的工具，demo很快就跑了起来。

这三个方向看似南辕北辙，却有一个共同的底色：**它们的种子，都是参与者自己真实生活里长出来的。** 喜欢追星的做爱豆模拟，被体重困扰的做情绪疗愈，天天发愁选题的做选题工具。需求离自己越近，产品越不容易做飘。

## 连跑两场之后，我沉淀了5个判断

**1. AI削平的是开发门槛，不是需求判断门槛**

它能让你更快地做出来，但不会替你判断：谁需要？为什么需要？现在怎么解决的？愿意掏多少成本？先做哪一步？

工具越强，这道题越不能跳。

**2. 对非技术人来说，Codex最像“技术同事”**

别一上来就把它当成“程序员替身”。把它想象成一个新来的技术同事：你得把需求讲清楚、把材料给到位、把反馈说具体，然后一轮一轮往前推。这个过程不是许愿，是协作。

**3. 线下实操局，没有截止时间不行**

讨论如果没有钟表掐着，能无限延展。反倒是时间有限，才能逼大家动手抓首选最小的一步。MVP的意义不是炫技，而是提前排队暴露问题。

**4. 新手局和进阶局，最好分层跑**

第一场现场同时出现两种人：一种想拿产品跑实操，一种先要Codex扫盲。所以如果继续办，拆两层：
- 第一层：Codex小白入门局——解决安装、基础使用、Skill调用、文档协作；
- 第二层：真实需求到demo实操局——解决需求判断、MVP制作、答辩反馈。

**5. 一场好活动，不是把流程走完，而是让人带着东西走**

第一场拖到19:00大家还不想离场；第二场18:00准时结束，因为有人远道而来还得赶路。活动结束之后我认真翻了反馈，不少伙伴写得十分用心。

一场活动的体验不只由内容决定，节奏才是隐形的手。好的线下局不是主讲人念完PPT，而是每个到场的人，都感觉这趟没白来。

## 如果下次再办，我会做3个调整

**1. 报名阶段就分好基础组和进阶组**
报名表上加几道题：装过Codex吗？独立跑通过项目吗？知道Skill是什么吗？有明确的产品方向吗？这样现场不用浪费时间分层。

**2. 把“真需求四问卡”变成硬性门槛**
这次现场发了四问卡的打印版，但收场时发现大半还是空白的。下次我会规定：开发之前必须先把四空填完，填不出来就先别碰Codex。

**3. 结束时统一回收产品输出**
这次的产品链接和反馈没有系统沉淀。下次收齐：产品截图、演示链接、用户反馈、评分结果、迭代方向。这些不只是复盘素材，更是后续反复验证需求的关键证据。

## 如果你也想用Codex做产品，先回答这5个问题

别一上来就馋“大而全”。先从这几个问题起步：

1. 你自己最近反复遇到的麻烦是什么？
2. 你身边有没有超过3个人也说过同样的问题？
3. 他们现在都是怎么解决的？
4. 他们为这个问题花过钱、时间或注意力吗？
5. 你能不能先做一个只解决其中一步的小东西？

把这五个问题琢磨明白，再打开Codex。不要对它喊“帮我搞一个大项目”，而要尽可能说：“我想服务某某人群，他们在某某场景下遇到了某某具体问题。我现在只想先做这个最小版本，只做完这一步。请你帮我拆步骤。”

成功率高得多。
