# 日本 IT 行业的概况与机遇：从个人观察到行业洞察

最近和一位常驻日本的朋友聊起当地的IT行业，挺有感触。今天就结合他的观察，把日本IT圈的现状、槽点和隐藏机会一次性讲清楚。

如果你对日本的程序员生态、企业IT服务模式，或者想判断那边是否存在创业切口，这篇应该能给你一些参考。

先说大背景：日本IT业正试图挣脱过去那种层层转包的旧玩法，开始往自主研发转型，并且把敏捷开发（Scrum）当成一个重要抓手。

在日本IT圈里，公司大致可以分成两条路线：一条是做IT咨询与整体解决方案的，另一条是专心打磨自家产品的。前者里的代表有NTT DATA、野村综研这类巨头；后者则包括乐天、雅虎日本这种偏创业或大型创业体质的公司。

做咨询和解决方案的，处在开发链的上游，业内管它们叫“SIer”。下游主要是那些做实际编码、实现功能的公司，大多是中小企业。有意思的是，在不少从业者眼中，上游反而没那么招人待见，有人觉得上游学不到真技术，下游则是出了名的“黑心工厂”。

为什么会有这种印象？这得从日本IT的一个特殊背景说起。

把日本SIer和美国的IT工程师放到一起看，差异非常明显。美国大厂的工程师大多呆在非IT公司的内部技术部门；而在日本，工程师则集中在IT主业企业里。原因是，日本传统企业一旦招了IT人员，后续就算不打算继续投资IT项目，基本也没法轻易把人裁掉，劳动法的制约摆在那。于是，大企业们干脆成立独立的系统子公司，把工程师往里放。这类公司叫“用户系SIer”，比如伊藤忠科技解决方案、日铁解决方案、SCSK等，背后分别是伊藤忠商社、日本制铁和住友商社。这些“用户系SIer”规模通常挺大，也因此，日本IT工程师大部分都在做SIer相关的工作。

日本独有的分包结构，是理解整个行业问题的钥匙。

大SIer靠强劲的销售拿单，即使内部人手不够，也会继续签约，然后转手分包给“合作伙伴”。需求定义、系统设计、人力安排和项目管理都留给自己，实际开发和测试这些“下游”活则交给分包公司，也就是中型SIer、中小开发公司或者SES公司。如今各类编程培训遍地开花，想当程序员的人不缺，所以上游不怕接了单没人干，反正金字塔底层有大量新人顶着。

这种结构天然适合瀑布式开发——需求、基本设计、详细设计、编码、单元测试、系统测试，一步步往下推。但它的问题也很扎眼：

一、质量和交付容易翻车。真正写代码的是分包公司里的工程师，甲方根本摸不清末端人员的技术水平。甲方只能盯着大SIer追问进度，大SIer转头向分包商施压，分包商拉上一帮新手硬赶工期，代码质量可想而知。

二、知识沉淀为零。因为不是自己人在动手，开发经验根本留不到公司内部。

三、不懂系统的人容易被“宰”。企业一旦上了ERP之类的核心系统，后期想换超级麻烦，哪怕只是改个按钮，被收个几百万甚至上千万日元也不是什么稀奇事。

四、终端用户体验被甩到一边。分包模式下，直接客户是上游公司，大家只要对着上游做正确的事就行，谁管最终用户会不会用？所以直到现在，网上银行还可能出现“错误代码：001”这种给外行看了一脸懵的提示。

正因为这些积弊，日本的IT常给人“落后”的印象，本土很多工程师也普遍反感SIer。日本制造业等产业其实还藏着不少潜力，不少企业开始重视内部培训、自建IT团队、自己动手研发系统。但毕竟补课要时间，当下和SIer合作依然会是主流。

不过，摆脱分包结构也是必然趋势。以小体量AI创业公司为例，它们已经能独立开发出大型企业级系统，靠的关键就是采用敏捷开发——不是一大摊子事做完再交付，而是小步快跑、边做边确认、边发布。

现在SIer也正尝试向敏捷转型，但阻力不小。第一，传统甲方要改变参与方式，敏捷开发要求高频次沟通和确认，甲方没法继续当甩手掌柜；系统上线后，公司内部还得自己攒运营经验，否则又会退回老路。第二，工程师缺口很明显，敏捷小队需要多面手，每个成员的能力要求更高，只靠几个月编程培训班出来的新手很难扛起来。这反过来也意味着，真正有实力的IT工程师，在日本的价值会越来越高。

希望这篇梳理能帮你对日本IT行业有个更立体的认识，也祝你从中看到属于自己的机会。
