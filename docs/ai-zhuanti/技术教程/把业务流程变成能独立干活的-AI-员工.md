# 一、AI Agent 筑基

Agent：可独立完成工作的 AI 员工

### 1. 什么叫 Agent？

Agent 是被赋予目标、权限边界、工具与验收标准后，能够持续执行一类工作的执行主体。用户只说想要什么结果，它会自行理解需求、拆解路径、调用工具、处理异常并交付成果。

我现阶段大部分事务都交给 Codex 处理。

过去装软件，要自己查官网、找安装包、下载、配置并验证；现在只需说“帮我装这个软件”，它就能找到靠谱渠道、完成安装并自检可用性。

Codex 本身就是一个编程 Agent，也是通用 Agent。它擅长读写文件、写代码、执行命令、操盘项目。借助浏览器、CLI、MCP 与插件，还能完成检索、文档、数据整理、软件部署等海量工作，能力边界远超代码。

不同项目间环境相对隔离，新对话不会自动继承全部记忆。这反而方便我们做岗位化设计：一个项目文件夹对应一名专岗 AI 员工。在该文件夹里留下代码、设定和资料，明确身份、职责、流程与标准，Codex 进入后即按此设定执行。不同项目规则不同，Codex 就能扮演不同角色。

做 Agent 员工的本质，是为 Agent 设计清晰、可复用、可沉淀的工作设定。

### 2. AI 员工的设定长什么样？

不同业务类型，项目结构自然不同。目前并无一套放之四海而皆准的黄金目录。起步时不必追求复杂完整的架构。

多数成熟项目都是在真实运转中长出来的。先让 AI 参与干活，随着任务推进，文件夹里会自然出现原始素材、产出结果、脚本、校验器、规则库、知识库与临时文件。

待某条业务链路跑通后，再让 Codex 回溯整理，把已验证的操作步骤、业务规则、禁区与验收标准固化下来。

看到这里新手可能会焦虑：文件太多怎么归档？自动沉淀会不会乱？能否稳定复用？其实不必过度担心。第三部分会给出可直接使用的提示词，按框架逐步推进基本不会出错。最终会得到结构清晰、可反复复用的项目，沉淀的 Skill 等资产还能跨项目迁移。

整理后，零散在聊天记录与文件里的经验会变成项目目录、AGENTS.md、Skill、脚本、验证器、业务资料与输出模板，形成可长期复用的工作系统。

### 3. Agent 使用的关键点拨

理解原理后，一些反直觉的操作就合理了。

新对话为何要先让 Agent 读项目？因新对话无历史记忆。让它先读项目文件，相当于新员工入职培训，了解身份、职责、流程与标准。

为何一个项目最好只对应一个 Agent，并长期专岗？项目在运行中会持续沉淀代码、规则、素材与产出。若让同一项目处理互不相关的工作，会导致信息混杂、职责漂移与规则冲突。时间久了 Agent 会迷失定位。

保持项目干净，服务于一类明确工作，积累越深理解越稳。

为何不能仅依赖聊天记录保存规则？上下文有限，对话越长早期指令越易被压缩丢失。今天刚纠正的问题，下次对话可能重现。

正确做法是把已验证的经验及时固化：长期原则写入 AGENTS.md，完整流程写入 Skill，确定性动作交脚本，验收标准交验证器。这样换对话后，Agent 重新读取项目即可按同一套标准工作。

稳定产出 AI 员工的核心，不是一条完美提示词，而是“真实执行→人工纠偏→规则沉淀→重新验证”的闭环。把一次成功转化为长期能力，保持边界清晰、流程可复用，让 Agent 换对话也能重新上岗——这正是本次分享想讲清的事。

# Skill：AI 员工的作业手册

理解 Agent 后，下一步是理解 Skill。

### 1. Skill 是什么？

如果 Agent 是员工，Skill 就是它执行某类工作的标准作业手册。它会说明何时启用、前置检查、执行顺序、可脚本化环节、需人工判断处、异常处理策略、交付物清单与合格标准。

Skill 是流程、规则、判断边界、工具与验收的集合。跑通首条任务时，我们通常会不断补充要求：某处不可删除、Cookie 失效要停止、推荐前需通读全文、必须生成三文件验证通过后才能改飞书状态……这些要求初始都落在聊天里，换对话就不在。

一旦某条要求经真实任务验证且会反复使用，就应从聊天中提取进 Skill。新对话的 Agent 读取后即可恢复该能力。

### 2. Skill 的基本组成

一个 Skill 通常是一个独立文件夹，以 SKILL.md 为入口，按需放入脚本、参考资料、模板与验证工具。

SKILL.md 为总入口，说明能力边界、触发条件、整体流程、停止时机与交付物。

references/ 保存详细规则，如字段说明、内容规范、异常类型、输出结构，避免塞满 SKILL.md。

scripts/ 保存可重复代码，如接口请求、字幕下载、JSON 解析、目录创建、文件检查等输入输出稳定、适合代码化的工作。

templates/ 保存产物模板，明确输出应包含的字段、标题与结构。

examples/ 保存正反案例，帮助 Agent 理解合格与不合格的边界。

结构并非唯一，关键是职责清晰。

### 3. SKILL.md 写什么

案例中的 SKILL.md 即按此思路生成，无需手动从零写，后续可让 Codex 基于真实流程生成并迭代。

### 4. Skill 的触发到执行链路

用户提出任务 → Agent 判断是否匹配某 Skill → 读取 SKILL.md → 按需加载规则、模板、案例 → 调用脚本/CLI/MCP → Agent 做语义判断 → 运行验证器 → 交付结果。

这种设计避免一次性把所有规则塞入上下文，按需加载，保持项目清晰，减少干扰。也可直接指令“使用 XX Skill 完成 XX”，降低误调风险。

### 5. Skill 的安装与查找

可让 Codex “帮我安装这个 Skill”。默认装到全局，也可在对应位置查看已安装列表。若业务特定、担心全局冲突，可不全局安装，只放进项目文件夹作为专属能力。本质都是包含说明与代码的文件夹，区别在于位置与生效范围。

### 6. Skill 与 Agent 的区别

流程短、操作单一时，直接用 Skill 足够。如“使用这个 Skill 完成任务”。

流程长、涉及多环节，则更适合搭建 Agent。Agent 能按工作流依次调用多个 Skill 协同完成复杂任务。如我部分复杂 Agent 会串联7个 Skill，每个 Skill 负责一道工序，内部再拆多步，便于维护、复用与迁移。

简言之，Skill 是单项能力，Agent 是调度多项能力完成完整任务的主体。

# 知识库：AI 员工的资料库与工作档案

Agent 是员工，Skill 是手册，知识库则是长期使用的资料库与档案。它保存业务背景、参考资料、历史产物、审核记录与已确认经验，让新对话也能恢复上下文。

注意：知识库不是 AI 大脑里的永久记忆，而是一组文件。Agent 每次重新读取文件才表现得像“记得以前的事”。

把大量资料堆在聊天记录里，短期可行。随对话变长会出现压缩丢失、规则与临时讨论混杂、版本难以分辨、换对话需重新交底、检索复用困难等问题。聊天适合讨论与试错，长久保存应写入知识库或项目设定。

### 1. Obsidian：适合 AI 读取的知识管理工具

Obsidian 本质是本地 Markdown 文件查看器。知识库就是一个普通本地目录，停止使用 Obsidian 后，文件仍可被 VS Code、Codex、Claude Code 等读取，兼顾人读与机读。

### 2. 从简单文件夹开始搭建

不必一开始纠结目录层级、标签体系、双向链接。不同业务保存内容不同，不存在通用黄金结构。更实际的做法是先服务真实任务，让结构随工作自然生长。

处理几条任务后会发现哪些文件常生成、哪些信息常被查、哪些资料需集中、哪些目录混乱、哪些字段适合模板化、哪些主题需索引。此时再让 Codex 统一梳理，效果更可靠。

知识库是先从业务中生长，再经整理固化。

### 3. 项目文件夹与知识库的分工

可放一起也可分开。项目文件夹像办公室，含 AGENTS.md、Skill、脚本、验证器、配置文件、临时目录、任务记录。

知识库像档案室，保存原始资料、整理后内容、历史产物、主题索引、审核结论、可多任务复用的业务知识。

小规模可合放，随着资料增多可独立拆分，再作为资料目录接入项目。

### 4. 让 Agent 准确找到资料

知识库小时可整体浏览，建立全貌。规模大了应分层读取：项目规则 → 知识库总索引 → 定位相关主题 → 读取对应文件与原始资料 → 完成任务写回产物 → 更新索引与审核状态。降低干扰，避免上下文被无关资料填满。

## CLI / MCP：Agent 连接外部工具的操作通道

Agent 能思考规划，Skill 规定怎么做，知识库提供资料。若只能在对话框里思考，仍只是建议大脑。CLI 和 MCP 是把判断变成实际动作的操作通道。

### 1. 从会回答到能操作：外部工具的价值

真实工作涉及飞书文档、任务领取、表格修改、GitHub 查询、视频下载、字幕处理、本地脚本、数据库、浏览器操作、结果回写系统等。Agent 负责判断下一步做什么，CLI/MCP 负责把判断传给外部系统落地。

# 把 AI 训练成能独立办事的数字同事：从 CLI、MCP 到完整 Agent 工作流

想让 AI 真正参与业务，关键不只是换一个更强的模型，还要给它准备稳定的工具、清晰的规则，以及可以反复运行的工作环境。

下面就以“批量处理 B 站视频字幕，并整理到 Obsidian”为例，完整走一遍搭建过程。

## 一、先认识两类基础工具

### 1. CLI：让 AI 通过终端调用软件

CLI 是 Command Line Interface，即命令行接口。简单来说，它就是软件提供的一套文字指令。用户可以在终端输入命令完成操作，自动化程序或 Agent 也能调用这些命令。

例如：

```bash
git status
gh pr list
ffmpeg -i input.mp4 output.mp3
lark-cli docs fetch --doc "飞书文档链接"
```

上面这些命令，分别可以用于查看 Git 当前状态、读取 GitHub Pull Request、转换音视频格式，以及读取飞书文档。

CLI 之所以适合接入 Agent，是因为它通常具备几个特点：

- 输入格式明确；

- 输出结果相对稳定；

- 可以被脚本串联；

- 容易记录和重复运行；

- 能够嵌入更长的自动化流程。

只要某条命令在电脑上能够稳定执行，Agent 就能把它当成一个可靠的工作节点。

如果希望 Codex 处理飞书里的资料，可以安装飞书 CLI，让它直接连接飞书并完成下载、创建、修改等操作。再结合相应的 Skills，能够覆盖更多业务场景。

请帮我安装飞书 CLI 工具，并安装所有相关的飞书 Skills：

第一步：

```bash
npm install -g @larksuite/cli
```

第二步：

```bash
npx skills add https://github.com/larksuite/cli -y -g
```

第三步：

```bash
lark-cli config init --new
```

安装完毕后，把执行结果反馈给我。

完成配置后，Codex 就能在飞书中创建和编辑文档，操作普通表格、多维表格，并完成数据读写等工作。

### 2. MCP：把外部服务变成标准化工具

MCP 的全称是 Model Context Protocol，即模型上下文协议。

它的作用，是把外部系统的功能整理成一套结构化工具。Agent 不需要自行研究底层接口，也不用手动拼接复杂请求，只要按照工具说明提供参数，再读取返回结果即可。

例如：

- 飞书 MCP 可以提供文档搜索、表格读取、任务创建、状态更新等功能；

- GitHub MCP 可以提供仓库读取、Pull Request 查看、评论获取等功能。

```text
search_documents(query="Agent")
update_task(task_id="123", status="已完成")
```

从使用体验上看，MCP 就像一套提前布置好的操作面板。每个工具有什么用途、需要哪些参数、最后会返回什么内容，都会事先约定好。

需要哪一种 MCP，直接交给 Codex 安装即可。

当然，如果没有可用的 CLI 或 MCP，Agent 也能借助浏览器，或者 computer use 插件来操作网页。但网页方案高度依赖页面布局、登录状态和弹窗情况，页面一改版，流程就可能失效。

所以在条件允许时，优先选择稳定的 CLI 或 MCP。

# 三、把重复业务改造成 Agent

## 一套八阶段搭建流程

这套方法是在包子老师六步法的基础上重新整理出来的。

| 阶段 | 具体动作 | 目的 | 最终效果 |

| 1 | 准备项目目录与版本管理 | 让资料集中保存并可追踪 | 出错时能够审查和撤销 |

| 2 | 让 AI 熟悉背景资料 | 避免在不了解业务的情况下贸然行动 | 减少错误推断 |

| 3 | 明确目标并调研方案 | 先确认技术路线是否可行 | 得到落地计划 |

| 4 | 完成一个最简样例 | 用真实结果暴露隐藏问题 | 形成 MVP |

| 5 | 接入飞书任务面板 | 支持排队、协作和批量处理 | 业务流程可视化 |

| 6 | 整理规则、Skills、脚本和检查机制 | 把临时共识变成项目资产 | 形成可复用流程 |

| 7 | 在当前会话再次运行 | 检验完整链条 | 找出流程漏洞 |

| 8 | 换一个全新会话重跑 | 排除聊天记忆带来的影响 | 证明能力属于项目本身 |

## 阶段一：准备项目目录和 Git

### 1. 建立独立工作目录

先创建一个专用文件夹，再让 Codex 打开它作为项目目录。

目录名称最好短一些、容易理解，尽量使用英文，避免使用“新建文件夹”“测试版”这类含义模糊的名字。

与项目相关的原始资料，可以复制一份放进去，原始文件继续保留在原处。

### 2. 加入版本管理

随后在该目录中初始化 Git，并用 GitHub Desktop 进行管理。

Git 会保存文件新增、修改和删除的历史记录，GitHub Desktop 则提供可视化界面。

这一步很重要，因为 Agent 往往会连续创建和修改许多文件。没有历史记录时，很难判断哪些内容来自原始资料，哪些是 AI 新生成的，也不容易撤销错误改动。

先在电脑上准备一个空目录。

如果有参考资料，再在项目目录里建立一个专门的资料子目录，将相关文件复制进去。尝试本文示例时，也可以把压缩包解压到这个位置。

## 阶段二：先让 AI 观察项目

在提出修改要求之前，先让 Codex 阅读项目现有内容，包括文档、示例结果、PDF、PPT 和必要图片。

重点是明确告诉它：当前只阅读，不执行修改。

可以这样说：

> 暂时不要做任何改动，请完整阅读项目目录中的所有内容。如果有文档、PDF 或 PPT，请同时查看其中的文字和图片。

如果需要参考外部页面，可以说：

> 先不要执行操作，请阅读下面的链接，完整查看其中的文字与图片。【链接 1】【链接 2】

针对本文案例，也可以简化为：

> 请先阅读项目目录中的全部文件，判断这个项目的用途和现有结构。

## 阶段三：描述目标，让 AI 先调研

不要一上来就要求它写程序。先把业务目标、输入、输出和期望流程说清楚，让它先给出技术方案。

例如：

> 暂时不要编写代码。我想实现这样一个流程：输入一个 B 站视频链接，获取视频信息和字幕，再对字幕进行整理，最后保存到 Obsidian 知识库。请到 GitHub 查找质量较高的项目和 Skills 作为参考。完成调研后，先说明可行方案、技术路径和所需信息，等我确认后再动手。

如果手里已经有源码，可以直接让它基于现有代码继续；如果没有，也可以先让它从头研究。

接着询问：

- 当前还缺少哪些信息？

- 是否具备运行最简版本的条件？

- 最先应该验证哪一个环节？

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_23_0.png)

样的话就可以问问他还需要什么信息，能不能跑最小 MVP，然后执行。你认为现在是否达到了最小闭环的开工条件？如果可以，先出抓取这个链接的字幕【链接】。

## 阶段四：先完成一个最简样例

这一轮的目标不是一次性覆盖全部场景，而是先把单条任务完整跑通。

先让一条业务链路正确运行，再逐步扩大处理范围。执行过程中，也可以同步补充验收标准。

本文案例需要提供 Cookie。若不知道如何获取，可以直接询问 Codex。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_24_0.png)

流程比较复杂时，建议分段验证。例如先只测试字幕获取，确认无误后，再进入字幕整理。

我希望最终内容尽量保持原始表达，因此先明确提出这一要求，等待第一版结果后再验收。处理完成后，可以打开“已处理”部分，观察 AI 的判断过程和输出结果，发现偏差就及时修正。

字幕获取和整理通过后，再进入知识库写入环节。此时同样需要把格式、命名、目录和内容要求讲明白。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_25_0.png)

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_25_1.png)

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_25_2.png)

文件命名可以根据个人习惯调整。到这里，一个最基本的业务闭环就跑完了。

刚开始不必急着设计复杂的知识库层级。更实际的方式，是先积累一批真实内容，再依据使用过程中出现的需求逐渐调整结构。

知识库的本质，就是一个用于保存和组织上下文信息的文件目录。

不建议照搬别人的目录结构。可以借鉴思路，但最终要根据自己的工作方式和检索习惯来设计。

知识库不存在唯一正确答案。只要它能够稳定保存内容、方便查找，并且确实解决问题，就是合适的方案。

## 阶段五：用飞书做任务面板

演示项目：B 站字幕知识库任务控制台。

在这个分工中：

- 飞书负责记录任务内容、处理状态和流转信息；

- Agent 负责领取任务、完成处理并提交结果。

这样一来，业务人员不需要进入代码目录，也不必每次重新编写一大段指令。

任务会具备排队、查看进展、记录失败原因和后续复盘等能力，未来还可以扩展到多人协作。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_27_0.png)

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_27_1.png)

还可以增加其他 Agent，让它们先批量处理任务，再把结果写回飞书表格；当前这个 Agent 继续读取表格并完成后续步骤。这样就能把不同角色组合成一条自动化流水线。

接入飞书后，还可以设置定时检查，让系统周期性查看工作台中是否出现新任务，有任务就自动处理，从而减少手动打开聊天窗口的次数。

## 阶段六：把经验沉淀成项目资产

当最简流程已经验证通过，就进入稳定生产阶段。此时重点不再是继续拉长聊天记录，而是把已经确认的业务规则写入项目。

通常需要整理四类内容：

- **AGENTS.md**：记录整个项目必须遵守的总规则；

- **Skill.md**：记录某一类任务的标准操作顺序；

- **脚本**：处理稳定、重复、机械的数据操作；

- **验证器**：检查输出是否满足最低要求。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_29_0.png)

这里必须注意：脚本只能做确定性的事情，不能替 AI 进行开放式语义判断。

早期为了尽快跑出结果，很容易在程序里加入临时规则：

```python
if "我们先看 2000 元以内这个区间" in line:
start_product_section()
```

这条规则或许适用于当前样本，但换一条视频，作者可能会说：

- “接下来我们按照价格展开。”

- “现在进入产品推荐部分。”

- “先从基础款开始介绍。”

- 也可能完全没有明显的过渡表达。

如果程序把某句话、某个行号、某个价格，甚至“第几款”直接写死，那么它只能处理少数相似样本。

更可靠的分工应该是：

- AI 阅读完整内容，结合上下文判断语义边界；

- 脚本保存 AI 已经做出的判断，并负责文件和格式检查；

- 验证器负责阻止不符合底线要求的结果进入下一阶段。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_30_0.png)

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_30_1.png)

本次演示需要特别强调一个危险点：不要依靠固定句子、固定价格、固定行号或产品序号切割文章。

程序负责稳定执行，AI 负责理解语义，验证器负责最后把关。三者各自承担不同职责，才能避免流程既不可靠又难以扩展。

另外，每轮生产都应把 Cookie 检查放在最前面，而且要静默完成：

1. Cookie 缺失或失效，立即中止；

2. 在确认凭证有效前，不读取业务任务；

3. 不把 Cookie 写入日志或归档；

4. 本地文件全部生成后，先运行检查程序；

5. 再由 AI 完成最终复核；

6. 所有条件满足后，才允许将飞书任务标记为完成。

这样设计，是因为聊天里的约定可能随着会话结束而消失，而写死的程序规则又只能适应单一案例。

把规范、工具和验收机制拆开保存，既能保留流程的稳定性，也能让 AI 保持处理复杂语义的弹性。

最终得到的，其实是一份可重复使用的岗位说明。下一次只要告诉 AI“处理任务 2”，它就应该知道：

- 先检查哪些前置条件；

- 到哪里读取任务；

- 结果如何保存；

- 哪些情况需要停止；

- 何时才允许回写成功。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_31_0.png)

## 阶段七：在原会话里做一次回归检查

每次修改项目规则、脚本或文件结构后，都要重新运行一条真实任务。

目的，是确认新改动没有破坏原本正常的功能。如果出现执行失败或结果质量下降，就修正问题，必要时恢复到之前的版本。

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_32_0.png)

![](img/zhuanqian_fab9b22cf1a5ded3c6c0c223fe180f51_32_1.png)

## 阶段八：换新会话验证独立运行能力

完成上一轮检查后，关闭原来的长对话，重新开启一个全新会话。

让 Codex 重新阅读项目文件，再执行一条任务。

这一步是为了确认：它能否仅依靠项目中保存的规则和 Skills 完成工作，而不是依赖此前聊天中没有写入项目的临时记忆。

如果新会话能够完成任务，并通过所有检查，就说明这套流程已经从“某一次聊天里表现不错”，升级为“项目本身具备可调用能力”。

这也是判断一个 Agent 是否接近生产可用的重要标准。

# 四、选学：用 Hermes 做持续运行，并接到飞书

如果电脑里还没有 Hermes，可以先准备一个新的目录和项目，再让 Codex 完成安装与部署。

可以这样提出要求：

> 请在当前项目目录中安装并部署 Hermes。部署完成后，让它调用我电脑里 Codex 的 GPT-5.6 Sol 极高模型，速度使用 1.5 倍。

> 请让 Hermes 承担持续生产任务，并连接到飞书。为这个项目创建一个专用机器人，以后我通过飞书与 Hermes 交流。

`/Users/shuye/Desktop/Project/bilibili agent/benchmarking agent`

接着说明：

> 请把这个项目接到飞书。它是一个新的 Agent，请为它创建独立机器人，以后通过飞书和 Hermes 沟通并运行这个项目。
