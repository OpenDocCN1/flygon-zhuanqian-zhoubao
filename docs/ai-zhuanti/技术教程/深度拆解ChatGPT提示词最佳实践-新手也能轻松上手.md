## 先搞清楚三个角色：USER、ASSISTANT、SYSTEM

在后面的案例里，你会反复看到这三个角色。我先统一介绍一下，顺便问问ChatGPT本人：

![](img/zhuanqian_cc627c749795e9226f52cadad9c363c4.png)

其中SYSTEM在官方网页版对话里基本不会现身，因为ChatGPT本身就是设计来跟用户直接聊天的。但如果你用API开发自己的应用，SYSTEM就能在不少场景里发挥大作用了。

举个例子，一个“音乐小助手”应用里，SYSTEM就是那个在后台默默控制全局的角色：

```
SYSTEM: 提示：您可以问我任何与音乐相关的问题。
USER: 什么是贝多芬的第五交响乐？
ASSISTANT: 贝多芬的第五交响乐是......（详细描述）。
```

不懂编程的小伙伴也别急，想在ChatGPT上体验SYSTEM角色，其实有办法。比如这句“当我请求帮助写东西时，你将在每个段落中至少加入一个笑话或俏皮话”，本质上就是SYSTEM的指令。只不过为了方便在网页窗口测试，后面所有的案例里，我们都会用USER来代替SYSTEM：

## 最佳实践一：把指令写清楚

GPT不会读心术。它输出的答案太长，你就让它简短点；太简单，你就要求它有专业水准；你不喜欢某种格式，就直接展示你想要的格式。GPT越少去猜你的意思，你得到满意结果的概率就越大。

具体怎么做？有下面几个策略：

### 策略1：给足细节，答案才更靠谱

适用人群：新手　难度：🌟

想要高度相关的回答，提问时就得把重要的细节和上下文都交代清楚。不然模型只能靠猜，结果自然容易跑偏。

说白了，这个策略就是通过提供更多信息，让答案更准确、更具体，减少来回试错的成本。GPT就像你的男朋友，但有时候它真的猜不出来（手动狗头）。

### 策略2：让模型扮演角色

适用人群：新手　难度：🌟

系统消息里可以指定角色，模型就会按照那个角色的特点来回答，回答会更有特色和针对性，质量也跟着上来了。

```
USER
写一封感谢信给我的软件供应商，感谢他们准时并在短时间内交货。这使我们能够交付一份重要的订单。
SYSTEM
当我请求帮助写东西时，你将在每个段落中至少加入一个笑话或俏皮话。
```

### 策略3：用分隔符划清边界

适用人群：新手　难度：🌟

三重引号、XML标记、节标题这类分隔符，能帮你把输入里不同部分的文本清楚地区分开。

```
USER
使用三重引号中的文本撰写一首诗。
"""在这里插入文本"""
```

```
SYSTEM
你将获得一对关于同一主题的文章（用XML标记分隔）。首先总结每篇文章的论点。然后指出哪篇文章提出了更好的论点，并解释为什么。
USER
在这里插入第一篇文章
在这里插入第二篇文章
```

```
SYSTEM
你将获得一份论文摘要和一个建议的标题。论文标题应该给读者一个很好的论文主题概念，同时也要引人注目。如果标题不符合这些标准，请提出5个备选方案。
USER
摘要：在这里插入摘要
标题：在这里插入标题
```

简单任务用不用分隔符可能差别不大，但任务越复杂，把细节分清楚就越重要。别让GPT费劲去猜你到底要什么。

想想看，你正在组装一个很复杂的玩具，所有零件混在一起还没有标签，是不是很崩溃？模型拿到复杂的输入也一样，没有清晰的分隔符，就容易混淆。分隔符就像给零件贴标签，让组装过程流畅多了。

### 策略4：把步骤写出来

适用人群：新手　难度：🌟

有些任务最好按步骤来。把步骤清楚地列出来，模型更容易跟上你的思路。

```
SYSTEM
使用以下逐步说明来回应用户输入。
步骤1 - 用户将用三重引号提供给您文本。用前缀"Summary: "对这段文本进行一句总结。
步骤2 - 将步骤1中的总结翻译成西班牙语，并使用前缀"Translation: "。
```

### 策略5：给个示例

适用人群：新手　难度：🌟

大多数时候，给所有示例的一般说明比演示变体更高效，但有些情况给示例反而更容易。比如，你想让模型模仿一种很难用语言描述的用户查询响应风格。这就是“few-shot”提示。

```
SYSTEM
用一致的风格回答。
USER
教我什么是耐心。
ASSISTANT
刻出最深峡谷的河流起源于一处平凡的泉眼；最壮丽的交响乐源于一颗单独的音符；最复杂的挂毯始于一根孤立的线缕。
USER
教我关于海洋。
```

### 策略6：规定输出长度

适用人群：新手　难度：🌟

你可以让模型生成指定长度的内容，比如多少词、多少句、多少段、多少个要点。不过要注意，让模型精确生成多少个单词可不太靠谱；相比之下，指定段落数或项目符号数会更可靠。

```
USER
用大约50个词总结由三重引号分隔的文本。
"""在这里插入文本"""
USER
用2个段落总结由三重引号分隔的文本。
"""在这里插入文本"""
USER
用3个项目符号总结由三重引号分隔的文本。
"""在这里插入文本"""
```

## 最佳实践二：提供参考文本

GPT会一本正经地编造答案，尤其是被问到冷门话题、引用或网址的时候。给它一篇参考文本，就像考试时给学生一张小抄，能明显减少它“胡编乱造”的概率。

### 策略1：让模型根据参考文本回答问题

适用人群：新手　难度：🌟

如果你能给模型提供和当前问题相关的靠谱资料，就可以让它用这些资料来组织答案。

```
SYSTEM
使用由三重引号分隔的所提供的文章来回答问题。如果答案在文章中找不到，写下"I could not find an answer."
USER
<插入文章，每篇文章由三重引号分隔>
问题：<插入问题>
```

不过GPT的上下文窗口有限，想用好这个策略，得用某种方式动态查找跟问题相关的信息。用提供指定内容的方式，就能实现高效的知识检索。

我觉得最大的好处就是减少错误。因为模型可能“幻想”出一些答案，尤其在被问到偏门话题或需要引用和URL时。有参考文本兜底，它瞎编的概率就小多了。

### 策略2：让模型用引文回答

适用人群：新手　难度：🌟

当输入里已经有相关知识了，直接要求模型把所提供文档里的段落引用到回答里就行。还可以通过字符串匹配，编程验证输出中的引文。

```
SYSTEM
你将得到一个由三重引号分隔的文档和一个问题。你的任务是只使用提供的文档来回答问题，并引用用来回答问题的文档段落。如果文档不包含回答此问题所需的信息，那么只需写下：“信息不足”。如果提供了问题的答案，必须用引文进行注释。使用以下格式引用相关段落 ({"citation": …})。
USER
"""<插入文档>"""
问题：<插入问题>
```

## 最佳实践三：把复杂任务拆成简单子任务

就像软件工程里把复杂系统拆成模块化组件一样，交给GPT的任务也应该这么处理。复杂任务通常错误率更高，但把它们重构成一系列简单任务的工作流——前一个任务的输出作为后一个任务的输入——就能好很多。

### 策略1：用意图分类找到最相关的指令

适用人群：新手、熟练者　难度：🌟🌟

遇到不同类型的情况，先按类型分类，再为每种类型设计专门步骤，像做菜有食谱一样。复杂任务可以分成小阶段，每个阶段有自己的指令，整个处理过程更有组织、更高效。

这样做的好处是，每个查询只需要包含执行下一阶段所需的指令，比一次性完成整个任务的错误率更低。而且提示更短，运行成本也更低——当然，这条是针对用API的小伙伴。

举个例子，客户服务应用可以把查询分类成这样：

```
SYSTEM
你将得到客户服务查询。将每个查询分类为主要类别和次要类别。以json格式提供你的输出，包含主要和次要两个关键字。
主要类别：计费，技术支持，账户管理，或一般咨询。
计费次要类别：
- 退订或升级
- 添加付款方式
- 收费解释
- 争议收费
技术支持次要类别：
- 故障排除
- 设备兼容性
- 软件更新
账户管理次要类别：
- 密码重置
- 更新个人信息
- 关闭账户
- 账户安全
一般咨询次要类别：
- 产品信息
- 价格
- 反馈
- 要求与人对话
USER
我需要让我的互联网再次工作。
```

基于客户查询的分类，模型就能收到一组更具体的指令来处理下一步。比如客户需要“故障排除”的帮助：

```
SYSTEM
你将得到需要在技术支持环境中进行故障排除的客户服务查询。通过以下方式帮助用户：
- 让他们检查到/从路由器的所有电缆是否已连接。注意，电缆随着时间的推移会常常松动。
- 如果所有电缆都已连接并且问题仍然存在，询问他们正在使用哪种路由器模型
- 现在你将建议他们如何重新启动他们的设备：
-- 如果型号是MTD-327J，建议他们按下红色按钮并保持5秒钟，然后等待5分钟后再测试连接。
-- 如果型号是MTD-327S，建议他们拔掉并重新插入，然后等待5分钟后再测试连接。
- 如果客户在重启设备并等待5分钟后的问题仍然存在，通过输出{"IT support requested"}将他们连接到IT支持。
- 如果用户开始提问与此主题无关的问题，那么请确认他们是否希望结束当前关于故障排除的聊天，并根据以下方案对他们的请求进行分类：
<插入上述主/次分类方案>
USER
我需要让我的互联网再次工作。
```

注意，这里已经让模型在会话状态改变时输出特殊的字符串。这样一来，系统就变成了一个状态机，状态决定哪些指令被注入。通过跟踪状态、判断该状态下哪些指令相关、允许哪些状态转换，就能在用户交互上设置保护，这在不太结构化的方法里很难实现。

简单说，就是先搞清用户的真实需求，再给最合适的答案。特别适合那些要用多种独立指令处理不同情况的任务。

### 策略2：长对话里，总结或过滤之前的对话

适用人群：熟练者、程序开发人员　难度：🌟🌟

假设你在和一个虚拟助手聊天，由于GPT的上下文长度固定，对话不可能无限延续下去。怎么破？有两个常用方法。

第一种，把前几轮对话做个总结，像写小短文一样把核心信息概括出来。当输入长度达到一定阈值，系统可以自动触发一个查询让模型总结，总结结果作为系统回复的一部分；也可以在整个对话过程中分批总结。

第二种，根据当前查询，挑选和当前问题最相关的前面对话。就像看书时直接翻目录找相关章节。“基于嵌入的搜索来实现高效的知识检索”说的就是这种方法。

我给大家模拟一个案例：在线医疗咨询应用里，用户会描述症状、病史、用药情况等，越聊信息越多。但当用户提到新症状时，模型必须记住前面的相关信息才能给出准确建议。这时候对前面对话做总结或筛选，只保留与当前问题最相关的信息，就能帮模型更好地理解和回应。

模拟对话数据如下：

```
用户：我最近总是感到头痛。
ChatGPT：您的头痛是突然发生的还是已经有一段时间了？您还有其他的症状吗？
用户：已经有两个星期了，而且我还伴随着恶心。
ChatGPT：您最近有没有服用任何药物或者有其他的医疗历史？
用户：我有高血压，正在吃降压药。
ChatGPT：了解了。您的头痛和恶心可能与您的高血压或降压药有关。建议您咨询医生并检查一下。
...[对话继续]
当对话达到一定长度后：
用户：我还想知道头痛的其他可能原因。
ChatGPT（在内部对之前的对话进行总结）：您之前提到有高血压并正在服用降压药，伴随头痛和恶心。除了高血压和药物反应，头痛的其他可能原因包括：应激、缺乏睡眠、饮食不当等。
```

这样，即使对话很长，ChatGPT也能一边结合历史信息，一边准确回应用户。

### 策略3：分段汇总长文档，递归构造完整概要

适用人群：熟练者　难度：🌟🌟

GPT这类模型在处理文本时，只能看到一定长度的文字，超过就“看不见”了。要总结一本厚厚的书，就得分段处理。

每一段都作为一个查询去总结，然后把各段总结连起来，形成整体总结。这个过程可以不断重复，直到整本书都被总结完。

在处理超长文档时，AI常常会因为上下文窗口有限而“顾此失彼”。一个很实用的做法是：把文档拆成多个部分逐一总结，再将摘要合并、提炼，得到全局结论。如果某些章节之间存在前后依赖，那么在总结后续内容时，把前面章节的摘要一并带上，能让模型理解得更透彻。OpenAI曾尝试用GPT-3的变体来做这类长文摘要，效果表现不错。

很多刚接触的小伙伴会问：token到底是什么？简单说，token是文本处理的最小单元，它可能是一个汉字、一个英文单词、一个标点，甚至一个子词。不同模型对token的切分方式不太一样，所以它代表的含义也有细微差别。例如，Claude-2-100k模型支持100,000个token，ChatGPT-16k模型上限是16,000个token，而ChatGPT-4-32k模型则可以处理32,000个token。一旦超出这个上限，模型就会“忘记”开头的对话。在Transformer这类架构中，文本首先被切成一个个token，再转化成向量交给神经网络计算。通俗点说，我们输入的文字变成token后，大模型就像在做词语接龙，一个接一个地生成输出，最终形成完整的回复。

## 第六个最佳实践：给GPT多一点“思考时间”

你大概不会一口报出17乘以28的答案，但只要花点时间算一算，很快就能得到正确结果。GPT也是类似——它被要求立即作答时，容易犯推理错误；如果先让它“想一想”、做一连串推导，答案的可靠性会明显提高。

这里有几个可执行的小策略：

*   指示模型在给出结论前，先独立解决问题。

*   用内心独白或多轮查询，把推理过程藏起来。

*   让模型自查一下，前面的处理是否有遗漏。

### 策略一：别急着下结论，先让模型自己算一遍

**适用人群：熟练者、程序开发人员**

**难度：★★☆**

### 策略二：用内心独白或多轮对话，隐藏模型的推理链

**适用人群：熟练者、开发人员**

**难度：★★★**

前一个策略告诉我们要让模型推理，但有些场景下，推理过程并不适合展示给用户。比如在辅导类应用中，我们希望学生自己动脑，但如果GPT把对学生答案的详细分析直接展示出来，就等于把答案泄露了。

这时候可以用“内心独白”策略：让模型把那些不想让用户看到的内容放到一个固定结构里（方便解析），然后在展示之前，把可见部分过滤出来，只把该给用户的内容呈现出去。

```

步骤 2 - 将你的解答与学生的解答进行比较，并评估学生的解答是否正确。将此步骤的所有工作都包含在三引号（"""）中。

步骤 4 - 如果学生犯了错误，将上一步的提示提供给学生（在三引号之外）。写"提示："，而不是"步骤4 - ...”。
USER
问题描述： <插入问题描述>
学生的解答： <插入学生的解答>
```

### 策略三：让模型再想想，前面有没有漏掉什么？

## 第七个最佳实践：善用外部工具，补足GPT的短板

GPT并不是万能的。给它接上外部工具，能有效弥补它在知识检索、精确计算等方面的不足。例如，用文本检索系统提供相关资料，用代码执行引擎处理数学计算。如果某个任务用工具比用GPT更可靠、更高效，那就放心地把活交给工具。

策略包括：

*   用基于嵌入的搜索做高效的知识检索。

*   用代码执行完成精准计算或调用外部API。

### 策略一：基于嵌入的搜索，让知识检索又快又准

**适用人群：程序开发人员**

**难度：★★★★**

所谓“文本嵌入”，可以把文字转换成一种特殊的向量，这个向量能反映文本之间的关联——内容越相似，向量就越靠近。借助快速向量搜索算法，我们就能在海量文本中迅速找到最相关的内容。就好比一个庞大的电影数据库，所有影片信息都被转换成了向量；当用户提问时，把问题也变成向量，然后在库里搜索最接近的几项，就能找到想要的答案。这样，模型就能借助外部信息回答得更准确。

#### 解读

这个方向更偏向开发者。举个具体例子：假设我们有一个包含海量电影信息的数据库（演员、导演、剧情等），用户想知道“小李子主演的电影”。系统会把这个问题向量化，再去数据库里做相似度检索，马上就能返回《泰坦尼克号》《盗梦空间》等匹配结果。

实现这个功能，大致需要这些步骤：

1. 选择文本嵌入工具，如Word2Vec、BERT、FastText等。

2. 准备电影数据库，可以是简单的文本文件，也可以是真·数据库。

3. 对每部电影信息做嵌入，得到向量并存储。

4. 处理用户查询，把查询也转成向量。

5. 用余弦相似度或KNN等算法，在向量空间中搜索最接近的电影向量。

6. 根据搜索结果，把对应电影信息返回给用户。

7. 封装成API或函数，集成到ChatGPT的对话流程中，让模型自动调用。

当然，这只是一个整体框架，实际落地时还会遇到更多细节，但核心思路就是把文本嵌入和向量搜索结合起来，从而实现高效、低成本的检索。

### 策略二：用代码执行做精准计算或调外部API

**适用人群：熟练者、程序开发人员**

**难度：★★★**

提醒一下：虽然这个策略名字里带“代码”，但它并不只属于程序员。哪怕你不懂编程，只要掌握了前面介绍的基础知识，也能比较轻松地使用它。

GPT在纯算术或长计算上的能力相当有限，所以我们不该指望它。靠谱的方案是——让模型写代码、运行代码，而不是自己硬算。操作上，可以要求模型把代码放在特定格式里，比如三个反引号内；输出后提取出来运行；如果必要，还可以把代码引擎（比如Python解释器）的运行结果再喂回给模型，作为下一步输入。

```
SYSTEM
你可以通过将代码包含在三重反引号中来编写和执行Python代码，例如 ``代码在此``。使用这种方式来进行计算。
USER
找出以下多项式的所有实数根：3*x5 - 5*x4 - 3*x**3 - 7*x - 10。
```

代码执行的另一个常见场景是调用外部API。只要在提示中提供API文档或代码示例，模型就能学会正确地调用它。

```
SYSTEM
你可以通过将代码包含在三重反引号中来编写和执行Python代码。另外注意，你可以使用以下模块帮助用户向朋友发送消息：
``python
import message
message.write(to="John", message="Hey, want to meetup after work?")
``
```

需要特别提醒：运行模型生成的代码有潜在风险，任何想这么做的应用都需要采取安全措施，比如在沙箱环境中执行，以隔离不受信任代码可能带来的破坏。

#### 解读

这个策略的核心要点可以归纳为：

*   GPT不能用来做精确计算，尤其长时间或大数运算。

*   需要计算时，让模型编写并运行代码，而不是让它直接给答案。

*   可以要求模型把代码放在特殊格式（如三重反引号）中，便于提取。

*   代码运行的结果，如需继续处理，可以输入给模型做下一轮查询。

结合案例来看：假如你想知道1000以内所有的质数，直接问GPT大概率得到的答案不完整。但你可以让它写一段代码去计算，运行之后就能拿到准确列表。类似的场景，都可以参考这个思路。

用代码当桥梁，让模型把难题算准，这件事比想象中简单。

第一步，先让模型帮你写代码。无论是 GPT-3.5 还是 GPT-4 都能胜任，遇到复杂的逻辑时 GPT-4 的编码能力会更稳。

![](img/zhuanqian_052339ca0c1fd16e5129b956de8e7956.png)

第二步，开一个全新会话，把刚生成的代码完整喂回去。在这一步提问时，优先调用 GPT-4 的 代码解释器 来跑。

![](img/zhuanqian_6ae0339389bdded9ae56cddedbcc51da.png)

第三步，给一个明确的指令号，让模型进入执行模式跑代码。这样你就能拿到完整且正确的计算结果。

![](img/zhuanqian_1c2649f8f05cbffc1ee96dc098148e5d.png)

看明白了吗？就算你没有编程基础，用这个组合拳也能先生成代码，再借助 代码解释器 执行，得到比直接让模型脑补更靠谱的答案。毕竟一条严谨的代码，在处理繁琐计算和复杂逻辑时，远比偶尔犯迷糊的模型更让人放心。

对程序开发者来说，这种方式的加成就更明显了。优秀的工程师能把玩法玩出花来，实现更多自动化与验证。我个人目前的成果还算普通，只能说火候还不够，哈哈。

## 八、最佳实践6 - 系统化地检验改动效果

适合人群：熟练使用者、程序开发人员

难度：🌟🌟🌟🌟

用完整的用例集合去压测，模型才更坚韧，也更贴合真实需求。要警惕的是，某项微调在单一测试上表现亮眼，放进更广的样本里却可能整体拉胯。所以想确认改动是否真的有效，就必须依靠一套完整的测试案例来做判定。

策略：

*   以参考答案作为标尺来衡量模型输出。

评估对系统优化的意义很大。一个好的评估体系通常具备：

*   贴近真实使用场景，场景要足够多样

*   测试用例数量充足，覆盖更广的统计区间

*   便于自动化执行

评估结果可以由机器、人或两者协同完成。机器可以采用固定标准，比如唯一正确答案的题目，也能用自动化手段处理部分主观题，其中模型的输出会被另一套测试程序校验其正确性。例如 OpenAI Evals 就是一个开源框架，专门用来搭建自动化评估流程。

当正确答案并非唯一，而是存在多个同等高质量的表达时，基于模型的评估会更有价值。什么该交给模型判，什么必须人工判，这个边界很模糊，并且随着模型能力提升而不断移动。官方建议多做实验，去验证基于模型的评估在你的具体案例上是否靠谱。

#### 解读

官方给出了两种思路，一种是与标准答案做匹配比对，另一种是在此基础上加入重叠与矛盾的分析，从而实现更立体的评估。

我觉得这两种思路能给 程序开发人员 带来以下帮助：

1.  评估更深入：不止比对表层是否一致，还会分析重叠与冲突，从而更全面地呈现模型表现。

1.  捕捉细节差异：通过追踪重叠与矛盾，更容易发现输出中的细微偏差和潜在风险。

1.  提升准确与可靠：确保输出既贴合专家标准答案，又不与其相悖，从而提高整体可信度。

借助这种评估方式，开发者能更清晰地看清模型的真实表现，判断是否需要进一步优化。这本身就是一套非常实用的测试手段。
