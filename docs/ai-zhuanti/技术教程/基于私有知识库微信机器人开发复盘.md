# 基于私有知识库微信机器人开发复盘
作者：龙哥

最近我完成了一个“私有知识库 + 微信机器人”的项目，趁热把整个决策过程、踩过的坑和最终架构整理一下。这篇复盘不打算堆代码，因为你会发现，只要架构想清楚了，写代码真的就是个熟练工。

先说项目目标。这个机器人要能管多个微信群，通过自动问答帮产品引流；把老师的个人知识沉淀下来，放大成标准化的产品；面向月嫂人群，提供一个能自助查询的机器人；在上户这种工作场景里，月嫂问一句就能快速拿到答案，给雇主一个及时交代；培训端也能快速响应，顺带完成课程引流和转化。最终它应该是一个标准的助手产品，不同人看到的是不同形态——给月嫂用是工作助手，给客户用是答疑工具。

我最大的感受是：很多IP、个人手里有技能和内容，但一直缺一个放大的方式。现在尝试的路径是“AI + 私有运营SOP + 私有内容”。就拿月嫂来说，群运营本身不复杂，本质上就是咨询群。真正的壁垒是私有数据——以前这些数据散落在各处，没法快速定位，更没法从多个角度综合出答案；现在可以了。

场景上，月嫂需要“快”，所以选了微信机器人；问题往往很复杂，比如“妈妈有高血压，现在发烧38.5，还能母乳喂奶吗”这种复合问题；回答之后还可以附带后续内容，顺便做营销。内容方面，尽量复用已有内容，不额外增加制作压力，把不同内容分成不同集合，做少量个性化设置就行。

商业上能想到的方向包括：客服、个人学习助手、作为整体SOP一环的自动文本生成、以及其他还没展开的玩法。

下面进入实操复盘。我以“国际认证泌乳顾问IBCLC培训课程”为例子。完整SOP是：先把已有的直播转录播课内容做成内容库；再用RAG做问题资料命中；然后把资料和问题整合成回答；最后接上微信机器人。

内容库怎么搭？课程都在小鹅通，可以下载成本地文件。转录工具有两个选择：一是本地跑Whisper，Mac上用whisper.cpp；二是通义效率的音频转录功能![](img/zhuanqian_adf5a67050bd90060066619927013904.png)。我选了后者，下载原文保存成txt，拿到全部原始内容![](img/zhuanqian_b19e6301c33962a34e783c6aae54a3a7.png)。

但直播转录的噪音实在太多。比如《泌乳原理》这节课，会出现这种信息量极低的段落![](img/zhuanqian_455d7f7bc6fbcf2e5eccf093bb7d3177.png)；《如何控制奶瓶流速》里也有类似情况![](img/zhuanqian_cad72b749c18d6881ed2e2945d224135.png)。这种噪音会让RAG切出来的chunk内容含量低、干扰大，查询命中率自然就差。试了几种清洗方案后，最终选了大模型LLM来做清洗：写一个清洗提示词，考虑到token限制，分段处理。前面标红的那段内容，清洗后变成了这样```
奶粉冲调前，要看品牌，是否是特殊奶粉，看生产日期在奶粉罐底部，再看冲调标准、水温标准，要和妈妈沟通奶粉水温冲调及宝宝喂奶瓶控制奶瓶流速的问题。
```。

清洗完还是太长，不能直接用，得先切分再向量化。切分我试了很多种，最后发现用“段落为单位的滑动窗口”就够了。Coze知识库后台有很直观的可视化展示![](img/zhuanqian_f101bcc2d8ffec69e8639989c5840e2e.png)。向量化可以用在线大模型的Embedding接口（花钱），也可以用本地Ollama的nomic-embed-text模型（免费）。

存储工具上，我强烈推荐pgsql + pgvector，没必要单独上向量数据库。因为要结合数据库的其他字段做查询，这个组合是最好用的，性能和社区支持也都非常靠谱。

再说RAG命中。原理不复杂：把问题向量化，再在已经向量化的内容里做相似度查询。但有个关键点：不要直接对原始问题做向量化，先拆分子问题。比如原始问题“孩子出生5天，吃的少，体重下降，妈妈很担心，我该怎么办”，先拆成“出生5天吃的少体重下降”和“担心孩子状况”两个子问题，再分别向量化查询，效果会好很多。

至于整合资料和回答问题，这部分其实不难，标准数据库查询加内容组合，唯一要注意的是别超过大模型的上下文长度。

微信机器人侧，工具选择很多，比如Wechaty、WechatFerry、ChatGPT-on-WeChat，具体细节可以去看9月的Coze航海。我主要说说架构设计。除了微信官方合规的限制，还要注意：微信和hook程序跑在Windows上，要么用云Windows服务器，要么用本机。如果本机没有公网IP，业务应用在公网就没法和这个Windows双向通信；而且很多服务软件只有Linux版，操作系统异构很麻烦。

我的选择是：让微信机器人只承担信息上传和下发的管道职责，不做任何业务处理。在机器人所在的Windows上启动一个pub/sub服务，业务服务（带公网IP）注册过来，主要注册两个接口：一个接口是消息推送，机器人收到新消息就推给业务服务器，订阅时可选全部消息或指定群/私聊；另一个接口是回复拉取，Windows上的机器人每隔几秒（比如5秒）去抓有没有新回复，如果有就把内容发到对应的群或私聊。

这么设计的好处很明显：普通家庭网络部署一台Windows就行，我自己测试时就有一台机器人是跑在家里旧Windows上的，另一台跑在Linux机器上的Windows虚拟机里。业务管理服务器可以同时对接多个机器人，批量管理很方便。

再往远了想，这套模式能不能用来批量生成自媒体文案？能不能加定时任务让机器人活跃群？能不能配一个CRM管理用户信息？能不能让机器人做个性化回复？展现形式上，可以做内容库批量生成问题，分发到小红书、抖音；可以做播客；也可以做客服。

最后说后续计划：可能借ChatPAN.ai“还魂”，做一个开源+商业的版本。毕竟做完发现，好多地方都会用到这个能力。
