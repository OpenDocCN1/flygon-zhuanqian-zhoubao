# 半天半：用 Cursor 和 AI 拼出来一个能用的小产品
# 产品从哪里来
在看赚钱风向标的时候，我注意到 Rizz 这个项目火了。它的玩法很简单粗暴：你丢一张聊天截图进去，它就帮你接着聊。
这个念头像是我去年就埋下的。当时我就想做一个能陪人聊天的东西，可一直卡在交互上。现在看到 Rizz 用上传截图的思路把问题解开，加上过去半年 AI 编程工具和应用层爆发式增长，正好赶上九月航海的窗口，我就想试试能不能 36 小时内把一个可用的 MVP 先跑出来。

# 怎么做的，以及做的时候在想什么
## 先说为什么要做
出发点在上面。但在开工前我还是确认了下这件事值不值得花时间。
1. Rizz 在约会类榜单里常年第一，据说月流水能到 20 万美金左右。
2. Rizz 的需求源头是 Reddit 上的大量求助帖，大家普遍不知道怎么回。
3. 我身边朋友也反馈，真实生活中很多人对这种需求是刚需。
有了这三点，我就没再继续做深度调研。想法是：如果 24 小时能搭出原型上线试水，只要用户量及格，后续变现和天花板都不成问题。
## 功能的取舍
时间盒定在一天以内，砍功能是必须的。
* 聊天对象的背景设定等，砍掉。
* 多对象同时处理，砍掉。
* 登录体系，砍掉了。纠结了很久，最后还是放弃。海外部署的话 Google 登录最顺手但门槛高，微信登录在网页端没做过，要查资料费时间。
* 多聊天软件截图支持，砍掉。先只做微信，把闭环跑通。QQ 很可能是下一个。
## 技术栈怎么选的
这个小东西的技术点其实就几块：
1. 前端
2. 后端
3. 文字识别
4. 数据库
5. 大模型调用
考虑的出发点是开发速度与长期维护的平衡。
航海手册里快速部署的方案很多，但 OCR 想要做得像样，还是得自己搭服务器。手上恰好有可复用的代码底子，我后端出身，前端几乎是白纸。Cursor 这类 AI 工具是靠海量代码训练出来的，所以选主流语言它才更靠谱。
后端我选了 Java。熟悉度高，后续维护压力小，且有存量代码可复用。Python 对我来说更适合搭脚手架。Go、Rust 不够熟，JS/TS 还没在需要长时间跑服务的场景里验证过。
框架选了 Micronaut。Spring 太重，Micronaut 文档齐全，Cursor 也能直接吃。
前端选了 Vue。我对 Vue 的掌握大概只有一成，但它是 JS/TS 生态，响应式网站做起来顺手。
组件库用 Flowbite，基于 Tailwind，省心，而且之前摸过。
## 真正开写
主要工具就是 Cursor。
用 Cursor 的时候我保持了几个习惯：
1. 前端、后端、OCR 这类服务各自独立成一个项目，让 Cursor 在一个仓库里只面对一种语言，理解起来更准。
2. 先把涉及的框架文档等资料塞进 Cursor 的知识库，让它提问时有据可查。
3. 能先找现成的项目脚手架就先找，让 Cursor 在已有骨架上改，而不是从零造轮子。
![](img/zhuanqian_4b9ca56879b0f0e1c8664af337c459cb.png)
### 为什么要先搭框架
不同语言的框架大同小异，没有绝对的好坏，只有适不适合。如果你让 Cursor 直接从零开始，它会按自己的偏好选型。比如 Java 最主流的是 Spring，Cursor 生成的代码大概率会带 Spring 的影子，从结构到配置都会被带偏。先用工具把骨架搭好，Cursor 就被限制在既定范围里，反而能给出更聚焦、更可控的代码。
## 我是怎么用 Cursor 的
大致分了三种角色。
1. 在熟悉的领域，我把它当结对编程的搭档。
2. 在不熟悉的领域，我当产品经理，它当开发，我负责评审和改代码。
3. 在纯技术咨询场景，我就把它当高级版 ChatGPT 用。
### 当结对编程伙伴
这种模式下我会大量亲手写。最常用的几种打法：
1. 我先写开头，比如变量定义、注解 @Inject 这类骨架，让 Cursor 去补全。上下文它能连起来，准确率大概八成左右，省的是手速。
![](img/zhuanqian_e0735a63f927cf51c26a34f932016029.png)
2. 我脑子里有清晰的实现思路，就用 Cmd+L 唤起对话，给一个粗糙的实现描述，让它生成初稿，我再合并。
3. 把报错信息原样丢进去，让它诊断。
我始终主导代码库，清楚每个细节。让它写单元测试，再通过审测试来反向检查业务代码质量。
### 我当需求方
前端对我来说就是盲区，很多生成代码看不懂。流程是这样的：
1. 用 Cmd+I Composer 让它一次性生成多个文件，前提是我知道这是多文件任务。
2. 生成的文件先放着，大概率是不可用的。
3. 直接跑起来，看报错，然后在对话里一边修一边反馈。
我当甲方，需求必须写死。还会给它参考产品，比如前端就指定要模仿谁的交互。
大部分时间都在对话区打磨需求。因为前端能在浏览器里即时预览，改-看的循环很快。

### 一些实操心得
1. 把文档提前喂进去。在小众代码场景里，用 @ 指名让它参考指定文档，效果更好。
1. 框架版本迭代快，不同版本不完全兼容，让它基于最新文档生成更稳。
![](img/zhuanqian_1d01c13ff1c6efdce4eceac7a1621273.png)
1. 连续几次生成不满意，就新开一个对话 Cmd+L，先让它重新通读代码库 @Codebase。
1. Cmd+L 新开对话，Cmd+Shift+L 把选中内容丢进已有对话，灵活切换。
1. 对话有上下文，如果想保留就用 Cmd+Shift+L 续上；如果人工改动了变量名之类，想避免它把改动改回去，就新开对话换上下文。
1. 要跨文件操作，就在对话里 @ 多个文件一起问，它能串联上下文，对服务端支撑业务代码特别有用。
1. 生成界面类代码时，让它参考和模仿已有产品，质量会高很多。
## 过程中踩到的坑
* Paddle OCR 配环境很折腾，配好也麻烦，自定义更头疼，好在最后跑通了。
* 聊天截图的 OCR 解析比预期复杂，目前只稳定支持微信白天夜晚两种主题。
* 大模型选择
* AI-1. 我分别测了国产、海外、本地模型，最后暂时落地 Kimi，本地 Ollama 的千问2 也调通了。
* AI-2. 推理模式会让回复质量明显提升，但现在能用的基本只有 ChatGPT4+ 和 Claude，成本太高暂时放弃。
在模型测试上发现，如果把识别后的散乱内容直接丢给 Claude 3.5 或 ChatGPT4+，它能轻松分辨对话主体和意图，甚至不用复杂提示词。国产模型和开源模型如 Llama3.1:8B、qwen2:7b 则表现较差，需要大量提示工程。综合成本和多 Agent 的规划，我先用 Kimi 过渡。长远看还是要做领域微调，中文以千问2 为基座，英文以 Llama3.1 为基座。
# 上线后的感受
这东西现在很粗糙，功能残缺，AI 味也重，但我还是先把它放出去了。小范围投放后定向聊了几个潜在用户，很快就收到了反馈和明确的需求方向，甚至在一些细分场景里出现了付费意向。
推广节奏上我打算先完善再放大。
### 下一步怎么想
我其实有非常多的行业细分想法，但决定先抄。Rizz 的价值在于需求被验证，也在于交互被验证。先把它的优点和同类产品的优点抄过来跑通，再谈创新。
下一步还想兼容 WhatsApp 等海外主流聊天工具，做全英文多语言版本。
