# 把 Git Worktree 当成“实习生小隔间”，我是怎么做到并行无干扰开发的
大家好，我是大铭。今天不聊具体的技术点，我们聊聊开发者的通病：被不断打断。
你是不是也有这种体会？白天被需求评审、线上 Bug、IDE 提示、IM 消息轮番轰炸，感觉自己一直在飞，晚上复盘才发现真正进入状态、能产出成体系成果的时间少得可怜。我们最稀缺的“心流”，就这样被敲成了碎片。
而 AI 编程工具的普及，又给我们加了新一层隐形干扰。
# 最让人难受的就是那 30 到 90 秒的等待
用 AI 写代码的场景大家都熟悉：你把任务丢出去，它去跑，然后几十秒到一分钟后才回来反馈。
这个时间段很尴尬。
它不短到让你立刻再发一条指令，也不够长到让你去干点别的正事。你只能盯着屏幕干等，心流被硬生生掐断，体验极其消耗人。
我当时就想，能不能把这个等待窗口故意拉大？把一个任务做得足够完整、足够长，让它能独立在后台跑起来，而不是一问一答地盯着。
思路一转，这不就是“招实习生”的感觉吗。
# 我的实习生式并行工作法
核心逻辑很简单：先把待办清单梳理清楚，然后把任务分派出去，让它们各自在后台闷头跑。
当你能做到这一点，单次任务的生命周期就会变长。你就相当于有了一个在 Background 里默默工作的“小助手”。
一个跑起来了，你再启动第二个，第二个收尾后再启动第三个。任务拆分得越细、指令越明确，跑得越顺手。我自己结合 Local Issues、RR / PLAN / Agent 的思路来做任务编排和驱动，效果还不错。

# 解决“多个人一起改代码打架”的办法
一口气开多个任务，最怕的就是代码冲突。尤其是项目越复杂，分支交叉越容易互相污染。
我现在用的最省事的方案是 git worktree。
它的原理就是在本地给同一个代码仓库，多复制出几个独立的工作目录。每个目录都基于一个干净的版本和独立的分支，互不干扰。
相当于给每个实习生都配一个独立办公室，随便折腾都不会砸到别人的桌子。然后你就可以在每个隔间里用 Cloud Code 之类的工具安心推进。
## 具体是怎么建的
假设我当前在 aimemocards-main 主目录里
```
/PATH_TO_CONTAINER/aimemocards/
```
在仓库里执行
```
git worktree add -b feature/lading-page ../aimemocards-landing-page develop
```
*   -b feature/lading-page 指定新建分支的名字
*   ../aimemocards-landing-page 指定新工作目录的名字和位置
```
/PATH_TO_CONTAINER/aimemocards-landing-page/
```
*   develop 新分支是基于 develop 分支创建的
执行完你就得到一个只属于 landing-page 的专属工作目录。
cd ../aimemocards-landing-page/ 进入后开始干活，完全不用担心影响主目录和其他任务。

### 任务收尾时
```
git worktree remove ../aimemocards-landing-page
```
# 实习生的交付物，我让他们自己提 PR
实习生在小隔间里干活，如何让它持续且准确地产出，这里篇幅另说。我们就先假设它干完了。
这时候别急着合并回来。
更推荐的做法是让它自己给你提一个 PR。
看起来多了一步，实则有两个关键价值：
1.  留痕。PR 里完整记录了这次改动、思考路径和解决过程，以后追溯非常清晰。
2.  复盘。它逼你从开发者视角切换到评审者视角，像个旁观者一样审视自己的产出，这个复盘环节对质量提升极大。
# 换个模式，感觉完全不一样
用这种做法我试过三开四开并行推进多个需求，整体顺滑很多。
本质上是把过去“实时反馈、实时处理”的同步模式，换成了“异步分派、集中复盘”的模式。
当然，前提是你的整体思路要先理清，任务必须拆得合理。想清楚了再开工，效果很可观。
它让你从一个被任务追着跑的执行者，变成一个冷静分配资源的指挥者。
# 也不是十全十美
这种隔离是代码层面的，数据库、Redis、配置文件这些共享资源还是没完全隔开，可能出现互相抢占的情况。
如果想要绝对隔离，用 Docker 做环境级隔离更彻底。
在“小隔间式隔离”和“真容器隔离”之间，可以按需选择。对我而言，worktree 的小隔间已经足够好用。
