# 不懂代码的人，如何让 Claude 乖乖听指挥？我把指令拆成了“短参数”

> 原文来自飞书公开文档，这里只作经验转述。

## 先说几句

我是李拜日，一个在产品岗上摸爬多年、目前待业的普通人。在生财这个社群里，我属于常年潜水、发言不多的小透明。第一次发帖，文笔不好，先请大家多包涵。

这篇东西我犹豫了很久才动笔。总担心自己知道的那点东西，在别人眼里只是常识，写出来帮不上忙。但纠结归纠结，磨磨蹭蹭一周，还是把它写完了。

起因是前两天看到一位前辈分享关于“AI指令设计”的帖子，一下把我看兴奋了。我赶紧顺着网线查了一圈，发现这背后要补的东西太多了：算法、调参、术语……对我来说，每一门都能劝退。

作为一个写不了代码的人，我过去攒下的那点技术皮毛，根本撑不起“AI指令设计师”这个名头。

当时我太太站在旁边问：“难吗？”

我说：“难。”

但等周末心静下来，我把社区里的精华帖一篇篇翻过去，慢慢竟也理出了一点头绪。我顺手把这些想法记进文档，日积月累，一份“用对话驯服 Claude”的笔记初稿就这样长了出来。

笔记还需要继续打磨。不过今天想聊的这套“短参数指令法”，是最近几天我反复验证过、确实能打的技巧，也很可能成为整套笔记最底层的支柱之一。

## 一、什么叫“短参数指令法”

说白了，就是用尽量短的斜杠参数，替换掉又长又啰嗦的自然语言，把我们想表达的意思压缩成 AI 更容易消化的格式。

名字是我自己起的，图个好记。

### 这个灵感从哪来

Claude 2 刚上线那会儿，我整理过它的一些内置参数，顺手发了一条帖子分享。几次用下来，发现这些参数是真的好用：写文章、答问答，输出质量都很稳。

我就忍不住琢磨：这些参数能不能组合起来用？

这时候，我想起以前共事过的开发同事。他们聊需求时，特别爱给我看代码。一开始我两眼一黑，后来慢慢才看懂：代码本质上就是“参数 + 逻辑控制”。就比如一条建表语句，说白了只是在告诉程序：表叫什么名字，有哪些列，每列用什么类型。```
create table employee (name1 varchar(20),age int)
```

如果用普通方式让 Claude 或 ChatGPT 做一个建表任务，很多人会写：“请你扮演一位编程专家，你擅长……当我说开始时，你就进入角色……现在请创建一张表，用来管理员工，有一列是名字，限制20字符，有一列是年龄，类型是int……”

而短参数指令只需要列出最核心的字段，干净、直接，不绕弯子。

### 为什么能生效

大模型生成内容，是一个词一个词往外“接龙”的。它先把你给的描述拆成关键要素，再拿这些要素作为起点去续写。描述越糊，起跑线就越歪，后面自然越跑越偏。

打个比方：

万众一心 → 心心相印 → 印贼作父 → 父相伤害 → 各自下线

这就是接龙接歪的画面。

Claude 背后的处理逻辑也类似：先拆解输入、抓取要素，再查语义、做关联，最后按逻辑生成输出。所以输入越接近结构化参数，它就越不容易“跑飞”。

### 不是 Claude 独有

这套玩法并不是 Claude 的专利。早前在写作训练营里，有人分享过一条带 model、prompt、temperature、max tokens 等字段的生成指令，很多人用过都说好。可见这种“字段化”思路是通用的。

区别在于，Claude 对短参数更友好，也更适合没有代码背景的普通用户。

Claude 可以自定义的参数非常多，题材、结构、语气、篇幅、输出载体，都可以用斜杠参数控制。组合词用下划线连起来就行，比如“/based_on_part 1”表示“基于第1部分续写”。这种做法其实是在模拟数据库里的字段命名：体重最轻记作 min_weight，最重记作 max_weight。模型看到这种结构，理解起来反而更轻松。

## 二、三个实际场景

我挑了三件事来试水：写短篇、拟标题、生成配图。

为什么是这三样？AI 画图是我第一个玩上瘾的爱好，虽然没赚到什么钱，但从去年年底刷到现在，确实开心。写短篇是因为之前我分享过用 Claude 拆解情感类素材的方法，当时整理出来的语料池长这样：![](img/b01df252790f032e84623597e852411a.png)

今天的实战，就从这个语料池出发，先做“写正文”，再顺手把标题和配图思路一起带过。

## 场景一：用短参数生成情感短篇

先随机拼一条语料作为选题：

- 主角 51 岁
- 想让 35 岁的儿子赶快娶妻
- 可笑的是，儿子相中的姑娘竟是自己的亲闺女
- 原来姑娘的妈妈就是主角当年的初恋
- 最后婚礼没办成，两家人陷入悲伤

以前我的笨办法是：先把故事梗概自己编出来，丢给 Claude，再附上各种限制条件。结果它经常把后面的情节提前抖出来。为了控制节奏，我只能一段一段喂，每段还要写一百多字的要求。一篇感情稿下来，少说 40 分钟，要是赶上 Claude 状态不佳，时间更没底。一天更新五篇的话，人都快废了。

### 试一次整体生成

为了省事，先不单独训练风格，直接用名家的文风来压场。

请求参数如下：

/theme 主角51岁，想让年长的儿子赶紧娶媳妇。可笑的是，他发现儿子找的姑娘竟是自己亲生女儿，原来姑娘的母亲是自己的初恋。最后婚礼没办成，两家陷入悲伤

/first_person
/style 模仿张爱玲
/genre 散文
/author 本文作者：李拜日（普通用户）
/gender male
/vocabulary 用词文学化

请根据以上参数，写一篇情感故事。

几个字段各自负责什么？

- /genre 和 /theme：先把体裁和主题框死
- /style：指定模仿对象，固定语言方向
- /first_person：固定叙述视角
- /author：防止 Claude 误以为自己就是张爱玲，让它清楚自己只是在模仿
- /gender：给定叙述者性别
- /vocabulary：控制文笔质感

可以看到，这篇偏文言风，不太符合时下大众阅读口味，字数也不够。解决办法有两个：一是追加字数限制参数，二是分段生成。分段更灵活，我试了试。

### 分段生成第一段：开头

这次把风格换成模仿莫言。

请求参数：

/theme 主角51岁，想让年长的儿子赶紧娶媳妇。可笑的是，他发现儿子找的姑娘竟是自己亲生女儿，原来姑娘的母亲是自己的初恋。最后婚礼没办成，两家陷入悲伤

/part1_theme 主角51岁
/paragraph_total 2
/style 模仿莫言
/genre 散文
/author 本文作者：李拜日（普通用户）
/memoir
/emotion 追忆，痛苦，懊悔
/conflict
/foreshadowing
/length 200字
/output part1_theme

请根据以上参数，写一篇200字的情感故事第一部分。

这里多解释几句：/part1_theme 告诉模型先处理素材里的第一行；/paragraph_total 用来控制段落数；/memoir 是回忆录气质；/emotion 给定情绪基调；/conflict 制造冲突；/foreshadowing 埋下伏笔；/length 控制字数。

这个开头已经相当能打了。即便不润色，直接发出去，也不输很多看起来不错的爆款开头。

### 分段生成第二段：催婚冲突

请求参数：

/part2_theme 主角35岁的儿子迟迟不成家，老父亲着急上火

/based_on_part 1
/style 模仿莫言
/genre 散文
/author 本文作者：李拜日（普通用户）
/emotion 烦闷，纠结，担忧
/action 争吵
/logic 自然衔接上一段
/length 300字
/output part2_theme

请根据以上参数，写一篇300字的情感故事第二部分。

这段逻辑很简单：/part2_theme 对应素材第二行；/based_on_part 1 表示在第一段基础上续写；/action 设计的是“父亲催促、儿子顶嘴”的争吵画面；/logic 负责让上下文不漏缝。

当时得到的片段是一段很生活化的父子对话：父亲动之以情、晓之以理，儿子嬉皮笑脸，最后父亲一拳砸在桌上，气呼呼地吼了一句：“去给我娶媳妇！”整体衔接自然，情绪也对。

### 分段生成第三段：反转

请求参数：

/part3_theme 可笑的是，儿子要娶的姑娘竟然是自己的亲女儿

/based_on_part 1,2
/style 模仿莫言
/genre 散文
/author 本文作者：李拜日（普通用户）
/emotion 震惊，慌乱，迷茫
/logic 自然衔接
/conflict 强化故事冲突

到这里，故事已经被推到悬崖边上。后面你还可以继续加 /climax 设定爆点，或 /resolution 安排结局，也可以直接让 Claude 自由发挥。

## 场景二：用短参数拟标题

做法和写正文一样。把主题、关键词、情绪、数量拆成参数丢过去，例如：

/topic 父子与旧情
/tone 反转，扎心
/count 8
/format 短句，悬念感

它通常会给出一组风格差异明显的标题备选，比干巴巴说一句“帮我想几个标题”要靠谱得多。

## 场景三：辅助 Midjourney 生成配图

这也是同一套思路。把画面里的主体、风格、光线、景别全部拆成短参数，再交给 Midjourney。比如：

/subject 雨中行走的人
/style 油画
/light 黄昏
/shot 远景

我现在还在实验阶段，具体参数组合就不放出来了，等玩熟了再单独分享。

## 写在最后

“短参数指令法”不是什么黑科技，它只是把我们对 AI 的需求从“长篇大论”变成“精准字段”。你给的信息越干净，它回你的内容就越稳定。真正要花心思的，是慢慢打磨出一套属于自己的参数组合。

希望这篇小文能给你一点启发。也祝我们每个人在内容创作的航程上，都能少走弯路，多留点时间给自己。

原以为事情已经定局，谁知老天偏要掀起波澜。

前些日子，张山领回一个女孩子，满脸喜色地说要娶她。我粗粗看去，只觉姑娘安安静静的，心里反倒宽慰——这小子总算开了窍。

订婚宴那日，宾客散尽，我才得空细细端详。大红喜服穿在身上，衬得她比三月的桃花还要鲜妍。姑娘冲我含笑欠身，就在那一瞬，我定在原地：那双眼睛，那枚唇角弯起的弧度，活脱脱是把少年时代那段旧情重新拓印到了面前。我的心猛地一沉，汗意顺着后背漫开——世上怎可能有如此雷同的两张面孔？

事后我绕着弯子探问她的来历，问到的结果像一记闷棍：她生母竟是我昔年的恋人刘英。相传刘英当年怀有身孕时被人拐往异乡，生下这孩子后便再无音讯。那一刻我方明白，苍天早已悄然布好罗网——张山满心欢喜要迎娶的，竟是我与旧日恋人所生的骨肉。

霎时间眼前发黑，我扶着桌角才没有栽倒。若任凭这婚礼照办，张山岂不是要娶了自己同父的妹妹？这伦理深渊，教我如何跨得过去？

那一夜，我枯坐在堂屋里，灯芯哔剥作响。这婚事若成，等于亲手把两个孩子推入火坑；若散，又不忍看他们眼里仅剩的光亮就此熄灭。我甚至隐隐害怕，刘英若还在世间，得知女儿险些嫁进自家门，该是怎样一番撕心裂肺。窗外的风摇乱柳影，正如我翻腾不止的念头——造化弄人，何至于斯。

## 为何注册后仍反复要求校验

很多人以为一次注册成功就彻底安稳了，实际上后续使用时同样会不定期弹出手机校验。

最近笔者本人就频频遇到这种情况，也在多个社群里看到同类反馈。

根本原因是操作模式触发了 Claude 的风控识别逻辑。

典型触发情形包括：

1. 网络环境切换。长期固定在某个 IP 访问，某天换了地点或连上了陌生的网络，系统就会判定异常并要求再次验证。
2. 登录终端变更。平时习惯在桌面端操作，忽然改用移动端登录，也容易被判定为风险行为。

以笔者近期的使用节奏举例：清晨习惯用手机打开，上班后切到电脑，有时外出会接入公共移动网络。这样频繁变动下来，一天之内被要求校验三四次是常态。

更稳妥的做法是尽量保持网络与设备的一致性。如果确实需要多场景使用，建议多准备几个账号，做到设备与网络一一对应，避免交叉使用。

## 唤醒与边界探测

浏览各路大神的分享时，你会注意到他们经常会在开头先抛一个确认：“XXX，你清楚XX吗？”

这并非凑字数。

以 Midjourney 为例。有些对话里，Claude 对 Midjourney 的原理、参数、风格都能娓娓道来，看起来无所不知。

于是有人会另开一个新会话，直接命令：“Claude，给我十条 Midjourney 的风景提示词。”

结果对方回：“抱歉，我是 Anthropic 推出的一款 AI 助手，对 Midjourney 并不了解……”

瞬间就觉得被打脸。

其实模型的潜台词是：我没有上下文，你抛出的术语我无法关联。

所以在开启正式任务前，先把共同语境锚定好至关重要。

这就好比在电商平台找客服。

假设有人想买一袋辣椒面，想确认辣度以及是否适合烧烤。他一上来就问：“你家辣椒面好用吗？”

客服会懵：到底是想问辣感强度？还是想问耐放、是否易碎？是内吃还是外调？

信息不清晰时，客服只能搬出标准话术：“亲，我们的辣椒面为 XXX，具备 XXX 特性……”

是不是似曾相识？
