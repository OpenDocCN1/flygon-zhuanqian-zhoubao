# 用半年实战检验AI编程：从鸭霸单词到复杂项目的通关笔记
作者：龙哥

半年前我踏进了AI编程的实战坑，现在想以一个非技术创造者的身份，把这段经历摊开讲讲。没有高深的术语讲解，只想说清楚当面对一个真实、复杂的项目时，我到底是怎么思考、怎么拆解、又怎么用AI把事情推进下去的。

这场复盘既是给自己的一次复盘，也是对鸭霸单词App近期大版本AI编程迭代的回望。如果你也在用AI做单产品的深度打磨，或是同时琢磨多个项目的并行管理，希望这里面的思路能帮你少走弯路。

# 从实践里长出来的AI工作方法

**用AI重塑素材产线**

在设计环节，我现在基本走的是AI驱动的素材制作路径。图片风格统一、数据整理、离线配置管理，这些过去要花大量手工时间的工作，现在都能被串起来。Mid Journey、Stable Diffusion这类工具我也会用，但对独立创造者来说，选工具的核心标准不是多专业，而是够高效、够好上手。

我常推一个叫Request的在线生产工具。它不用装客户端就能用，免费且操作直接。官方自带风格预设，叠加自定义风格就能做出符合品牌调性的图。需要系列图时，一组提示就能批量出图，几十秒内就能拿到可用素材。

生成风格化的图其实有套小习惯。先选PNG或JPG格式，找参考图到📕这类平台攒灵感，然后在Request里建自定义风格，填好分类和提示词，多测几版再收入自己的风格库。AI做的是风格生成而非精修，离预期有差距就微调提示词，而不是反复抠像素。

在鸭霸单词的迭代里，Request和Figma配合得挺顺。统一风格的配图提高了效率，数据处理上则靠AI编程批量产出结构化单词书数据，解决了学习成本高、不同来源数据格式不统一的问题。交叉验证是保证准确率的关键。

数据处理我总结为一条链路：找数据源、清洗、核对、写脚本、修复。GitHub上能挖到不少公开源，用Python脚本先跑一遍，遇到格式混乱就让AI编程去补齐规则，最后再跑一遍校验脚本把错误捞出来。批量化核对比手工快得多，也更稳。

批量生成结构化数据的思路其实可以搬家。单词书的逻辑放到日志预设、功能模板上都适用，核心是先统一格式和字段规范，多和做过的人交流共识再开工。

**离线数据怎么存才靠谱**

AI编程把技术门槛压得很低，但数据怎么放、怎么同步，依然是必须想清楚的事。粗略分两类：核心数据，量大但管理相对简单；结构化数据，信息丰富、需要跨设备同步。

临时数据有两种常见做法：一种轻量但不支持iCloud同步，适合小量缓存；另一种像本地数据库，能做跨设备同步。我目前的App都还没接服务端，前期更关注快速交付用户价值，等场景成熟再考虑网站类项目的服务端对接。

**组件化才是规模化的关键**

做久了会发现，提效的本质是复用。组件化思维说白了就是把功能模块化。支付、充值、设置页，这些通用能力做成独立单元，下一个项目直接搬过去改参数就行。这样规范更好建立，AI生成的失误率也会下降。

我的组件化实践从复用开始：红包支付、余额充值、多语言资源、数据模型都打包起来。配上配置文件，不同项目里一键适配。组件说明文档很重要，既是给自己看的逻辑地图，也是给AI的说明书。复制到新项目时，文档能指引AI怎么接、怎么改。

很多人觉得组件化很高深，其实就是“能抄作业的版本”。做一个日志类App，第二款直接复制第一款的基础代码，只做场景化微调，重复劳动大幅减少。新App第一版就尽量把功能组件化，界面元素也做组件化，比如弹窗、导航栏。功能组件解决“能做什么”，界面组件解决“长什么样”。

关于开源，我的想法是先小范围开放部分支付类组件让大家试用。最终目标是让更多人能用AI编程做产品。像新手引导模块，就是可配置的组件，换文字、换动画就能放到不同产品里，提升质感。

算法组件也值得单独提：一个文件里定好输入输出，内部逻辑封装起来。复用性高、一致性强，也少出bug。视觉统一类产品里，主题配色组件能让整套界面迅速统一。

在设计上我也很在意风格统一和配色。把支付流程抽象成组件后，在多个项目里反复使用，省心很多。另外一个小习惯是让AI生成预览数据和模拟数据，测试更快，分享截图也更清晰。

**和AI打交道的小技巧**

复杂问题往往跨模块。我的做法是让AI先梳理文档，把项目脉络捋清楚，弥补非技术人员对代码细节的盲区。排查问题时，把操作步骤直接标注在图上，和AI对话更顺。

构造虚假测试数据、做预览环境，都是降低沟通成本的好办法。AI编程不是全自动驾驶，还需要人盯着。规划任务时，先让AI出一份文档，再按文档落地，执行感会强很多。

整体来看，AI更像一把放大器：思路清晰的人做得更快，思路模糊的人会更乱。项目实践加同行交流，才是把AI用熟的正路。期待下一次茶话会，我们能带更多真实案例来聊。
