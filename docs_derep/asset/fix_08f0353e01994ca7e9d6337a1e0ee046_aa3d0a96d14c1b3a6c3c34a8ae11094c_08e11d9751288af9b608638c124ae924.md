# 开场

大家好，我是伍拾陆，半路出家、代码零基础的普通人。

从去年 7 月加入外卖 CPS 小型航海至今，我一直深耕 CPS，也积累了一批复购用户。上篇我提到想把 CPS 放大，起初设想过做账号矩阵、做私域沉淀、跨平台分发。但实践下来发现，这类打法并不适合我：**流量来源和成交始终被平台掌控，我缺一个真正属于自己的承接载体。** 5 月在 AI 大航海学习到 AI 编程后，我尝试换条路——用 AI 自建小程序。

这是我第一次把一个想法从零做到可上线的完整产品。

6 月下旬到 7 月中旬，我借助 Codex 全流程开发并发布了两款微信小程序：

一款是基于生财中标信息做的倒班人群找同休排班工具；另一款是围绕自身 CPS 业务做的优惠券汇总工具。

从需求梳理、原型构思、功能编码，到自测、提交审核、正式上线，全部都是边学边做。

作为一个不写代码的人，这次最大的收获不是上线了两款产品，而是验证了一个判断：普通人配合 AI，能把一个模糊念头快速变成可用的线上服务。本文就用纯小白视角，复盘从 0 到 1 的全过程。

全文分四段：先讲为何用小程序做放大，再给一套可复制的 SOP，随后复盘两个项目的坑，最后总结给同路人的建议。

## 第一部分：为什么我选择小程序来做放大

### 一、我想要的不是多开账号，而是一个可控的流量承接口

做 CPS 时，常见的放大手段是增发内容、拓平台、分发私域，再导向成交。

这些方法有效，但对我而言痛点很明显。

其一，CPS 营销属性强，容易触发平台警告甚至封号，规则一变原有路径就失效。其二，用户每次都要翻笔记找口令、问活动，交付体验零散。其三，我做 CPS 已一年，有真实用户和持续更新的优惠，却没有一个固定的入口做沉淀。其四，我是普通人，精力、账号、资金都有限，矩阵、私域等玩法驾驭不了，求稳更重要。

[PRE1]

我在 AI 编程深海圈学习，并通过精华帖了解到小程序的玩法。小程序正好能补上承接的短板，把原本分散在短视频里的访客，整理成一条稳定导向微信小程序的路径，进而放大 CPS 业务。

对我的 CPS 而言，商业链路很短：

用户准备点外卖、订住宿或出行时，打开小程序，挑选对应平台，复制当下需要的优惠口令，再到官方 App 领取即可。

### 二、首个动手项目并非 CPS，而是找同休排班

我真正先落地的第一个小程序，是找同休工具，灵感来自生财一条中标信息。

问题描述：倒班人群自己的班表难记，多人想找共同休息日，需要反复沟通。

我去看那篇笔记，评论区反馈强烈，不少人催更，也有人把场景延伸到医疗、铁路、电力、民航和酒店等行业。

后来才明白，我只验证了需求存在，却不清楚首版应该是什么样。跟随 AI 建议不断扩功能，代码越写越多，范围从双人排班扩到多人排班，又加上生日、纪念日等杂项，Bug 累积。我像无头苍蝇一样修错，一周仍未跑通基础功能，最后只能先停。

### 三、排班暂停后，我才回到 CPS 本身出发

排班项目搁置后，我翻看圈友经验帖，看到 HP 圈友写的优惠券聚合小程序分享，这才醒悟：

> 与其从零找项目，不如围绕手上一直在做的 CPS 业务，做一个更确定、能放大小流量的小程序。

这个方向具备几个确定性：用户在消费前寻找优惠是刚需，不需要培养新习惯；我手里有持续更新的活动口令，无需先做产品再找内容；口令一键复制后在官方 App 可直接识别，用户信任度高。

起初我选了短链接加口令的形态，在体验版测试时发现短链接跳转不通，于是把产品收敛为“一键复制口令，再到官方 App 领券”的形态。

更关键的是，这次我没有立刻写代码，而是先用 SPEC 方法让 AI 持续追问，把模糊的“优惠券聚合”整理成可交付的最小可用版本。

所以 CPS 小程序起步晚，却先上线。

## 第二部分：小白可照做的 SOP 手册

### 第 1 步，找需求选方向

寻找需求是产品开发的起点。需求的本质是有人愿意为之付费。

当下讲究**“需求倒推”**——**先找到用户痛点，再设计产品，最后开发。**

很多人起步时不清楚要做怎样的小程序。

这时可以借用小排老师的产品自查四问：

- 什么人？
- 什么情境？
- 愿意付多少？
- 解决什么问题？

若仍无方向，可去看生财的中标与风向标，里面常有可做成小程序的需求。

**我第一个小程序的灵感就来自生财中标。** 日常刷小红书时，也可留意评论多的笔记，最好是近一周或一月内发布的。

找到笔记后，可用 Chrome 浏览器的“社媒助手”插件批量抓取评论，建议用小号登录，抓取后交给 AI 分析评论区的抱怨点和痛点，从而确定方向。其他做法还有：

1. 发一篇小红书笔记直接描述场景和痛点；
2. 在目标用户群里提问；
3. 翻同类产品的差评、评论和求助帖；

#### 第 2 步，先定定位，再划边界，最后定 MVP

- **产品定位**：明确要解决谁的什么问题；
- **边界**：划定范围，哪些功能不做、哪些场景不覆盖；
- **MVP**：在定位和边界内，挑出最小可验证版本。

需求初步验证后，用 SPEC 方法整理完整需求，划定边界，避免开发时像无头苍蝇一样碰壁。

**下面是 AI 编程深海圈学到的 SPEC 提问模板 我有一个需求，想跟你说一下。但在写一行代码之前，我希望你扮演一个极度认真、稍微有点偏执的产品经理。**

你的任务不是写代码，也不是给我方案。

你的任务是，像苏格拉底一样追问我，直到把我下面这些藏起来的东西全挖出来：

我没想清楚的隐含假设（我以为不言自明、但其实没说的事）；我没想清楚的边界（出错怎么办、空数据怎么办、撤销怎么办）；我可能在偷懒（把“随便实现一下”当成“已经想清楚”）；我可能在自欺（把“我想要”当成“用户想要”）。

请每次只问一个问题，问到第 N 个问题之后，你认为问得差不多了，再帮我总结成一份完整的需求文档。

下面是我的初始想法，你开始问吧：

这里的 N 不一定要填具体数字，它代表的是**“持续追问，直到问清楚为止”——具体要问清楚四件事：用户是谁、边界在哪、不做清单有哪些、验收标准是什么。** 我开发 CPS 小程序之前，用这套 SPEC 提问让 AI 连续追问了我一百多个问题，其中很多是我自己根本没注意到的点。所以重点不在于问了多少轮，而在于知道第一版小程序该做成什么样。

需求彻底明确后，再开始动手。

#### 第 3 步，微信小程序开发

##### 1. 小白词典

**AppID**：该小程序的身份编号。

**微信开发者工具**：用于创建、编译、预览和上传小程序代码的工具。

**Codex**：能读取项目文件、修改代码并运行检查的 AI 编程工具。小程序开发耗 token 较多，有条件建议开 Pro，Plus 会卡。

**Git**：给代码留下可回退版本的工具。若暂时不会用，至少先备份完整项目。

**CloudBase**：为小程序提供云数据库、云函数和文件存储的后端服务。

**云函数**：运行在云端的代码，适合处理权限、数据校验和不应放在前端的操作。

##### 2. 动工前需准备

1. 微信小程序账号及对应 AppID；
2. 微信开发者工具；
3. Codex 或其他能读取项目文件的 AI 编程工具；
4. 一个独立的项目文件夹；
5. 已确认的 SPEC 与不做清单；
6. Git 版本记录或至少一份可恢复备份；
7. 真实测试样本、测试微信账号和测试手机；
8. 完成账号与本地项目准备；CloudBase 环境是否创建，视数据是否需要跨设备共享再决定。

##### 5. 流程概览

1. 先在微信公众平台按当前官方指引注册小程序账号，确认主体、服务类目和计划使用的能力是否允许发布，再取得 AppID。
2. 安装微信开发者工具，用自己的微信登录，新建空白小程序项目，并确认可正常编译预览。
3. 代码要放在单独目录，不要让 AI 在空目录假装已读取不存在的配置文件。若目录为空，先让开发者工具生成基础结构。
4. 接着把已确认的需求文档放入项目目录，让 Codex 只做只读检查，明确指出缺失的文件，而非一打开目录就大改。
5. 确认项目入口、页面目录和云端配置后，建立首次 Git 记录或完整备份，最后再进入功能开发。
6. 每完成一步都保存结果，不把账号注册、环境配置和写功能混在同一轮。

**验收标准**

微信开发者工具能正常打开和编译项目；SPEC 已放入项目；知道报错在哪查看；当前版本有可回退基线；前端没有 AppSecret、云 API 密钥或其他管理凭据。

**避坑提示**

不要把 AppID、云环境 ID 和管理密钥混在一起。AppID 用于识别小程序，密钥用于更高权限，不能因 AI 说要“帮我配置”就把密钥写进前端。

##### 6. 命名、备案与认证

**发布流程**

[PRE11]

- 写代码前，先把命名、备案、认证确定好，再开始也不迟。
- 微信认证需提交 30 元费用。
- 小程序信息、类目、备案需与认证内容完全一致。
- **特别注意：先认证再备案。** 若先备案后认证未通过，需重新提交备案审核，会浪费数天。
- 我起初按官方流程从上到下，先备案后认证，结果信息不一致，认证需改备案重审，共提交两次审核，耗时 6 天。
- **每个小程序因功能不同，审核时长也有差异。** 我做的找同休小程序一次审核约 3 天。
- 审核人员一般在工作日上班，建议周一或周二提交，若周五提交会拖。

##### 7. 不懂就问 AI

我是非科班出身，开发时很多代码和流程都不懂。我都是截图直接问 AI 这段代码作用、下一步做什么、报错如何解决，Codex 可直接处理。

用 Codex 开发小程序时，推理模型不必一直开最高，极高容易过度规划，做很多无用功。小程序代码并不复杂，平时推理模型在 5.6 级时用中或高即可，个别情况才用极高，省 token 的同时提速。

#### 第 4 步，多人跨设备功能需先确定真相源

真相源：就是在一份数据上，所有人都认它说了算。

做多人或跨设备功能，第一件事是确定哪份数据是真相源。数据可分三类：

第一类，仅自己查看的临时数据，如草稿、页面偏好，放本地即可。

第二类，多人多设备需看到的数据，如小组、成员、班表，必须放云端，大家都认同一份。

第三类，来自第三方平台的数据，如优惠是否成交，不能由小程序自己说了算。

云端失败时要明确提示失败，不能偷偷伪造“看起来创建成功”的结果。

另有一点易被忽略：记录的动作要与真实动作对应。点击不等于复制，复制不等于领券，页面打开不等于成交。只记录自己能观察到的那一步。

做多用户产品还要想清楚身份区分。第一版不做账号密码登录，不等于不需要区分用户。小组成员、班表和权限都要能绑定到一个稳定身份。

**验收标准**

明确每类数据存在位置、谁可读写、失败时怎么办。多人场景下，设备 A 写入后，设备 B 在有权限时能读取。

#### 第 5 步，建立逻辑地图，每轮给 AI 执行指标

每轮开发前，让 Codex 先回答四个问题：改什么；影响哪里；不能动什么；怎么验证。

“逻辑地图”开发法，是在写代码前先把“这个功能是什么、用户怎么用、系统怎么跑、数据放哪、规则是什么、怎么验收”梳理清楚。这是郭东超老师在深海圈直播时分享的技巧。

例如做“创建任务”功能。

普通做法：想到哪写到哪，先做页面，再补接口，最后才发现漏了校验和测试。

逻辑地图做法会先拆解：

- 它属于什么能力？——任务管理
- 出现在哪个页面？——任务列表页
- 用户点哪个按钮？——创建任务按钮
- 用户做了什么？——填写任务并提交
- 系统完整怎么处理？——校验内容、调用接口、保存数据、刷新列表
- 调用了什么接口？——创建任务接口
- 保存了什么数据？——任务记录与列表缓存
- 哪些规则不能破坏？——任务标题不能为空
- 怎么确认没问题？——测试空标题、正常创建、列表刷新

这样功能就变成一张可追踪的地图，而非一堆代码。

再用“修路”比喻：

- CAP 是目标能力
- PAGE 是页面
- UI 是上车点
- ACT 是用户动作
- FLOW 是业务流程
- API、STORE、RULE、TEST 是配套设施

前五个是主路线，后四个是配套。只画路线不看配套，路可能走不通；只写代码不看地图，功能易漏。

其最大价值，是让每个功能都能回答九个问题：做什么？在哪做？点什么？谁来做？怎么流转？调什么接口？存什么数据？哪些规则不可破？怎么验证？

开发前，还要先回答四个问题：改什么？影响哪里？不能动什么？怎么验证？

这不是为了把文档写复杂，而是让开发少靠猜。人能看懂地图，AI 也能按图改代码。

##### 验收标准

Codex 能说清本轮改了什么、影响了哪里，需求与代码一致，能单独回退这一轮。

##### 避坑提示

不要用“还有什么可以优化”“帮我全面检查”这类无停止条件的指令，AI 会按自身想法越改越多，token 消耗也会剧增。
