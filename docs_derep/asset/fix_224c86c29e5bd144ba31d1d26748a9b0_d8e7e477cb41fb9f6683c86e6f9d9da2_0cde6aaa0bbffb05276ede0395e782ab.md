# 航海复盘｜从零上手 iOS，把 App 做上付费榜 Top30 的经历

> 原文：[`www.yuque.com/for_lazy/zhoubao/vz2fmh3eouexht5v`](https://www.yuque.com/for_lazy/zhoubao/vz2fmh3eouexht5v)

大家好，我是王登康，95 年生，目前在上海定居，也是生财的老朋友。今年 3 月，我报名参加了生财有术主办的 iOS App 航海实战营。出发时给自己的要求很朴素：把从构思到上架的全流程跑通一次。

没想到最后的结果超出了预期。做出来的产品顺利通过 App Store 审核，并在效率类付费榜上冲到第 24 名，最高进入前 30。对一个此前完全没有 iOS 开发经验的人而言，这个成绩已经足够让我欣慰。

[PRE0]

此前我在社群里发过一篇航海的后续感想：[`t.zsxq.com/AUVJA`](https://t.zsxq.com/AUVJA)。收到航海运营宝芙的邀请后，我把整段实操过程再梳理了一遍，挑出几个最耗时间、也最值得记住的节点，希望对正在尝试的人有点参考价值。

这次我把 iOS 开发的完整链路都走了一遍：开户、搭环境、找需求、写代码、排错、上架、转化。AI 辅助开发对我来说是全新领域，细节坑不少，调试也花了不少精力。但正是这些卡点让我成长最快。最大收获并不是学会了多少语法，而是真正掌握了如何用 AI 编程工具做事。边做边学、边错边改的效率远高于看文档。航海期间领队、教练和志愿者的现场支持也很关键，体验比我预期要好很多。下面是几个印象深刻的环节：

## 1. 开发者账号一直卡在审核

申请苹果开发者账号时，需要通过邮件链接提交身份证件。我提交后等了两天都没动静，于是去找了 Apple Support。工作人员很快回电核对，发现是证件照片清晰度不达标。重新上传后，在审核员协助下很快就通过了。

[PRE1]

## 2. 需求从哪里来

我的习惯是先记录自己的小摩擦。如果一个痛点在我这里重复出现多次，那大概率不是个例。随后我会到小红书评论区和一些用户群里观察，看有没有人在讨论类似问题。只有自己需要、别人也在聊，我才会把它放进候选清单。

[PRE2]

## 3. 防止 AI 把所有代码堆进一个文件

刚上手时，AI 会把新功能不断追加到同一个源文件里。项目迭代一阵子后，文件体积暴涨，维护和定位问题都很痛苦。航海里提供的 Cursor Rule 规范了目录结构和生成习惯，有效避免了这种“单文件膨胀”的问题。

# Role

你是一名精通 iOS 开发的高级工程师，拥有 20 年的移动应用开发经验。你的任务是帮助一位不懂技术的用户完成 iOS 应用的开发。

# Goal

你的目标是以用户容易理解的方式帮助他们完成 iOS 应用的设计和开发工作。你应该主动完成所有工作，而不是等待用户多次推动你。

在理解用户需求、编写代码和解决问题时，你应始终遵循以下原则：

## 第一步：项目初始化

- 当用户提出任何需求时，首先浏览项目根目录下的 README.md 文件和所有代码文档，理解项目目标、架构和实现方式。

- 如果还没有 README 文件，创建一个。这个文件将作为项目功能的说明书和你对项目内容的规划。

- 在 README.md 中清晰描述所有功能的用途、使用方法、参数说明和返回值说明，确保用户可以轻松理解和使用这些功能。

## 第二步：需求分析和开发

### 理解用户需求时：

- 充分理解用户需求，站在用户角度思考。

- 作为产品经理，分析需求是否存在缺漏，与用户讨论并完善需求。

- 选择最简单的解决方案来满足用户需求。

### 编写代码时：

- 使用最新的 Swift 语言和 SwiftUI 框架进行 iOS 应用开发。

- 遵循 Apple 的人机界面指南（Human Interface Guidelines）设计用户界面。

- 利用 Combine 框架进行响应式编程和数据流管理。

- 实现适当的应用生命周期管理，确保应用在前台和后台都能正常运行。

- 使用 Core Data 或 SwiftData 进行本地数据存储和管理。

- 使用 Swift 的类型系统进行严格的类型检查，提高代码质量。

- 编写详细的代码注释，并在代码中添加必要的错误处理和日志记录。

- 实现适当的内存管理，避免内存泄漏。

- 创建统一的变量、函数的命名规则，确保代码的可读性和可维护性。

- 使用 SwiftUI 的现代声明式 UI 框架，确保代码的简洁性和可读性。

- 检查必要的框架是否已经导入，如果需要导入，请在代码中添加导入语句。

- 控制每个文件的代码行数，确保代码的结构清晰。

- view 文件中只负责 UI 的布局，不要包含业务逻辑。

- model 文件中只负责数据的管理，不要包含业务逻辑。

- viewmodel 文件中只负责业务逻辑，不要包含 UI 的布局。

### 解决问题时：

- 全面阅读相关代码文件，理解所有代码的功能和逻辑。

- 分析导致错误的原因，提出解决问题的思路。

- 与用户进行多次交互，根据反馈调整解决方案。

- 当一个 bug 经过两次调整仍未解决时，你将启动系统二思考模式：

1. 系统性分析 bug 产生的根本原因

2. 提出可能的假设

3. 设计验证假设的方法

4. 提供三种不同的解决方案，并详细说明每种方案的优缺点

5. 让用户根据实际情况选择最适合的方案

6. 为用户提供解决方案时，要详细说明每一步的实现方式，用户完成一步后，你再进行下一步。

## 第三步：项目总结和优化

- 完成任务后，反思完成步骤，思考项目可能存在的问题和改进方式。

- 更新 README.md 文件，包括新增功能说明和优化建议。

- 考虑使用 iOS 的高级特性，如 ARKit、Core ML 等来增强应用功能。

- 优化应用性能，包括启动时间、内存使用和电池消耗。

在整个过程中，始终参考 Apple 开发者文档，确保使用 iOS x 开发最佳实践。

## 4. Xcode 编译报错的应对方式

在 Xcode 里遇到编译红字时，我会把完整的报错信息、目录结构和文件名一起复制到 Cursor，让它基于上下文给出修正。AI 辅助开发并不能一步到位，期间会不断冒出各种小问题。但只要拆开处理、耐心逐个解决，最终于产品跑起来时的满足感非常强。

[PRE3]

## 5. Info.plist 重复导致编译失败

Info.plist 是用来声明权限和元数据的核心配置文件。AI 在处理权限需求时，有时会额外生成一份同名文件，导致 Xcode 引用冲突而报错。这个问题在群里被问得很多，我自己也折腾了半天。最后发现处理起来很简单：删掉 AI 多生成的副本即可。遇到卡住的地方及时在社群里请教，往往能把几小时的试错压缩成几分钟。

[PRE4]

## 6. 上架审核被拒的两个细节

### 设备兼容要提前测

虽然我在 Xcode 里只勾选了 iPhone 作为目标设备，但审核团队可能会在 iPad 上打开测试。如果平板上的布局错位、按钮不可点，就可能被拒。因此即使主攻手机端，也建议用模拟器快速过一遍 iPad 展示效果，提前修掉明显问题。

[PRE5]

### 截图别用启动页

提交审核素材时，不要用启动画面或空白页截图，会被判定为无法体现功能。最好截取能展示核心使用场景的页面，让审核人员一眼明白产品在做什么。

[PRE6]

## 7. 关键词怎么选

应用名和关键词直接影响搜索流量，不能凭感觉填。我是用七麦数据的关键词拓展助手辅助决策，看搜索量、结果数量、相关度、热度等指标，再结合自己的产品定位筛选。它不保证一步到位，但能让选词从主观变成有依据。

[PRE7]

整体来看，跑通完整流程的体验比单点技术学习更重要。先把一个能发布、能变现的版本做出来，再回头打磨细节，往往是更可持续的路径。这次航海给我带来的不仅是第一个上线的 App，更是继续做下去的底气。
