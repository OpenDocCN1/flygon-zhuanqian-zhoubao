# 让 AI 成为真正能帮你干活的“员工”：CLI、MCP 与 Agent 搭建实战

先解释两个基础概念。

**CLI 是什么？**

CLI（Command Line Interface，命令行接口）可以理解为软件留出的“文字遥控器”。很多工具都会把功能暴露成一组可在终端中运行的命令，人能用，AI Agent 也能用。只要把命令交给 Agent，它就能代替你完成操作。

比如下面这些就是常见的 CLI 操作：[PRE0] 它们分别对应 Git 状态查询、GitHub PR 拉取、音视频格式转换以及飞书文档读取。

CLI 对 Agent 友好的原因在于：输入输出结构清晰，容易组合、可以记录、能被反复执行。只要一条命令在本机稳定运行，Agent 就可以把它当作流程中的一个环节，嵌入更长的工作链。

**MCP 又是什么？**

MCP（Model Context Protocol，模型上下文协议）在概念上更进一步：它把外部系统的能力封装成一组结构化工具，Agent 不用关心底层请求怎么写、命令怎么拼，只需按工具定义传参数、读返回值。

例如：飞书 MCP 可以提供“搜索文档”“读取表格”“创建任务”“更新任务状态”等能力；GitHub MCP 可以提供“读取仓库”“查看 PR”“获取评论”等能力。[PRE4]

对 Agent 来说，MCP 更像一个摆好的操作面板：每个按钮叫什么、需要什么参数、会返回什么，都提前定义好了。需要什么 MCP 也一样，直接让 Codex 安装即可。

如果 CLI 和 MCP 都不可用，Agent 还能通过浏览器或 computer use 插件直接操作网页。但这种方式依赖页面位置和 UI 状态，页面改版、弹窗、登录掉线都可能让流程中断。所以只要存在稳定的 CLI 或 MCP，优先用它们。[PRE5]

# 三、把日常业务做成 Agent 的核心方法

这一套八步法，最早是在包子老师的六步法基础上改的。

| 步骤 | 发生什么 | 为什么做 | 得到能力 |
| --- | --- | --- | --- |
| 第一步 | 建项目文件夹 + Git 仓库 | 所有素材放进可追踪环境 | 可审计、可回退 |
| 第二步 | 让 Agent 读背景材料 | 先理解业务再讨论方案 | 减少错误假设 |
| 第三步 | 交代目标并研究实现方式 | 先验证渠道与技术可行性 | 形成可执行方案 |
| 第四步 | 跑通最小闭环 | 用真实结果暴露隐藏需求 | 得到 MVP |
| 第五步 | 接入飞书任务控制台 | 团队协作与批量执行 | 团队协作与批量执行 |
| 第六步 | 沉淀规范、Skill、验证器 | 把对话共识固化成文件 | 流程可复用 |
| 第七步 | 当前对话再执行一次 | 验证完整生产链路 | 发现流程缺口 |
| 第八步 | 新开对话再执行一次 | 验证不依赖聊天记忆 | 证明 Agent 可重新上岗 |

## 第一步：建项目文件夹和 Git 仓库

先新建独立项目文件夹，再让 Codex 把它作为项目打开。

文件夹名称最好简短清晰，别用含义不明的临时名，建议用英文。

业务原始材料可以复制一份放进项目，原件保留。

然后让 Codex 创建 Git 仓库。用 GitHub Desktop 管理 Git 仓库。Git 会记录新增、修改和删除，GitHub Desktop 把变化可视化。

Agent 会生成大量新文件，没有版本记录的话，你很难分清哪些是原始材料、哪些是产物，也很难安全撤销错误操作。

电脑上新建一个空白文件夹。

如果有相关材料，就在项目文件夹里再建一个文件夹，把材料复制进去。想试示例的话，可以新建文件夹，把这个解压到里面。

## 第六步：固化阶段，制作 AGENTS.md、Skill.md、脚本和验证器

接下来是稳定生产阶段，这步开始才是在做 Agent。项目已经完成最小闭环，要走向稳定生产。目标是让 Agent 开展生产。你有哪些建议？有哪些能沉淀的东西？目前的工作流清晰吗？需要做 Skill 吗？

最小闭环跑通后，不要持续把对话越写越长，而是把已经确认的业务共识沉淀进项目。

一般沉淀四类文件：AGENTS.md、Skill.md、脚本、验证器。

AGENTS.md 保存全项目不可违反的原则；Skill 保存这一类任务的完整操作顺序；脚本负责稳定的数据获取和文件检查；验证器负责兜底。

[PRE18]

注意：脚本不能代替 AI 做判断。脚本只能做机械执行的工作。需要语义判断的工作要交给 AI，不能拿脚本硬编码！

为什么不能硬编码？最初跑案例时，我们很容易为了尽快拿到结果，在脚本里写临时规则：

[PRE19]

这条规则可能刚好适合当前视频，但换一个视频，作者可能说：

- “接下来按价格来讲。”
- “下面进入具体产品推荐。”
- “我们先从入门款开始。”
- 或者根本没有明显的过渡句。

如果把某个句子、行号、价格或“第几款”写死在脚本里，这段代码就只能适配少量样例。

更稳定的做法是：让 Agent 通读全文，根据上下文判断语义边界；脚本只保存 Agent 给出的判断结果，并检查产物结构是否完整。

[PRE20]

[PRE21]

这次演示特别纠正了一个危险设计：不能在脚本里硬编码某个句子、价格、行号或“第几款”来切分文章。脚本只对确定性负责，Agent 对语义负责，验证器对底线负责。

流程还规定，每次生产第一步必须静默检查 Cookie。Cookie 缺失或过期立即停止，不能先读取任务，更不能把 Cookie 输出到日志或归档。只有本地文件全部生成、验证脚本通过、Agent 复核完成后，飞书状态才允许改为“已完成”。

为什么要做？对话里的约定会随上下文消失，硬编码又只能适配一条样例。把规则、工具和验收拆开，才能同时保留确定性和语义能力。

能带来什么？Agent 获得了一份可重复使用的岗位说明书。下次用户只需说“执行任务 2”，Agent 就知道先检查什么、从哪里取任务、怎样归档、何时停止以及什么时候可以回写成功。

[PRE22]

## 第八步：新开对话再执行一次（去记忆回归测试，必做）

关闭原来的长上下文对话，在新对话里让它读一下项目文件再执行任务。

目的是验证 Agent 能否通过项目里的 AGENTS.md 和 Skill 从零开始正确工作，而不是依赖之前聊天中尚未沉淀的记忆。

如果新任务能完整执行并通过验证，说明这套能力已经从“对话中的能力/单次能力”变成“项目能力”。这也是判断一个演示是否真正具备生产潜力的重要标准。
