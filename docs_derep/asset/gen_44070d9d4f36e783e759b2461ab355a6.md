## 1 从 AI 工具到 Agent：接下来十年的主线

[PRE0]

这段时间我自己动手做的事很多：

在生财内部，我已经让几十个 AI 员工正式上岗，并且进入真实的生产链路。现在很多产出不再靠人一步步推动，而是交给 AI 去持续运行。在我的推动下，团队里大家也开始自发搭建各类 AI Agent。有的只是把原有工作的某个环节升级，有的则是对过去使用 AI 的方式彻底重构。截止到现在，团队里每天都有新 Agent 上线，我粗略估算内部总数至少在三五百个左右。

这已经不能用“做个 Demo 玩玩”来概括了。现在必须去想的问题是：这些 Agent 怎么来、怎么迭代、怎么养；更关键的是，Demo 如何变成能扛生产的 Agent，真正接入公司业务系统。

过去半年是我接触 AI 以来进步最快的一段。除了内部建 AI 员工，我还同时推进了几十个项目，有停留在验证阶段的，也有已经进入开发的。其中最有体感的是 TokenRank，以及生财有术·会员榜单这个产品。会员榜单从零到一的所有环节都是我亲自操刀，这种真实面向用户的打磨，和只做内部使用完全不一样：用户反馈的压力、迭代的节奏、问题暴露的密度，都会把你对 AI 产品化的理解拉到一个新层级。

基于这些体感，我现在的判断非常坚定：未来十年最值得押注的方向只有一个，就是 Agent。不是某个 AI 工具火、不是某个赛道火，而是 Agent 会重塑几乎所有行业、服务和产品形态。去年我们聊 OAI，今年在公司和生财社区内部的说法已经进化为 OEAgent。重点不再是“会不会用 AI”，而是把 AI 训练成 Agent，让它能承接任务、串联流程、直接进入生产。

所有人都需要统一认知：

**AI 工具只是提升局部效率，Agent 才是重构生产关系。**

## 2 FDE：普通人也能拿到的高位机会

当 Agent 成为十年主线，一个新角色就自然走到台前：所有领域都需要 Agent，所有公司都需要 Agent，所有人都在问谁来做。但 AI 能力、技术理解、业务拆解、落地部署，这四块很难一个人全占。

这个角色就是 FDE。全称 Forward Deployed Engineer，前端部署工程师。最早是一些头部 AI 公司提出的思路：自建强技术平台，然后把人派到客户现场，用 AI 把能力真正落到业务里。

这个概念现在已经在扩散。OpenAI、Claude、国内大模型厂商、飞书等，都在招募和孵化 FDE。这不是某家公司的岗位，而是一种新的能力模型。

通过我这几个月的实践，我反而更看好：

**FDE 不只是大厂的专属，更是独立个体和普通人的弯道机会。** 不同层级的机会当然不一样。对个人而言，如果能卡位到 FDE，很可能迎来十倍级别的增长。如果你正处在职业转型、方向迷茫、找项目的阶段，不妨认真研究一下 FDE。也许几年后你会庆幸今天的投入。

我这几个月做的事，本质上就是把自己打造成公司的 FDE。我先把关键项目、核心产品、服务 Agent 化跑通，再带着团队一起复制放大。

在传统外包里，一个人通常只服务一家客户。随着大模型能力提升，以及你对 AI、业务和部署的理解加深，一个人同时服务多家客户的上限会被不断拉高。未来，一个足够强的 FDE，可能同时托起几十家企业的 Agent 化进程。这种人的价值会非常惊人。

## 3 把飞书改造成 AI 员工的前台

现在打开我的飞书左侧导航，已经不是会议纪要、营业执照、时间表这些过去的内容了，而是几十个 AI 员工的入口，随时待命。

这套东西基本在 5-6 月搭建的。飞书 CLI 上线不久，配合爱马仕等工具，我就把它们组合起来，做成了内部 Agent 体系。

目前飞书里的 Agent 被分成好几个部门，最核心的一个叫“Agent 组织部”。它相当于 Agent 的 HR，负责 Agent 的创建、维护、审核、入职、运维等全生命周期。

### 3.1 Agent 架构师：替我发现可被智能化的工作

组织部里我设了一个 Agent 架构师角色。它接入 Claude Code，有比较高的权限。

这个角色每天能看到我和他人的聊天记录、群内发言、当天会议、文档转发，以及同事间的协作流程。它的日常任务是每天告诉我：哪些流程可以被智能化，哪些环节有被 Agent 替代或重构的价值。

我收到的一大批建议里，有的是工作流可以直接自动化，有的流程可以被重塑。只要我觉得有价值，就让它直接生成对应的 Agent，把那项工作接走。

等于 Agent 架构师接管了我“观察流程、判断智能化价值”这部分工作。

### 3.2 Agent 运维官：让所有 Agent 自动自愈

用上 Agent 之后才发现，运维很耗精力：权限错了、授权过期了、飞书升级导致流程跑不通了……于是我专门建了一个 Agent 运维官。

它按时巡检我所有的 Agent，大部分问题它能自动修复。非紧急问题我也不必立刻介入，等它处理完即可。这样就把我从琐碎的权限、授权、版本兼容问题里解放出来。

### 3.3 Agent 审核官：解决团队 Agent 洪水

现在团队每天上线十几个 Agent，大家各自创建。只靠我一个人审，根本审不过来。每個 Agent 的权限、工具调用范围、风险点都不一样，人工审查成本太高。

所以我又建了一个 Agent 审核官，专门审新 Agent。他会检查权限配置、风险点、是否合理，让 Agent 的扩张不再受限于我个人。

这套组织部里还有技术专家等角色。核心逻辑很简单：Agent 数量上来之后，你不能只造“干活的 Agent”，必须同时造“管理 Agent 的 Agent”。

## 4 已在内部跑通的三大类业务 Agent

目前跑通的 Agent 大致分三类。

第一类是运营类，比如周报自动生成、申请流转、会议纪要、财务对账、微信日报。大量运营琐事已经可以交给 Agent。

微信数据特别有意思，拿到权限后可以做很多自动化服务：读取聊天记录、公众号文章、收藏、通讯录，然后基于这些数据做日报、洞察、提醒。实现细节不展开。

第二类是内容生产类，覆盖选题、改写、发布、转录等。内容链路里有很多有规律但需要判断的重复动作，很适合拆成多个子 Agent 协同完成。

第三类是社群管理类，比如评分卡、帖子筛选、打标签、用户洞察。群里用户在说什么、什么困惑在集中出现、哪些帖子值得沉淀、哪些用户行为需要关注，都能通过 Agent 流程自动化。

这只是开始。我们还在做内部 Agent 工作台，完成后整个体系会再扩大一层。

## 5 案例：我最常用的多平台音视频转录 Agent

我个人使用频率最高的 Agent，是多平台音视频转录 Agent。

原因很简单：我现在几乎不看长视频了。几十分钟、一两小时的课程，或三四小时的播客，即便内容顶级，我也很难一次性投入。YouTube、播客平台都有大量好内容，时间成本太高。

市面上的转录工具普遍有两类问题：一是过度压缩成摘要，细节全丢；二是保留太多口水话，阅读很累。

我想要的是中间态：去废话，但不丢细节。因为真正拉开差距的，往往是细节、案例、推理过程和上下文，而不是一句结论。

于是我做了“小 D”，视频转录助手。它能把主流视频、音频、图文内容转成干净的文档：口水话被过滤，细节最大化保留。对我来说价值巨大，如果市面上有，我愿花上万块买。

使用方式很简单：刷到 Twitter、YouTube、小宇宙上的好内容，直接丢给它。它能把一个 4 小时的 Claude 教学视频完整转出来，我不用亲眼看完。

它不止转录，还会在文档里标注重点，根据我的阅读偏好，标出我已知的、未知的、值得关注的内容。相当于一个非常懂我的超级助理。

背后是一套完整工作流：下载、转录、提纯、写入飞书文档、基于我的上下文标注重点。可以看成若干子 Agent 的组合。

这套方法的 Prompt、流程、Skill 文档我已经分享到星球里。类似这样的 Agent，团队内部还有很多。

## 6 Agent 时代，人要负责什么

当 Agent 能主导流程，人还干什么？我现在越来越清晰，人的精力要集中在几个关键点。

第一，是提出好问题。你要清楚自己要什么，能不能把问题定义好。有想法的人在 Agent 时代会迎来最好的窗口。没有问题、没有好奇心、没有行动欲望，Agent 也帮不出高价值结果。

第二，是判断力。你要判断什么有价值、往哪走。过去我用 AI 时，我在等它：我下指令，它开发，我等结果。现在反过来了，是 AI 在等我。因为我能同时开十几个线程，最多时我同时推进 15 个项目，每个项目里还有多个 Agent 在跑。

这时重要的不是你能不能亲手执行，而是能不能快速判断：这个方向该砍、这个方向该放大、这个结果可否用、这个结果要重做。

很多人用 AI 用得更累，正是因为仍在旧工作流上叠加 AI。旧流程不变，只是把 AI 插进某个环节。线程一多，人就会被判断和衔接拖垮。

更好的做法是让 AI 主导整个生产流程，人做配套。你要把意图、目标、判断标准、样本都讲清楚，让 Agent 重新组织流程，而不是在旧流程里补一块 AI。

这也是 Agent 和传统工作流的核心区别。过去的工作流改造是把 AI 嵌入旧流程，Agent 出现后，效率能提升 10 倍甚至百倍，关键在于：不是让 AI 兼容老流程，而是让 AI 定义新流程。

## 7 幻觉问题的本质：定义、标准、上下文

很多人担心 AI 幻觉、结果不可靠。我的判断是：**AI 是人的能力放大器。** 你本人容易跑偏，AI 也会更跑偏。你讲不清边界、标准、目标，AI 只能靠猜。反过来，你能清晰定义问题、给出好与坏的标准、划清产出边界，它给出的结果往往远超预期，能直接上生产。

对大多数业务场景而言，我们离 AI 的真实边界还远。OpenAI 研究员可能在研究极限，但对我们来说，绝大多数情况 AI 只会带来惊喜。很多“AI 不行”的抱怨，本质是问题、上下文、标准和授权没有讲清楚。

幻觉还和上下文工程有关。现在很火的概念叫 Harness。简单说：Agent 减去大模型能力，剩下的就是 Harness。它包含你有没有搭好上下文、是否给了 AI 足够授权和信任、是否让它理解目标-流程-结果，以及人与 Agent 的角色分工。

这些都清楚了，效果会远超“幻觉期”的想象。

最后一条底线：高风险决策必须人兜底。涉及法律、财务、品牌、重大业务风险的事，不能完全交给 AI。Agent 可以主导流程，但责任必须由人承担。

## 8 团队工作方式：从工具统一到组织重构

### 8.1 为什么我们统一到飞书、Codex、爱马仕 Agent 框架

过去团队的 AI 基建比较分散：有人用 Claude Code，有人用 Codex，有人在飞书做自动化。随着实践深入，我们意识到要让 AI 真正进入组织协作，就必须统一技术栈。

飞书是底座。团队几年的文档、项目、汇报、沟通都在飞书。飞书开放 AI 能力后，Agent 就能无缝接入：发消息、读文档、整理汇报、盯项目、沉淀内容。这不是加一个工具，而是让原有协作系统长出 AI 能力。

服务层统一到 Codex，并不是抛弃 Claude Code，而是现实约束。Claude Code 的 Token 配额消耗很快，个人每周 200 多美金，通常周一到周二就用完；团队账号还常被封。因此现在 Claude Code 只供给核心 5 位工程师。

新成立的工程师团队统一配置：每人 200 美金 Codex 配额 + 250 美金 Pro Code 配额。判断很明确：给工程师足够的 Token 和工具保障，才能产出高质量成果。现在鼓励所有人把 Codex 当主力工作台，在这里建项目、开发 Agent、做产品。过去分散的工作台会逐步收拢到 Codex。

但光有 Codex 不够，要让 Agent 在飞书、企微、微信等协作环境里自动维护、持续运行，就需要一套框架。爱马仕 Agent 框架就是干这个的。它让 Codex 去修、去维护、去处理异常。对大多数成员来说，只要会用 Codex 即可，框架理解即可，维护交给 AI。

目前团队的技术栈是三件套：

- Codex，作为核心工作台；
- 爱马仕 Agent 框架，用于 Agent 自动维护和多平台接入；
- 飞书 AI / 协作体系，用于文档、项目、消息、办公落地。

我们还在做一个内部 Agent 工作台，把所有 Skill、Agent、MCP 聚合，让团队共享能力。把这套栈用好，价值会非常大。

### 8.2 Obsidian、知识库与 Skill：个人和团队是两回事

Obsidian 依然好用，但更适合个人。它是个人知识库，沉淀大量资料，再通过插件接入 Claude Code 或 Codex 处理内容。

团队的核心需求是协作，Obsidian 在协作上很难顺畅，飞书天然更适合。团队在 Codex 做出的 Demo，可以直接一键放到飞书里让所有人讨论、迭代。如果放在 Obsidian，链路会很复杂。

因此团队层面，飞书比个人知识库更关键。即便对个体，我也建议提前用飞书，因为协作、共创、与外部伙伴协同会是常态。飞书文档在分享和协作上的体验依然很强。

“知识库”和“Skill”的边界也在变化。AI 进化很快，很多知识库和 Skill 的能力会被模型和工作流内化。更理想的方式是：让 AI 用它擅长的格式维护知识库，沟通过程自动沉淀成本地库，项目结束自动整理成 Skill，下次同类任务自动调用。

用飞书 Bot 作为入口还有个优势：上下文和记忆能力更强，任务可以在同一协作环境里延续，Skill 复用也更自然。人不需要频繁打开知识库，也不需要手动管理 Skill。

知识库不是没用，而是它不该成为人的负担。最好状态是：**AI** 自己维护知识库，人只负责提问题、定标准、推结果。

### 8.3 普通人最该跨的门槛：先把 Codex 用起来
