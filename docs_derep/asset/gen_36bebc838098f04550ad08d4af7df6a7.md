- 这条素材对业务、内容、方法论、认知、投资机会分别有什么价值
- 它值不值得被进一步加工
- 应该流向哪个出口
- 下一步怎么处理

**复用层**

要进入复用层的前提，是先判断这条素材是否值得继续投入。

复用层可以通向：

- 仅归档保存
- 内容素材
- 资料卡
- 支持卡
- SOP 候选
- 方法论候选
- 项目动作
- 暂时不确定放入输入箱

这里最关键的原则是：候选始终不等于正式。

即便一条素材看起来非常契合，也不能直接定为正式 SOP 或正式方法论。它必须先以候选身份存在，经过多次真实场景的使用和验证后，才考虑升级。

**为什么核心规则必须写进 AGENTS.md**

在搭建过程中，我额外加了一条硬性要求：核心规则不能只沉在详细文档里，必须直接写进 AGENTS.md。

原因在于 AGENTS.md 是 Agent 进入 Founder OS 的第一入口。

如果里面只写一句“请参考某某规则文档”，实际执行中很容易出现：

- Agent 根本没去读
- Agent 读了但理解偏差
- Agent 只读入口，没读细则
- Agent 因上下文过长，执行时丢掉了关键约束

因此我要求把最核心的执行规则直接落到 AGENTS.md 里，包含：

- 三层处理逻辑
- 快速判断标准
- 分流出口清单
- 日常周月复盘节奏
- 候选与正式的边界

详细文档负责展开说明，AGENTS.md 负责让 Agent 用最短路径明白要做什么。

这件事让我更清楚：规则不是给人看的摆设，而是给 Agent 执行时减少绕路的操作约束。规则如果只躺在深层文件里，而没有被稳定触发，那就等于没有进入系统。

**踩坑一：同一指令，不同 Agent 结果不同**

很典型的例子是 Claude 和 Codex 对 douyin-video-to-text 的安装理解不一致。

我让 Claude 安装同名工具，结果它安装的是一个更宽泛的社交媒体转写工具，并非我期望的具体实现。

这提醒我：自然语言指令对人来说明确，对 Agent 来说并不确定。不同 Agent 会基于自身上下文、工具生态、搜索结果产生不同解读。

“安装 douyin-video-to-text”在人眼里很清晰，在 Agent 眼里可能被理解为：

- 安装同名 Skill
- 安装功能相近的替代品
- 安装泛化的转写工具
- 按自身生态选择一个包

最终我选择让 Codex 主导该任务：

1. 先确认 Codex 侧已安装并测通的正确版本
2. 核查 Claude 侧的安装是否一致
3. 不一致则清理掉 Claude 侧的错误工具
4. 将 Codex 已验证的 Skill 对齐到 Claude
5. 统一规则与落点

启示是：多 Agent 协作时，不能默认语义一致。工具、规则、落点必须显式统一。

**踩坑二：工具输出成功，不等于进入知识库**

douyin-video-to-text 能把视频转成文字，但默认写到 Downloads。

从工具视角，这算成功；从知识库视角，这不算成功。

Downloads 只是临时目录，清理即丢失。而且后续在 Obsidian、Claude 插件、Codex 工作区继续加工的前提，是原文必须在 Founder OS 内部。

于是我重新定义成功标准：不是文件生成，而是文件落在了正确位置并可被后续流程调用。

这件事的本质是：知识库系统里，上下文正确性比生成本身更重要。

**踩坑三：txt 能存文字，不适合做长期知识卡**

工具默认产出 txt，简单易用，但不适合长期留存。

因为我需要的不仅是正文，还包括：

- 原始链接
- 平台来源
- 视频 ID
- 采集时间
- 处理状态
- 提炼与分流状态
- 后续衍生产物

用 txt 记录也能实现，但结构松散。可读性和可维护性不足。

因此我决定：txt 仅作为中间产物，进入 Founder OS 的长期原文统一用 Markdown 原文卡。

**踩坑四：AI 交付文件也需要验收**

我曾让 AI 把“每日冲浪信息自生长闭环草图”导出成微信可打开的图片。

第一次生成的是 SVG，微信无法打开。
第二次改成 PNG/JPG，虽然格式对了，但右侧和底部都被裁切。

这说明：文件生成不等于交付合格。若只检查文件是否存在、大小是否正常，很容易误判。

真正的验收标准是：用户能否打开、内容是否完整、有无裁切、是否符合使用场景。

最终我重新生成竖版长图：

1. 不再依赖系统缩略图转换
2. 重新生成竖版 HTML 原稿
3. 浏览器完整渲染
4. 截取完整长图
5. 实际打开 PNG/JPG 核查
6. 确认从标题到“闭环含义”全部完整

结论是：AI 执行完不等于任务完成，任务完成的标准是交付物经过验证且可直接使用。

该原则适用于所有交付：脚本要跑通、文件要读回、索引要可检索、图片要可打开、规则要能触发、状态要无误标。

**最终测试：用一条真实视频跑完整闭环**

规则写好不等于系统可用。所以我用“Codex + Obsidian 自生长知识库”这条抖音素材，跑了一次完整的每日冲浪复用测试。

**第一步：读取原文卡**

**第二步：快速判断**
结论：值得深加工，但仅限候选级。
理由：
- 与 Founder OS 当前建设高度相关
- 提供了多源输入→AI整理→回写知识库→周期复盘的参考
- 已帮助产出原文规则、复用规则和 IP 素材
- 目前仅一条样本，不足以升级为正式 SOP/方法论

**第四步：生成支持卡**

**这套方法适合谁，不适合谁**

**适合**
- 信息输入量大的人
- 想做个人 IP 输出的人
- 已在用 Obsidian/飞书/Notion/本地知识库的人
- 希望用 AI 辅助整理外部信息的人
- 想把资料变成长期资产而非收藏的人
- 愿意维护轻量规则而非追求一键全自动的人

如果你经常遇到：刷到过的好内容找不到、收藏很多但写东西用不上、不知道资料该放哪、日常输入无法稳定成素材，那这套方法可能适合你。

**不适合**
- 只想要一键全自动的人
- 不愿维护规则的人
- 希望 AI 替自己做全部判断的人
- 不区分原文/草稿/候选/正式资产的人
- 还没明确知识库入口就急着做自动化的人

特别是最后一点，若原文位置、状态标记、分流出口都没确定就做自动化，很可能只是自动制造混乱。

**下一步：为何暂不做大自动化**

视频中提到自动抓取、定时日报、自动整理，但我不会马上照搬。

没有验证的自动化只会放大混乱。目前仅用一条素材跑通闭环，还不够。

接下来想用 3-5 条不同来源素材继续验证：抖音、个人公众号、网页文章、小红书。

每条都要检查：
- 能否顺利进入原文池
- 快速判断是否有效
- 分流出口是否合理
- 支持卡/SOP 候选是否可复用
- 索引能否稳定更新
- 是否出现误升级、误发布、误写档案

只有问题被多次验证后，才考虑：
- 每周自动回顾冲浪素材
- 自动挑选值得深加工的素材
- 自动生成待确认分流建议
- 自动提醒候选复验

这些必须建立在稳定规则上，否则自动化是放大器，会把混乱放大。

**结尾：我搭建的不是工具，而是外部大脑的入口**

回头看，做的都是小事：安装 Skill、测试链接、txt 转 Markdown、建目录、写规则、生成流程图、跑一次闭环。

真正有价值的是：冲浪信息第一次被接入知识库系统。

以前冲浪就是冲浪：收藏、转存、遗忘。

现在有了新路径：能否进入原文池？有何用？该分流到哪？能否成内容素材？能否成支持卡？有没有 SOP 候选价值？是否影响项目？需否留到周复盘？

这才是我想要的知识库：一个能持续吸收、判断、复用、进化的外部大脑。

这两条抖音视频，第一条给了入口，第二条给了生长逻辑。我做的事是把它们连起来：

抖音转文字 → Markdown 原文卡 → Founder OS 原文池 → 快速判断 → 分流复用 → 支持卡和 SOP 候选 → 周期复盘。

它还不完美，也不是正式 SOP，但已跑通一次。

下一步会继续用真实素材验证，若稳定再升级为正式 SOP，未来甚至做成 Skill。

一句话总结：真正有用的冲浪，不是收藏信息，而是把信息变成自己的系统。
