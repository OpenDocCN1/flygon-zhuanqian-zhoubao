# Creem 收款配置全流程：一个纯小白的踩坑实录与保姆级指引

做网站出海、赚老外的钱，几乎是每个出海人的共同目标。工具层面我们往往已经打磨得不错，但一到“把钱收进来”这一步，尤其是做一次性买断或订阅制产品，就绕不开一个关键环节——找到一个靠谱的美元收款通道。

市面上常见的选择各有门槛：Stripe 需要折腾港卡，风控又严，新手上手相当劝退；PayPal 在电商里虽然普遍，但往往要求公司主体，个人开发者同样不友好。就在这种背景下，Creem 冒了出来。

它主打的三点很抓人：对中国人友好、款项能直接打到支付宝、接入流程相对简单。这三点凑在一起，如果真能兑现，那确实是个“王炸组合”。

# 三、Webhook 与 ngrok（按需使用）

## 1. Webhook 是什么

直达入口

可以把 Webhook 理解成一个“网络通知器”。

想象你在等快递，有两种方式知道快递到了：

1. 传统方式：隔一会儿就打开 App 查一下物流到哪了（这类似轮询，反复询问、反复拿结果）
2. Webhook 方式：快递员到了直接打电话给你（这就是 Webhook 的运作方式）

## 2. 怎么判断自己要不要用

[PRE22]

以下场景你可能需要 Webhook：

1. 需要实时通知
   - 用户下单后立刻通知商家
   - 博客有人留言后马上收到提醒
2. 需要自动化处理
   - 用户付款成功后自动发货
   - 有人提交表单后自动发确认邮件
3. 需要系统联动
   - GitHub 代码更新后自动部署网站
   - 订单系统和库存系统实时同步

如果你的网站用不到这些实时性或自动化功能，那可能就不需要 Webhook。

## 2. 用 Cursor 连接

### 2.1 支付的逻辑

我让 AI 画了张说明流程图，结果画得非常复杂——看起来好像真那么复杂。简单说就是：

- 前端看到的：用户点付款按钮 → 跳转付款页 → 填写信息付款成功 → 返回某个页面 / 获得积分
- 后端实际：服务器发起请求 → 支付端收到请求，返回一个付款链接 → 服务器把链接给用户 → 用户支付 → 支付端收到支付通知 → 支付端回传消息给服务器（通知支付完成）

大概就是这么个意思（主打一个看图说话）。

网站的支付就两种：一次性（pay one-time）和订阅（subscribe）。下面就手把手带大家试一次一次性付费。

配置规则文档直达

### 2.2 一次性付费（Return URL）

一句话说逻辑就是：配置规则在这里，我有这些配置信息，我希望实现什么效果，你帮我写。

划重点：“配置信息”、“配置规则”、“实现效果”——就这三块。配置信息上面已经搞定了，接下来是配置规则和实现效果。

先确定这次要实现的效果：

⚠️ 整个操作不涉及用户注册和登录，所以实现起来挺容易的，别害怕！即使后面要加注册和登录，也都有第三方集成方案，莫慌！

这个实现逻辑，我们需要一个使用参数 `success_url` 和 `signature 验证`，直接看对应文档的官方解释：

1. 你可以为每个 checkout_session 传一个自定义 success_url，它会覆盖产品上设置的 success_url。这样就能在每次付款后，动态地把用户重定向到自定义页面（适用于付款后把用户引导到他们的专属账户资源）。
2. 返回和重定向 URL 是成功付款后客户会被重定向到的 URL。它们包含由 Creem 签名的重要信息，你可以用这些信息验证付款和用户。

划重点：付款成功、重定向到自定义页面、用信息验证付款（和用户）。

一次性付费总共需要 3 个 API：创建 checkout、生成 signature、验证 signature。
