让 AI 真正落地，最关键的环节是打开它与各种外部系统的沟通通道。

把模型和工具连起来，是从试验走向实用的第一步。

市面上常用的联通手段主要有 MCP、API、CLI 三类。MCP 可以理解成一套让模型挂载外接工具的通用规范。API 则是服务方对外暴露的程序调用口。CLI 就是可以在终端直接执行的指令集合。

具体选哪一种并不重要，关键是连上之后，模型能够自行读取所需信息并把处理结果写回去，这样信息搬运的工作就不用人再手动完成了。

[PRE0]

### 以 Git 作为多 Agent 编程的支点

在代码协作里，让多个 Agent 协同工作最稳的办法就是依托 Git。

Commit 相当于一次代码快照。模型完成一段修改并且测试通过后，可以生成一个 Commit。之后如果出现问题，可以清晰看到改动范围，也能轻松回滚到旧版本。

Branch 是一条独立的开发线路。通常一个需求对应一条分支。Agent 在自己的分支上操作，不会影响主干的运行。

Worktree 则为不同分支分配独立的本地文件夹。一个 Agent 在一个文件夹里处理视频导出功能，另一个 Agent 在另一个文件夹里修复登录缺陷。双方可以同时读写文件、装依赖、跑测试，不会互相覆盖。

当然 Git 并不能自动解决所有冲突。两作业同时改动同一模块，合并时仍可能产生冲突。多 Agent 协同的前提，先要把任务拆分清楚。

### 把重复性操作交给模型

工具打通以后，不必每一步都靠人工点选。

一个完整的工作闭环可以是：先和模型讨论需求，让它整理成 Issue。确认可行后，模型自行读取 Issue 与设计稿，创建分支与工作目录，随后编写代码、执行测试、提交 Commit，再发起 PR/MR。

开发期间，它可以把进展回写到 Issue。上线后若监控报警，模型能够读取日志、定位代码并提交修复。用户行为数据也能作为下次迭代的参考。

人在流程里主要承担三项工作：确认目标、评估方案、验收成果。建立任务、更新状态、管理分支、运行测试、整理日志等重复劳动，尽量交由模型完成。

国内也有对标工具。Linear 可替换为 PingCode、TAPD 或禅道，Figma 可替换为即时设计或 MasterGo，代码仓库可用 Gitee 或 CODING，异常监控可用 Fundebug，用户分析可用神策或 GrowingIO。

名称会变，作用相近：记录项目事实，让人跟模型都能读取。

### 流程可以做减法

个人做项目时，我不会照搬团队的完整规范。

需求通常直接写进 GitHub Issue，或放在项目文档里。一个任务对应一条分支，只有确实需要并行开发时，才会额外创建 Worktree。

页面较为简单时，不会专门维护 Figma，参考图加文字说明即可。产品尚未上线时，也不会急着接入 Sentry 与 PostHog，先把功能跑通再说。

流程精简后，保留三类记录：本次要完成什么、代码改了什么、是否通过验收。

其余可自动化的环节，包括整理任务、创建分支、修改代码、运行测试、提交 Commit，我都尽量让模型去做。

工具连通后，模型会持续读取 Issue、设计稿、代码与日志，Token 消耗自然上升。

但这些消耗用在了真实的推进上，而不是切回对话窗口后重新梳理背景。

## 六、案例一：销售成本报告脚本

前面谈到本地项目、方案调研、上下文沉淀、分阶段开发。接下来用一个销售成本报告脚本把这些方法串起来。

需求本身不复杂。

供货商或采购平台可以导出采购数据，格式多为 Excel 或 CSV，包含商品名称、编号、规格、采购成本。

独立站保存的是销售订单，使用另一套 SKU。供货侧编号无法直接对应销售 SKU，需要先依据商品名称、颜色、尺寸等属性建立映射，再把采购成本与销售数据整合。

手工处理需要在多张表格间反复查找复制，数据量增大后极易出错。

### 1. 从对话进入本地项目

这类任务不适合只在聊天窗口完成。

采购数据、销售数据、生成的报告均在本地。把脚本纳入本地工程后，模型才能直接读取样本文件、修改代码、执行脚本并检查输出的 Excel。

后续更换销售数据时，无需重写逻辑，只需把文件放入指定目录运行即可。

注：并非每个工具都需要 Web 页面或 GUI。轻量脚本在本地处理数据往往更高效。

[PRE1]

### 2. 先调研，再定方案

写脚本前，先让模型理解两边的数据结构。

独立站 SKU 规范清晰，供货商编号仅在其平台内有效，与销售 SKU 并非同一体系。

因此第一步不是计算成本，而是构建商品映射关系。

模型先读取两侧商品数据，整理名称与属性，生成可能的匹配结果。能确定的直接关联，名称相近、属性缺失或存在多候选的单独列出人工确认。

确认后保存为商品映射表。后续脚本据此找到销售 SKU，再将采购成本合并到销售数据中。

按报告需求把处理逻辑固化为代码。之后字段不变即可直接运行，无需模型再介入执行。

### 3. 分阶段开发与验证

可分为四步推进。

第一步，读取各平台数据，统一商品名、颜色、尺寸等属性。
第二步，生成供货商品与销售 SKU 的映射表，未确认项单独输出人工审核。
第三步，依据映射表将采购成本关联到销售订单。
最后汇总销量、销售额、采购成本，生成 Excel 报告。

每完成一步都用真实商品核对。先确认关系，再校验成本与销售。匹配错误，后续计算必然偏差。

### 4. 真实业务推动持续迭代

首版跑通仅说明流程可行。

接入新供货商时表格格式与字段可能变化；新商品需要补充映射；同一 SKU 多次采购时采用最近成本还是平均成本，也需按业务口径确认。

报告日后还可能加入退款、广告费、物流费等维度。

每出现新情况，模型都要重新读取样本数据与项目规则，修改脚本，再用真实数据验证。

Token 主要消耗在分析表格、整理映射、修改代码、排查异常、重新生成报告上。

这个本地脚本虽小，但业务数据与统计口径始终在变化。模型需要跟随变化持续维护，Token 消耗随之提升。

## 七、Token 消耗的第二个门槛：业务需求增多

前几节讲的是如何让项目持续做下去。

流程跑通后，还需要真实业务支撑。否则做一个 Demo 改几轮页面，项目便告终结。

以自动化剪辑为例。

一场两小时直播结束后，团队需要剪出十几条竖屏短视频。

要求自动拼接、加字幕、配 BGM，按固定规格导出。

[PRE3]

听起来是几个功能，实际开发会遇到大量细节问题：

视频无声、编码不兼容、字幕时间错位、素材路径含中文。

每新增一种素材，模型都要重新阅读代码、查看 FFmpeg 日志、修改处理逻辑，再跑测试。

Token 就消耗在这些具体问题上。

再看跨境电商。

卖家同时使用 Shopify、Amazon、TikTok Shop，仓储与供应商又是两套系统。

需要搭建后台同步订单、商品、库存、售后。

难点在于各平台接口与字段不统一。同一商品 SKU 各不相同。取消订单、部分退款、库存锁定规则也各异。

模型需阅读多套接口文档，编写适配代码，查看返回数据，处理限流、授权失效、字段缺失。接入新平台往往要新增一套适配。

财务报表亦然。

老板希望每日看到销售额、广告费、物流费、退款、实际利润。数据源自 Shopify、Stripe、PayPal、Meta 广告、物流商。

模型先厘清口径，再编写脚本抓取清洗汇总。只要金额对不上，就要沿着订单、支付、退款记录回溯。

这些项目耗费 Token，并非代码多难，而是业务细节与例外太多。

模型不断读取文档、代码、测试数据、错误日志，再进入下一轮修改。

真实业务上线后不会停止，新需求、新数据、新问题会持续出现，模型也需持续读取、修改、验证。

Token 的第二次跃迁，源于老项目的迭代维护与新项目的开发。

## 八、Token 消耗的第三个门槛：业务自动交付

到此阶段，使用方式又发生变化。

此前是我在使用模型。现在是业务系统通过 API 调用模型。

API 本质上是程序调用模型的入口。

用户发起请求后，系统自动整理相关数据发送给模型，再把结果写回业务流程。整个过程在后台完成，无需人工打开对话窗口。

当前很多所谓 AI 应用，只是网页里放了个聊天框。用户仍需自行组织问题、补充资料，再把答案复制到别处。

这只是换了入口，并非真正的业务自动化。

判断一个 AI 功能是否真正接入业务，看其结果能否直接驱动下一步：更新任务状态、生成待确认方案、调用已有系统继续处理。

调用模型 API 本身不难，难的是上下文。

模型不知道客户是谁、订单在哪、公司业务规则是什么。这些信息必须由系统在调用时主动提供。

若模型需要查询订单，后端需提供查询工具。模型发出请求，程序查询数据库并返回结果，模型据此继续判断，直至任务完成。

我不会把所有事情都交给模型。

金额计算、库存扣减、权限校验等规则明确的工作，仍由程序处理。模型更适合理解表达、判断类型、整理信息、生成内容。

涉及退款、付款、删除数据、对外发布，我会保留程序校验与人工确认。业务自动化的目标不是让模型随意操作，而是减少人工来回搬运信息、反复判断的步骤。

一次业务处理往往会调用多次模型，每次调用都带上系统规则、业务数据、历史记录与工具返回结果。

个人使用模型，一天能发起的任务有限。接入业务后，每个用户请求与数据变化都可能自动触发模型。Token 消耗开始由业务量决定。

未来所有 AI 产品，表面卖功能，实质卖的是业务封装后的 Token。

这就是第三次跃迁：以前是我调用模型，现在是业务系统在调用模型。

## 九、案例二：小程序 GMV 12K+ 微信小店+知识库自动交付

下面看一个近期上线的案例，AI 服务成为业务核心。数据为上线后真实的 Token 消耗，用于生成分析报告。

这是一个通过微信小店销售的知识服务产品。用户付款后填写问卷，系统结合问卷与知识库生成个性化报告，以 PDF 交付。

流程：微信小店下单 → 自动发货 → 小程序填问卷 → 飞书创建任务 → Hermes 调用国产大模型 → 生成报告 → 自动推送用户

用户付款后系统自动发货。

[PRE5][PRE6]

交付的不是固定资料，而是小程序入口。用户从订单进入小程序，系统校验订单有效后再开放问卷。

问卷提交后自动创建报告任务。用户无需添加客服，也不用发送订单截图。

技术栈主要由微信小程序、微信云开发、飞书、Hermes 与国产大模型构成。

小程序负责交互。云开发处理订单校验、问卷数据、报告文件与消息通知。

飞书多维表格用于管理任务。运营可查看待生成、已完成的报告，也能人工补充信息与处理异常。

本地电脑以 CLI 运行 Hermes Agent，定时从飞书读取任务。拿到问卷后先从知识库检索，再调用大模型生成结构化报告。

报告完成后检查内容与格式，生成 PDF 上传云端，随后通过微信消息推送入口。用户点击后可在小程序查看或下载。

从下单到通知，全程无需运营手动传文件。

[PRE7]

在这套系统里，模型负责理解用户情况、匹配知识库内容、撰写报告。订单、身份、任务状态、PDF 排版、消息通知均由程序处理。

模型层可替换。后续需调整效果或成本时，可接入其他国产模型，小程序与交付流程无需重构。

正式上线前还有合规工作。

小程序需要备案，隐私指引需按实际收集信息配置。姓名、联系方式、业务数据哪些保存、哪些进入模型，需提前确定。

报告由模型参与生成，页面与 PDF 中需保留相应说明。技术跑通只是第一步，备案、隐私与完整交付流程需同步完成。

该虚拟报告商品已售出 600 多份，系统已稳定生成 500 多份报告，整条链路在真实业务中跑通。

每新增一笔有效订单，系统就会自动读取问卷、检索知识库并生成报告。

Token 消耗不再取决于个人每天发起多少任务，而是随业务量增长。

前面提到的本地项目、方案调研、上下文沉淀、业务自动交付，在这个小程序中均有体现。

从对话进入本地项目

小程序代码、云函数、配置与运行日志均保存在工程目录。

模型进入本地工程后可直接读取代码、修改云函数、运行测试并依据日志排查。更换对话或模型，只要重新读取目录即可继续。

## 先调研，再确认方案

开发前需先梳理完整用户路径：小店下单、自动发货、进入小程序、校验订单、填写问卷、生成报告、微信消息通知。

下单自动推送小程序入口；生成报告推送微信服务消息；小程序将部分信息推送到飞书；电脑 Hermes 拉取飞书数据处理后再写回飞书；小程序拉取飞书报表记录。这些易卡点环节需提前做技术验证。任一环节不通就需调整方案。

技术验证时，若平台较大，如微信开放平台、小程序平台，让模型严格按官方文档设计开发，可少走弯路。

[PRE8]

小程序支持云开发、云托管与自建服务器。

自建服务器需备案与域名，耗时较长，不予考虑。

云开发与云托管可走小程序 ICP 备案，审核较快。还能将小程序与小店通过云开发绑定，使用同一套用户身份验证，开发量更少、稳定性更好。

因此部署方案采用 小程序 + 云开发 + Agent 主机。

## 把项目上下文保存下来

项目涉及多系统，依赖聊天记录难以长期维护。

订单校验方式、问卷字段、任务状态、报告结构等需写入项目文档。更换窗口或模型时，模型无需重新询问整套业务流程。

## 分阶段开发与验证

不必一次性跑通整条链路。

先完成小店订单与小程序身份校验，再处理问卷提交与任务创建。流程稳定后接入知识库与大模型，最后完成 PDF 生成与微信消息推送。

每段均用真实数据验证，出问题时可快速定位是订单、问卷、报告生成还是消息通知环节的问题。

所有流程验证完成后可小范围上线，走真实一单测试。再逐步放量，遇到问题也便于处理，不伤用户信任。

[PRE10]

系统稳定后全量发布，开始大规模推广。

当用户量级提升，做直播带货等营销场景时，还需考虑爆单问题。

## 打通各个工具

系统不仅包含小程序。

微信云开发保存订单、问卷与报告文件；飞书管理报告任务；Hermes Agent 读取任务、检索知识库并调用模型。

打通后任务信息可在系统间流转，人无需反复复制问卷、下载报告再手动发送。

## 从真实业务走向自动交付

系统开始接收真实订单后，还需应对问卷未填写、报告生成失败、任务需重试、运营处理异常等需求。

这些并非开发前能全部预见。用户越多情况越多，项目会持续调整。

链路稳定后，每一笔有效订单都会自动触发问卷、知识库检索、模型生成、PDF 制作与消息通知。

## 十、未来

Token 榜单可关注，无需焦虑。

每个人的工作与业务不同，消耗量本无统一标准。

刚开始使用 AI，多问多试，先摸清能力边界，再设定目标。

随后把 AI 嵌入日常工作与真实项目，处理更多重复事务。

有了合适业务，再将其做成可自动交付的产品，或协助他人完成 AI 化改造。

Token 排名只是结果。更值得关注的是，这些 Token 是否帮你节省时间、做出产品、带来真实收入。
